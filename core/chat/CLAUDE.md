# core/chat/ — 智能体工作台对话运行时（K9）

对话式挖洞入口（蛙池式）的独立轻量运行时。**与会话窗/任务队列体系完全解耦**：无 sessions 行、无任务认领、无计划闸——每线程一个 `ChatTurn` 跑一轮（LLM 循环到纯文本回复为止）。复用件：LLM provider（`llm.chat`）、`ToolDispatcher`（工具处理器原样复用，含审计/spill）、`load_expert`（专家池）、技能注册表。

## 数据（blackboard v25/v26）

`chat_threads`（project/agent_id/title/status idle|running|error/parent_thread_id **ON DELETE CASCADE**/spawned_task/todo JSON/usage JSON/**provider+model（v37，2026-10-13：线程级模型覆写，''=跟随全局 executor）**）+ `chat_messages`（role user|assistant|tool / content / **thinking（v31：assistant 行该步推理正文，纯展示不参与重放）** / tool_calls JSON / tool_use_id）。消息按 API 数组序落库，**重放即 LLM messages**。唯一写入口 `store.py`（`bb._tx()`）。

**线程级模型（v37，2026-10-13）**：`POST /api/projects/{pid}/chat/threads` 建线程可带 `provider/model`；`PUT|DELETE /api/chat/threads/{tid}/llm` 设置/重置（坏值 422 不落盘）。`chat_send` 起轮时按线程值经 `llm_store.build(provider, model or None)` 换装 `ChatTurn.llm`，**坏值静默回退全局**（配置事后被删/停用不能把线程卡死）；无覆写才要求 `_llms()` 全局就绪。

`delete_thread` 手动 BFS 收齐后代 → 先清消息再删线程行：chat_messages 外键无 CASCADE 而 foreign_keys pragma 开启，靠 DB 隐式级联会被子消息挡路报 FOREIGN KEY constraint failed。

## 运行时（runtime.py）

- **主控**（agent_id=chat-orchestrator）只做编排与只读查询：todo_write + call_expert + skill_open/kb_search/kb_open/bb_query + `bb_delete_asset`/`bb_delete_assets`（批量，单次 ≤200）/`bb_merge_assets` + **`propose_pack_edit`（经验沉淀唯一出口，2026-10-14 从子专家排除面移回主控）** + mcp__*，不直接执行扫描/利用。专家清单进 call_expert 工具描述（`_generalist`/主控自身不进清单）。**主控态势注入（asset-tri-state D8，2026-10-09）**：`_system_prompt` 主控分支追加 `_situation_context()`——`core.coverage.situation_snapshot` 三态分桶（未测试 open 清单 / 已访问 visited 清单含带洞标 / 已测干净计数）+ 派发纪律（优先未测试、已访问续深挖、已测干净勿重派、`call_expert(asset_ids=...)` 划范围防重复）。**每轮重投影**（态势随黑板演进），读取失败降级占位不阻断。与子专家 `_mission_context`（分配资产台账+维度面）对称，各取所需。**蓝图注入（R4 消费面接线 M1，2026-10-13）**：主控与子专家 `_system_prompt` **均**追加 `_blueprint_context()`——列项目开发蓝图（名/status + 模块名/status/锚点数，**紧凑形态不进 spec/notes 全文**，详情走 `bb_query what=blueprint`），此前 AI 侧完全读不到 blueprints 表；无蓝图返空串不注入、读取失败降级不阻断（上限 `_BLUEPRINT_CAP=10` / `_BLUEPRINT_MODULE_CAP=20`）。
- **技能名≠专家名消歧**：主控 system 同时注入「技能清单」与 call_expert 的「专家」列表，模型曾把技能名当专家名传入——`expert` schema 加 `enum`（值域=`_delegatable_experts`）、技能清单标题标注「下列是【技能名】，不是专家」、未知专家报错同口径；硬校验仍是 `_tool_call_expert`。
- **知识库迭代（kb-iteration，2026-10-14，可选功能）**：项目 `config.kb_iteration.enabled`（默认 False，`core/skills/kbiteration.py` 归一化）**仅主控**在**轮正常收尾后**触发——`ChatTurn.run()` 在 `bb.prune_chat_thread_deltas` 之后调 `_maybe_kb_iteration()`：实时读 `bb.get_project(pid)["config"]` 判开关 → `signals_of` 按本轮事件窗（`self._round_start_event_id`/`_round_start_iso`，起轮前记录）聚合 → `should_trigger` 规则命中才 **spawn daemon 线程**跑 `run_iteration`（LLM 生成 kb/skill 提案，`origin="agent"`）。**绝不打断会话**：提案是后台异步产物，人类在工作区「变更提案」页审批即可（满足「不打断会话」口径）；`run_iteration` 整体 try 包裹，任何异常静默。**为何用事件窗而非会话 id**：子专家活动落在子线程 session 下，按 session 过滤会漏掉，故按事件窗聚合。开关改配置即时生效（每轮现读，无缓存）。**2026-10-15 升级为「Agent 提案总闸」**（Nan 报 bug：开关关闭时主控仍提提案——根因是只有轮末路径有门禁、`propose_pack_edit` 工具路径裸奔）：关闭时 ①`_system_prompt` 不注入「经验沉淀」段；②`_tool_specs` 不下发 propose_pack_edit schema；③`_build_dispatcher` 白名单剔除；④ToolDispatcher 执行层硬闸双保险（实时读，关即时生效；开于轮内翻转下一轮工具面生效）。读开关统一走 `ChatTurn._kb_iteration_on()`（异常/非法按关）。
- **子专家**（agent_id=专家池 id）：AGENT_TOOLS 全量裁剪——排除任务队列/计划/意图/收尾/私信/HITL 控制原语（`_EXPERT_EXCLUDED`；**`propose_pack_edit` 2026-10-14 已移出本排除面**，主控与子专家均可提案，见 `core/skills/kbiteration.py`）；专家 yaml `tools:` 优先；+ mcp__*；无 call_expert（**spawn 深度=1**）。`expert_tool_names` 返回 **None**（yaml 未配 tools）=「全量裁剪」而非空白名单——`_build_dispatcher` 与 `_tool_specs` 必须同一处理，否则 specs 全量给 LLM、dispatch 层全拒。**bb_query 按轨裁剪（track-query-split，2026-10-13）**：`_tool_specs` 末尾把 bb_query schema 换成轨家族变体（`tool_registry.bb_query_schema_for(self.track)`，家族表与语义见 core/agent/CLAUDE.md）——渗透子专家拿不到 func/blueprint/package/feature_tree/logic_block 面，逆向子专家拿不到 site。
- `call_expert`：spawn 持久子线程（parent_thread_id 留档）→ 隔离上下文跑完 → 摘要+线程引用回传；同轮多个并发执行，**最多 8 个同时运行**（2026-10-06 由 4 提到 8——主控常一次并发 5+ 个，4 会让多出的排队串行），超出排队；**每个专家一完成即落库工具结果**（不等整批）——前端靠 2s 轮询 messages 逐个反映完成态，不依赖会滚出窗口的 `chat.tool` 实时事件；乱序落库安全（`_load_history` 装载时按 tool_use 顺序重排）。**`_parallel_expert_dispatch` 恒并发（含单个，2026-10-12）**：只要本批有 call_expert 就走线程池——单个专家此前回落主线程串行，卡在长工具（MCP ≤60s/浏览器/大扫描）时会连带卡住主线程，点停止不生效。**中止即返**：主线程只轮询中止信号，置位立刻返回（显式 `executor.shutdown(wait=False)`，**勿回退 `with ThreadPoolExecutor`**——其退出走 `shutdown(wait=True)` 会阻塞到所有专家收尾）；结果落库职责单一化——**call_expert 的工具结果恒由 `run_one` 落库**，主循环中止分支对 call_expert **不补「已停止」占位**（否则同 tool_use_id 双写）。
- **激进主控（aggressive-controller，2026-10-17）**：第二个**控制器类**智能体（`CONTROLLER_IDS={chat-orchestrator, aggressive-controller}`，`packs/experts/aggressive-controller.yaml`，`tracks:[ctf]`）——与 chat-orchestrator 共用全部委派原语（is_orchestrator 成员判定拿到主控工具面/可委派池/态势蓝图注入），只在**调度策略**上相反：chat-orchestrator 蛙式排队、等整批摘要回来再推进；激进主控**探针海 + 先返先触发**（把题目拆成单一快速探针→同轮多个 call_expert 并发→第一个返回即行动：[命中] 立即派深耕专家、[未命中] 放弃换向）。工作方式文案 `_AGGRESSIVE_CONTROLLER_STYLE` 与 yaml persona 互补（改派发语义必须同步两处）；persona 约定探针结论以 `[命中]`/`[未命中]` 开头。**`_parallel_expert_dispatch(first_return=True)`**（仅 `is_aggressive` 时 `_loop` 传入）：首个结果（+timeout=0 再捞一轮窗口内收尾的）到手即止，剩余探针进 `_probe_abandoned` 转后台；主循环为断候探针补 `_PROBE_PENDING` 占位 tool 结果（**缺 result 的 tool_use 会被网关 400 拒收**，DB+内存同写），worker 完成后**不独占该 id**：真实结果推 `_probe_overflow` + 以**同 tool_use_id 续写**真实 tool 行，`_drain_probe_overflow` 在**每个步边界**（下次 LLM 请求前，`_inject_nudge` 并入尾部 user 消息——**不能新起 user 消息，连续 user 会被 400**）把后台结果并进上下文；`skip_ids` 防时间窗内双落盘进两遍。**断候登记必须在「再捞一轮」之后**（先登记会把窗口内已完成的也标成断候）；**中止路径不标记断候**（worker 照旧落真实结果，原语义不变）。**`_load_history` 同 id 后写优先**：先按 id 汇总最终内容（真实胜出、占位不反向覆盖），回放统一取汇总值——worker 续写行可能落在占位行**后面的 flush 组**（中间隔了别的 assistant），按行序回放会被 `_sanitize_history` 当孤儿 tool_result 丢弃、跨轮只剩占位（2026-10-17 实测踩坑）。前端 `buildWbItems` 同 tool_use_id **取最后一行**渲染（探针卡从「[后台继续]」平滑更新为真实结果）；单结果行历史等价。**委派门禁加严**：`_delegatable_experts` 排除两个控制器 id；`_tool_call_expert` 拒收控制器类目标 + `_is_spawned_subagent`（spawn 出来的控制器线程 depth=1 语义兜底，虽 expert_names=[] 已堵死）；app.py `expert_names` 改 `thread.agent_id in CONTROLLER_IDS` 才发专家池。测试 `tests/test_chat_aggressive_controller.py`（13 例）。
- **激进主控子代理 = 快速子任务（probe_mode，2026-10-17 晚，用户要求「不需要声明意图、不需要查询黑板」）**：`_tool_call_expert` 仅在 `self.is_aggressive` 时给子 ChatTurn 传 **`probe_mode=True`**（chat-orchestrator 的子专家默认 False、行为逐字不变）。probe_mode 五处联动：① **工具面双边裁** `_PROBE_EXCLUDED_TOOLS = ("bb_query", *意图三件套)`——`_tool_specs`（schema）与 `_build_dispatcher`（allowed）必须同步，只砍一边会「看得见调不动/调得动看不见」；② **对话链入口硬拒**（`_dispatch`）：intent/plan 类工具带 plan/control flag，**ToolDispatcher 白名单检查对收尾原语恒放行**（§6.6），只裁 allowed 挡不住模型惯性调 declare_intent，故 ChatTurn._dispatch 显式拒并解释原因；③ **ToolDispatcher `intent_free=True`**：跳过意图先行闸与「发现必挂意图」双检查——否则探针的 run_cmd/bb_add_finding 全被打回、快检瘫痪（错误文案还会指回它没有的工具，纯空转）；④ **维度收敛闸跳过**（`_dimension_gate_status` 对 probe_mode 恒 None）：收敛口径=意图覆盖，与「不声明意图」直接互斥；⑤ **system 注入 `_PROBE_SUBAGENT_STYLE`** + `_mission_context` 换「快速子任务纪律」文案（只砍工具不留口径，模型会按惯性找 declare_intent/bb_query）。**chat-orchestrator 路径零影响**。测试 `tests/test_chat_probe_mode.py`（8 例：工具面/硬拒/intent_free 双闸/维度闸/system/spawn 接线，含对照）。**附件可读性修复（2026-10-17，用户报「附件贴给激进主控、子代理无法读取」）**：根因是 `_attachment_lines`（core/agent/loop.py，对话轮与任务链共用）渲染**裸工作区相对路径**（`artifacts/attachments/<f>`），而所有消费方基准都是 **scratch**（read_file/search_files 相对路径基于 scratch 解析、run_cmd cwd 恒为 `<ws>/scratch`）→ 裸相对路径谁都读不到（实测该轮 3/4 探针全「文件不存在」，只有一个瞎猜 `/workspace/...` 的探针读到了 ZIP）。修法=渲染 **`/workspace/<rel>`**（系统约定的工作区根：读工具 `_resolve_read_path` 映射回宿主工作区、docker run_cmd 同根；host/wsl run_cmd 用 `../<rel>`）。`_PROBE_SUBAGENT_STYLE` 同步加第 3 条「读项目内文件」口径（防止模型把 `/workspace/...` 再相对化）；`bb_declare_challenge` 回执删掉不兑现的「压缩包会抽成可浏览的文件树」承诺（无抽取逻辑）。测试 `tests/test_attachment_read_path.py`（5 例：渲染形态/探针 read_file+search_files 真读到/裸相对路径仍报错固化 bug/chat run() 注入行）。
- **对话链意图链路**：意图三件套 + `bb_delete_intent` 开放给对话主控与子专家，与任务管线同纪律——`bb_add_finding` 意图先行门禁扩到 `chat-*`；子专家交摘要前若有 open 意图须先 `close_intent`（主控豁免，它是调度者）；`declare_intent` 回执按轨附 `[意图口径]` 提示。
- **CTF 轨 flag 纪律（ctf-kernel 接线，2026-10-19）**：`_CTF_CORE_TOOLS` 含 `ctf_submit_flag`（激进主控工具面 26 项），`_challenge_context()` 末尾追加两条纪律——①「拿到疑似 flag 一律走 `ctf_submit_flag`，别直接 `bb_add_finding`」（三道机械判定：形态置信 / 变换回环 / 跨题防串，见 `core/ctf/CLAUDE.md`）；②「管理员密码/API key 这类非 flag 格式命中用 `candidate=true` 登记为候选线索（intel/未验证），不判为解出」。`_AGGRESSIVE_CONTROLLER_STYLE` 同步一条（改 flag 口径必须两处同改）。非 CTF 轨 `_challenge_context` 返空串、`ctf_submit_flag` 直接拒——零影响。
- **严格单一派发 + 维度收敛闸 + 资产越界闸（agent-path-intent-loop M2/M3，2026-10-09）**：`call_expert` 新增 **`asset_ids`**（资产 id 数组，服务端逐个校验同项目存在，非法回 `[错误]`）——主控把该子专家负责的资产**显式划给它**（不同子专家分不同资产，避免重复测试）；未分配（查询/登记类委派）不强制。`ChatTurn.__init__` 接 `assigned_asset_ids`（spawn 时透传，`chat.spawn` 事件带 `asset_ids`），`_mission_context()` 把「本线程分配资产（含『未分配资产仅可 bb_add_asset 上报』约束）+ 测试维度面清单（`core.dimensions.load_track_dimensions`）+ plan→execute→plan 纪律」注入子专家 system（不进消息历史，读取失败降级占位不阻断）；`_tool_call_expert` 的 `chat.spawn` 事件带 `asset_ids`。**收敛闸 `_dimension_gate_status()`**：仅 spawn 子专家（parent_thread_id + spawned_task 均有）且（`assigned_asset_ids` ∪ 本线程意图锚定资产）非空时启用（主控/无目标资产/本轨无维度清单返 None 不拦）；逐资产按 type 匹配适用面做 `dimension_coverage`（面覆盖 ⟺ 该面有 ≥1 closed 意图且无 open），ok=所有适用面都覆盖。**未覆盖、或分配了资产却一条意图都没声明（`empty`）→ `_loop` 纯文本收尾前推回 plan**（nudge 明写未覆盖面 id + `declare_intent(dimension=..., target_asset_id=...)` 指令），连续 `_DIMENSION_GATE_MAX=5` 次仍不给 plan 才放行并落 `chat.dimension_gate`（phase=nudge/giveup）。**资产越界闸（M3）**：`assigned_asset_ids` 非空时子专家的 ToolDispatcher 命中 `_ASSET_REF_TOOLS` 且引用集外资产 → `[越界拒绝]`（见 core/agent/CLAUDE.md）；bb_add_asset 恒放行（上报通道）、bb_query 只读不拦。open 意图另有独立守卫，先生效。
- **流式事件**：`chat.delta`/`chat.thinking.delta`（节流 ≥6 字符或 0.05s≈20Hz，2026-10-04 由 80/1s 一路压密求顺滑）→ 每步完成落 `chat.thinking` 终稿；工具调用落 `chat.tool`（**phase=start/done 两段，均带 `tool_call_id` 用于并行调用配对**；并行专家在 worker 内发，单专家/普通工具在主循环发——**三条路径都必须发 done**，单专家此前漏发致工具行一直「运行中」）；终稿 `chat.message`；spawn 落 `chat.spawn`。**消息全文以 chat_messages 表为准，事件只做实时可见**；**思考正文（v31）随 assistant 消息落库**（`append_message(..., thinking=)`），轮结束后前端仍能渲染「已思考」折叠行。**顺滑要三处同步压密**：节流阈值 + WS 投递节奏（app.py `ws_events` 1s→50ms）+ 前端 flush 窗口（`useEvents` 的 `flushMs`，工作台传 50ms）——只降其中一处=白降。轮**正常收尾后**调 `bb.prune_chat_thread_deltas` 清剪本轮流式 delta（终稿全文已在 chat_messages；异常/中断不调，残留=现场审计）。
- **工具历史严格配对（2026-10-04）**：`_sanitize_history` 装载旧线程时按 assistant tool-use ID 去重、只保留首个同 ID result、按 tool-use 顺序重排并补缺失占位，孤儿/错配结果不回放；当前 `resp.tool_calls` 落库前拒绝空/重复 ID、空工具名和非 dict 参数。修复只作用于内存回放，原始 chat_messages 审计不删除。

## MCP 桥（mcp_bridge.py）

读 `config/mcp.json`（app 传 `MCP_CONFIG_PATH`），按项目域过滤（domains ∩ capabilities∪track）。transport：streamable-http（JSON-RPC over HTTP，initialize→Mcp-Session-Id→initialized→tools/list/call，**只允许 loopback**）+ stdio（子进程行分隔 JSON-RPC，后台读线程收响应、stderr 排干、崩溃重拉一次）。工具名 `mcp__<server>__<tool>`；tools/list 300s TTL 缓存；单 server 离线不阻断。**stdio 命令 `python`/`python3` 是平台解释器占位**（`_resolve_command` → `sys.executable`，本进程环境已带 `mcp`/`httpx`；打包形态或其它命令名原样返回）——2026-10-08 fir-proxy 由 `uv run --active` 改此：`--active` 依赖 `VIRTUAL_ENV`，平台自 `.bat` 直起时为空致 uv 用无 `mcp` 的解释器，`tools/list` 失败。**无 `Mcp-Session-Id` 头的 http server**（如 x64dbg 调试器插件 `127.0.0.1:3000`，2026-10-08）：握手成功即置 `_HttpConn._ready`，不再因 `_session_id` 恒 None 而每次调用重握手（仅掉线 `status==0`/4xx 复位重握）。要点：

- **会话级 server 隔离**：`SESSION_SCOPED_SERVERS={"playwright"}` 的 stdio server **按 `(server, session_id)` 各起独立子进程**（环境变量 `PW_SESSION_ID` 传会话标识，启动器据此派生独立 Chrome profile/CDP 端口）——修「多会话抢同一持久化 profile」；同会话多轮复用同一进程（登录态跨轮保留）。**子进程回收（2026-10-11 事故修复）**：`_load_servers` 60s 重载旧实现**无条件重建 runtime 且从不 kill 旧 stdio 子进程**——每 60s × N 项目催生海量子进程 + reader 线程（实测残留 356 个 fir_proxy_mcp + 179 playwright + 79 fofa，进程线程数破 1500）。现重载时**同配置且存活的 runtime 原样复用**（`MCPServerRuntime.cfg_key` 指纹比对，配置变才重建），被丢弃的 runtime 一律 `close()`（`_StdioConn._reap_proc`：kill → 关 stdin/stdout/stderr → wait，唤醒等待者并放 reader 线程退出）。`_LazySessionServer` 同样加 `close()` 回收探针进程。`ChatTurn._dispatch_mcp` 传 `session_id=self.thread_id`。`MAX_BROWSER_SESSIONS=10` 限并发，超限回结构化错误，已死会话配额自动回收；装配工具面用 `PW_NO_CHROME=1` 探针进程（只 tools/list）；`status()` 标 `session_scoped=true`；启动器**默认 30 分钟无 MCP 操作**（`PW_IDLE_MS` 可覆盖；代理 stdio 在 `tools/call` 打点，判据是「有无操作」非「有无活动页」）→ 关自管 Chrome + 删 profile + 释放锁；**仅自管/复用 Chrome 路径启用**，内嵌项目浏览器（`PW_BROWSER_CDP_ENDPOINT`）不起 Chrome、不走该看门狗。
- **项目内嵌**：Playwright 调用按项目注入 `PW_BROWSER_CDP_ENDPOINT`，先启动 `BrowserPool` 的项目持久浏览器，再让 MCP 通过 loopback CDP 接入同一 context/profile——共享登录态/页面/抓包链路，不再另起外部 Chrome。stdio server 统一以仓库根目录为 cwd。
- **stdio 握手**：`_StdioConn._rpc` 先做 MCP 握手（`initialize` → `notifications/initialized`）再发业务请求，每次进程重启后重做（`_ready` 标志）——缺握手时 `@playwright/mcp` 的 `tools/call` 会被拒（`tools/list` 却可能成功）。启动器：`--user-data-dir` 必须排在 `--remote-debugging-port` 前；端口跳过 Windows TCP 排除段（本机 8421~9880），默认基址 **14000**；绑不上调试端口时换端口重试而非降级自托管浏览器（降级会丢会话隔离）。
- **FOFA 密钥统一（2026-10-11）**：stdio server 的附加 env 统一由 `_env_for_entry(name, entry)` 组装——基线=`mcp.json` 条目 `env` 字段；**`FOFA_SERVERS`（`fofa`/`fofa-search`/`fofa_mcp`）额外注入 `config/fofa.json`（测绘设置）的 `FOFA_KEY`/`FOFA_EMAIL`**（`_fofa_env_from_config()` 实时读，`setdefault` 让显式 env 优先）。动机：fofa MCP server 自读它自己目录的 `.env`，与测绘 `config/fofa.json` 漂移成两份 key；`fofa.py` 优先取进程 env 且 `load_dotenv` 不覆盖已存在变量 → 注入即统一。两处 spawn（`_load_servers` 非会话级 + `_server_for_session` 会话级）都走此 helper，勿各自拼 env。
- **代理池全局化（2026-10-11）**：`fir-proxy` 是**全局域 server**（`MCPBridge.PROJECT_AGNOSTIC_SERVERS`）——**不注入 `PW_PROJECT_ID`**（池已全局化，工具打 `/api/proxy/*` 无 pid）。其余非会话级 stdio server 照旧注入。
- **重活工具体积闸（2026-10-13）**：`MCPBridge.call` 命中 `HEAVY_MCP_TOOLS`（默认 `{"survey_binary": 30MB}`）时，先调该 server 的 `server_health` → `input_path` → `stat` 取**当前库对应源程序大小**；≥阈值即返回拒绝文本、**不转发**（GUI 上的全量工具会把 IDA 主线程占死、界面卡死）。**fail-closed**：拿不到大小（探活失败/`input_path` 空/文件缺失）一律拒。阈值与引擎分析的 10MB **有意不同**（前者是对已开库的重活遍历、后者是新分析）；后续别的全量工具按同一清单扩。**重活工具调用超时放宽到 180s**（`HEAVY_CALL_TIMEOUT`，用户口径「等待拉到 3 分钟」）——默认 60s 对全量工具不够，会先超时报「server 离线或协议错误」；其余工具维持 `_CALL_TIMEOUT=60s`（`MCPServerRuntime.call(*, timeout=)` 透传）。

## API 与边界

- 端点（app.py「智能体工作台」节）：`GET /api/chat/agents?pid`（主控+专家池，排除 _generalist）/ `GET|POST /api/projects/{pid}/chat/threads` / `GET|DELETE /api/chat/threads/{tid}`（detail 带 messages，after_id 增量）/ `POST /api/chat/threads/{tid}/messages`（**202 + 后台线程跑轮**；同线程并发 409；`app.state.chat_running` 去重）/ `GET /api/chat/mcp?pid`。`_pid_of_chat` 反查项目 id。
- **中止**：`POST /api/chat/threads/{tid}/stop` 置每线程一个 threading.Event（`app.state.chat_abort_events`，轮次收尾弹出防泄漏）→ ChatTurn 在**步间 / llm.chat 流式帧（should_cancel 逐帧探测）/ 工具分发前 / 并行专家等待**（`_parallel_expert_dispatch` 用 `wait(timeout=0.3)` 轮询替代裸 `as_completed`，且中止时 `shutdown(wait=False)` **不等待**专家收尾——主线程立即回步边界结束本轮）退出并落「已按人类要求停止」消息（stopped:true）；事件向下传（call_expert 子轮同事件、ToolDispatcher abort_event 进 run_cmd）。**2026-10-09 语义修正**：中止抛 `ChatStopped` 专用异常直达 `run()`——归位 `idle` 并落停止说明，**绝不落错误卡**；此前中止被当成可重试流中断（只吐 thinking 时原样重发 ≤3 次、有半截文本时续写 ≤10 次）再 `_classify_error` 判成 `unknown`「执行异常」（用户实测：点停止要等很久且落错卡）。**2026-10-12 修复「派发子代理时点停止不立刻停」**：根因=主线程阻塞在 `_parallel_expert_dispatch` 的 `with` 退出（`shutdown(wait=True)`）直到所有子专家自然收尾，卡在长工具（MCP ≤60s）里的子专家能拖住整个停止。现改 `shutdown(wait=False)` 立即返回。**遗留**：子专家若卡在**不可中断的工具**（MCP `_CALL_TIMEOUT=60s` 内无 abort 探测）仍会继续跑完才收尾——但主控已即时停止，仅该子线程短暂残留。没在跑返回 **204**（幂等，前端状态刷新竞态）；线程不存在 404。
- 无 per-thread 模型选择（全局 executor LLM）；LLM usage 不进 orchestrator_state 记账。chat.* 事件未接 lib/events.tsx 样式（事件流显原始 JSON；工作台内已结构化渲染）。
