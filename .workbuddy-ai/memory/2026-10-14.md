## kb_search 单次调用卡 4 分钟 —— 根因定位 + 修复（core/skills/kbsearch.py）

- **触发**：上条工具执行 bug 的副产物——第一个 `kb_search` 从 10:16:25 跑到 10:20:27，
  后面排队的工具全被堵住。
- **链路**：`writing.search_kb` → `KbSearchIndex(packs_root).search()`，而 **`search()` 每次
  都 `self.sync(capabilities)`**（无独立后台索引器）；`_tool_kb_search` 按能力逐个循环 →
  一次工具调用 = N 次 sync。
- **根因**：`kb_documents_fts.path` 是 **UNINDEXED** 列，FTS5 对非 rowid 条件的 DELETE 只能
  **全表扫 content 影子表**；`_sync_locked` 原来**逐行** `DELETE ... WHERE path=?` → 删 N 行
  扫 N 次 → **O(N²)**。库越大越慢。
- **实测证据**（643 篇 web / 12.1 MB 微基准）：逐行删 **3.86s**；不删 **0.46s**；
  `executemany` **0.39s**。整体：纯文件读+解析 1796 篇 = **1.72s**，全量重建 = **46.0s**
  （≈44s 全耗在 DB 写）。
- **修复**：新增模块级 `_delete_fts_rows(con, keys)`——`IN (?,?,...)` 分块（`_DELETE_CHUNK=400`，
  低于 SQLite 999 绑定上限）批量删，一条 SQL 只扫一次；`_sync_locked` 重写为「先定 pending
  集合，再一次性批量删旧行 → 插入」，stale 清理同样走批量。
- **效果**：全量重建 **46.0s → 6.5s（7.1x）**；路径漂移 churn **92.5s → 3.3s（28x）**；
  热态同步 1.32s 不变。索引一致性保持 1796/1796；真实检索 `search_kb` **0.42–0.56s**。
- **零回归确认**：`git stash push -- core/skills/kbsearch.py` 前后跑同一组测试，基线完全相同
  （**21 failed / 51 passed**，失败项是既有 FastAPI/Starlette 环境不兼容 + 无关规则模板/同义词
  用例；`test_kbsearch.py` 单独跑全过）。
- **文档同步**：`core/skills/CLAUDE.md` 补 `kbsearch.py` 模块行，写明「**新增按 path 删 FTS 的
  代码一律走 `_delete_fts_rows`，勿写逐行 DELETE**」这条红线。
- **为什么偏偏是那一次**：知识库刚做完「树状化」重构（大量改名），首个查询撞上最大规模的
  陈旧/新增 churn，叠加 235MB 被重写放大的库。

## CTF「资产 → 题目」改造 —— 现状调研（Nan 提需求，待决策，尚未动代码）

- **需求**：① 「资产」改叫「题目」；② 用户建题目时自动在题目内加一个节点表示这道题，
  意图/发现绑到对应题目上。附件形态：压缩包 / 文件夹 / 网址。
- **诊断**：CTF 轨的资产模型整套继承自渗透轨（`domain→host→service→url` + `binary`），
  前提是「目标是站点」，靠 DNS/CDN/覆盖度三态驱动，对「一道题」完全不成立。后果是
  findings/intents 的 `target_asset_id` 普遍为空 → 前端归入「项目级（未挂载具体资产）」
  分组（`Blackboard.tsx` 的 `projectLevelFindings`），截图三条发现即是。
- **关键事实（决定改造方案）**：
  - `assets.type` 是**自由 TEXT、无 CHECK 约束** → 新增 `challenge` 类型 **零 schema 迁移**。
  - `register_asset(bb, pid, value, type_="challenge", parent_id=…)` 支持显式 type，
    走不到 `detect_type`（`challenge` 名如「web-easy-1」本来就识别不出，必须显式传）。
  - `findings.target_asset_id` / `intents.target_asset_id` **已是**指向 `assets(id)` 的外键
    → 绑定零成本；`attackpath.py` 已是「以某根资产为界做子树」，题目节点可直接当
    `target_root_id`（它只要求 id 存在于 assets，host/domain 名字集为空不影响）。
  - `core/coverage.py::COVERAGE_TYPES = ("host","domain","url","service")` **不含 challenge**
    → 题目节点不会派生 `effective_status`，也不进 `situation_snapshot` 的未测/已测清单
    （好事：避免主控把「题目」当待测资产反复派单）。题目状态应改由前端按子树聚合。
  - `bb_add_finding` 的 `target_asset_id` **可选** → CTF 轨可加「缺省挂题目根」。
  - 前端「资产」字样共 **93 处**（`Blackboard.tsx` 29 / `lib/events.tsx` 9 /
    `SampleAnalysisView.tsx` 8 / `lib/types.ts` 8 …）→ 全局改词有风险（渗透轨的
    domain/host 叫「题目」是错的），建议抽 `assetLabel(track)` 做**轨内改名**。
  - 分析包（`SamplePackageStore`）已能把 zip/文件夹抽成项目内内容寻址树
    （`<project>/trees/<manifest_sha256>/`），登记资产时**不复制文件**只记包坐标
