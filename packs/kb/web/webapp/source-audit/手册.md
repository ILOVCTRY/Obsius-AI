# 源码白盒审计方法论（覆盖率矩阵与三策略）

> 白盒 = 手里有源码，能读文件、能追数据流、能枚举端点。与黑盒手册（`web/webapp/*/手册.md`）的分工：
> **白盒负责"哪条路径真能打通"，黑盒负责"这条路径在线上是否真生效"**。两者证据互补，不互相替代。
> 本手册回答三个问题：**先查哪、用什么策略查、查到什么程度才算查完。**（面向 CVE / 0day / 深度审计场景。）

---

## 一、覆盖率矩阵（查完与否的判定尺）

审计容易漏的根因：只搜了核心模块、假设"有防护就安全"、假设"某路径不可达"。对策 = **先测绘完整攻击面，再逐维度判定覆盖**。

| # | 维度 | 关键问题 | 策略 |
|---|------|---------|------|
| D1 | 注入 | 用户输入能否到达 SQL/命令/LDAP/SSTI/表达式执行点？ | sink |
| D2 | 认证 | Token/Session 的生成、校验、过期、密钥是否完整？ | config |
| D3 | 授权 | 每个敏感操作是否校验资源归属？CRUD 权限是否一致？ | control |
| D4 | 反序列化 | 是否存在不可信数据的反序列化？利用链是否可达？ | sink |
| D5 | 文件操作 | 上传/下载/读取路径是否可控？是否路径穿越？ | sink |
| D6 | SSRF | 服务端出站 URL 是否用户可控？协议/内网是否受限？ | sink |
| D7 | 加密 | 硬编码密钥/IV？ECB 或无 MAC？弱 KDF？证书校验被绕过？ | config |
| D8 | 配置 | 调试端点（Actuator/pprof）、过宽 CORS、错误堆栈是否暴露？ | config |
| D9 | 业务逻辑 | 竞态、金额篡改、流程跳步、Mass Assignment、水平越权？ | control |
| D10 | 供应链 | 依赖是否有已知 CVE？版本是否在安全区间？ | config |

**覆盖判定（✅已覆盖 / ⚠️浅覆盖 / ❌未覆盖）按策略分轨**——见第二节；**D1+D2+D3 任一 ❌ 不得出结论**。

## 二、三条审计策略（不同维度用不同打法）

**关键区分**：Grep 命中 ≠ 覆盖；**追到 sink/端点的数据流才算覆盖**。

### 2.1 sink-driven（D1/D4/D5/D6）
- 打法：Grep 危险函数 → Read 定位上下文 → 从入口点向上追数据流到 sink → 验证净化/绕过。
- ✅ = 该维度核心 sink 类别都搜过 + 有数据流追踪 + **扇出率 ≥ 30%**（已追踪文件数 / Grep 命中文件数）。
- ⚠️ = 仅 Grep 未追踪 / sink 类别有遗漏 / 扇出率 < 30%。

### 2.2 control-driven（D3/D9）
- 打法：**枚举端点 → 逐一验证控制是否存在 → 缺失即漏洞**（不靠 grep 危险代码，见 `web/webapp/control-gap/手册.md`）。
- 输入 = **端点-权限矩阵**（路径 / 方法 / 认证要求 / 权限注解 / 资源归属校验），先行测绘。
- ✅ = 端点审计率 ≥ 30%（standard）/ ≥ 50%（deep）+ 至少 3 类资源做过 CRUD 权限一致性对比。
- ⚠️ = 只 grep 了 pattern、没系统枚举端点验证（**仅 sink 搜索不算 control 覆盖**）。

### 2.3 config-driven（D2/D7/D8/D10）
- 打法：搜配置项/依赖版本 → 对比安全基线（默认口令、调试开关、算法强度、依赖 CVE）。
- ✅ = 核心配置项与版本/算法均已对照基线。

## 三、五阶段精力分配

| 阶段 | 目标 | 精力 |
|------|------|------|
| 1 侦察 | 技术栈、入口点、认证链、模块地图、快速排除（0 命中即跳过该方向） | 10% |
| 2 模式扫描 | 关键词/Grep 定位潜在漏洞点（广度） | 30% |
| 3 关键路径手审 | 高风险文件逐行读 + 数据流追踪（深度） | 40% |
| 4 验证与攻击链 | 确认可利用性、构建跨模块链 | 15% |
| 5 报告 | 结构化输出 + 修复建议 | 5% |

**反隧道视野**：单一模块不得超过阶段 3 时间的 30%；同类文件 ≥3 个共享同一模式时，合并为 1 条发现 + 影响清单，不逐个深挖。
**部署模式感知**：`application-*.yml` / Dockerfile 变体可能启用或禁用关键 Filter——不同 Profile 的端点要单独判定。

## 四、两条铁律（坑最多的地方）

### 4.1 证据锚定（防幻觉）
- **先验证文件存在再报告**：禁止凭"典型目录结构"猜路径；`file_path` 必须是你**实际 Read 过**的文件。
- **引用真实代码**：代码片段与行号必须来自真实读取，知识库里的示例**不是**目标项目的代码。
- 原则：**宁可漏报，不可误报**——1 个真实可利用漏洞 > 20 个无法验证的疑似项。

### 4.2 终局结构化（防"假完成"）
- 结论必须落**结构化字段**（位置 file:line、source→sink 链、PoC、影响），不接受"自然语言说完成了"。
- 单条发现**不足以收尾**：发现 1 个漏洞只代表当前攻击面有收获，不代表审计完成。
- 收尾前逐条自问：**还有哪些攻击面没碰过？** 未覆盖维度必须显式标注。

## 五、严重度校准（多来源发现防漂移）

同一漏洞可能被不同轮次/不同视角评出不同等级。统一口径：

```
严重度 = f(可达性, 影响, 利用复杂度, 防护绕过)
  可达性:   未认证可达(+2) / 低权限(+1) / 管理员(+0)
  影响:     RCE 或全库(+3) / 部分数据(+2) / 信息收集(+1)
  复杂度:   单请求(+0) / 多步骤(-1) / 特定环境(-2)
  防护:     无防护(+0) / 可绕过(+0) / 绕过需额外条件(-1)
  合计 ≥5 Critical | 3-4 High | 1-2 Medium | ≤0 Low
```
- 决策树等级与原始等级差 1 级取决策树；差 ≥2 级标"等级争议"并说明两种理由。
- 同一 sink 类别的多个实例，取最高实例等级作为该类统一值。

## 六、攻击链构建（把低危拼成高危）

对每个 Critical/High，标注 **前置条件**（需认证? 需何种权限?）与 **利用结果**（信息泄露/RCE/提权/文件读写）；当发现 A 的"结果"满足发现 B 的"前置条件"时即候选链 `A→B`。

- 典型链型（启发，非穷举）：认证绕过 → 需认证的 RCE / 信息泄露 → 取密钥 → 伪造 Token → 管理 API / SSRF → 云元数据 → 凭证 → 内网。
- **每条链最多延伸 3 层**；报告里"攻击链"单列，与独立漏洞列表分开，并给"组合等级"。
