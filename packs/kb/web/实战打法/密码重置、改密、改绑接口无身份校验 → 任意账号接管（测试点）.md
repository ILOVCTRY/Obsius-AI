# 密码重置、改密、改绑接口无身份校验 → 任意账号接管（测试点）

> 场景：高校自研 ASP.NET/PHP/Java 报名、赛事、教务类系统。典型漏洞：密码重置/找回接口只校验弱标识（姓名、学号、手机号、邮箱之一或组合），且**把用户名/手机号/邮箱也当作可写字段**，导致攻击者凭公开/社工信息接管任意账号。
> EDUSRC 判级：`rating:edu-rating` 高危#2「任意账号密码修改 / 重要业务配置修改」（实证即高危）。

## 一、攻击面识别

- 登录页旁的「密码重置 / 忘记密码 / 找回密码 / 改绑手机」入口（`Reset.aspx`、`ResetPassword.aspx`、`forget.jsp`、`findpwd.do` 等）。
- 注册页 `Register.aspx` 常泄露字段结构（含 `TB_username`/`TB_pw` 等命名），重置页字段可与注册页对照。
- 前端常只做 `$.md5(pw)` 后提交（密码明文不下发），**校验完全在服务端，也完全可能缺失**。

## 二、无损探针（不触碰他人账号）

1. 先看重置表单有哪些字段：`姓名/邮箱/用户名/新密码` 同时出现 → 高度可疑（用户名本不该在重置里可填）。
2. 用**不存在的身份**提交（如 姓名=zzz_nonexist、邮箱=zzz@example.invalid）：
   - 返回「姓名或邮箱与注册时不符」→ 证明服务端**仅按 姓名+邮箱 匹配**，用户名不参与校验。
   - 返回「重置成功」→ 更危险（可能不校验任何存在性）。
3. 看是否要求邮件/短信验证码、原密码、二次确认——全无即可疑。

## 三、无害化闭环验证（关键：只在自建账号上做）

1. `Register.aspx` 现场注册一个测试账号（拿到已知的 姓名/邮箱/用户名/密码）。
2. 基线：`POST 登录页` 用该用户名 → 观察区分性报错（如「已停止学生用户登录！」= 账号存在；「系统无此用户」= 不存在）。
3. 提交重置：姓名+邮箱=真实值，**用户名填攻击者想要的新值** → 返回「账号重置成功」。
4. 验证接管：原用户名登录 → 「系统无此用户」（原用户名失效）；新用户名登录 → 有效账号报错（新用户名+密码已生效）。
5. **复原**：再次重置把用户名/密码改回原值，不留残留。
6. 全程**不碰任何真实用户账号**；仅在报告里说明「若掌握真实用户姓名+邮箱即可接管」，并把管理员路径标为未验证的推测。

## 四、避坑

- 学生/普通用户登录若被站点禁用（「已停止学生用户登录」），无法用登录成功来证明「密码被改」——改用**用户名存在性报错**做差分（旧名→无此用户、新名→存在），即可证明账号被改写。
- 站点公开的联系人邮箱（页脚「网站管理」等）可作社工输入；但**不要**对真实联系人账号执行重置，只在自建账号闭环。
- 别把「重置成功」当唯一证据——要打出「原用户名失效 + 新用户名生效」的差分。

## 五、修复建议

重置必须走带时效的一次性邮箱令牌；禁止重置接口修改用户名；加频率限制与验证码；重置后强制原会话失效并通知账号所有者。
