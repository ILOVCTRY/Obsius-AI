# 逻辑漏洞与状态机判据库

> 来源：`web/赛事专题/Writeup合集` 中 46 篇逻辑题 + 28 篇 Web3 题（324 条观测 / 201 条失败尝试）。
> 主库 `漏洞分类/业务逻辑/逻辑漏洞.md` 与 `条件竞争/竞态条件.md` 已覆盖基础，
> 本文补**数值溢出的具体位宽判据**与**DeFi 比例凑单**两类主库没有的内容。

## 0. 判据速查

| 现象 | 判据 | 去哪节 |
|---|---|---|
| 金额/数量字段可改，服务端不校验范围 | 负数、零、超大值三连试 | §1.1 |
| 数值参与比较但类型是 32 位无符号 | `2^32 - N` 可绕 | §1.2 |
| 有「先查后改」的两步操作 | TOCTOU 竞态 | §2.1 |
| 优惠券/积分/库存有并发窗口 | 单包多请求（H2） | §2.2 |
| 状态机有 `pending`→`paid`→`done` | 跳步或回退 | §3.1 |
| 有 `sign`/`token` 但只校验存在 | 重放 | §3.2 |
| 合约用 `balanceOf` 当价格源 | 闪电贷操纵 | §4.1 |
| `addLiquidity` 的 `minAmount` 可传 0 | 单边注入抽干池子 | §4.2 |

## 1. 数值型

### 1.1 三连试

```text
负数    → -1、-100、-999999
零      → 0、0.0、""、null
超大    → 2^31-1、2^32-1、2^63-1、999999999999
小数    → 0.0001、0.999999
科学计数 → 1e10
```

判据是**服务端有没有 `min`/`max` 校验**。只有前端 `maxlength` 的不算校验。

### 1.2 整数溢出的位宽判据

| 场景 | 位宽 | 绕过值 |
|---|---|---|
| C/Go 的 `uint32` | 32 位 | `2^32 - N`（N 是要付的金额） |
| Java 的 `int` | 32 位有符号 | `2^31 - 1` 再加就变负 |
| PHP 的 `int` | 平台相关（64 位系统是 64 位） | 需 `2^63` |
| Solidity < 0.8.0 | 无检查 | 直接溢出 |
| Solidity ≥ 0.8.0 | 有检查 | 只能从**业务逻辑**造 |

**关键判据**：Solidity 0.8.0 之后编译器自动加溢出检查，溢出类题必须从**公式本身**找（比如先乘后除导致精度损失，或比例计算顺序）。

### 1.3 精度与舍入

```text
先除后乘  → 精度丢失，可反复刷
向上/向下取整 → 充值少、提现多
toFixed 截断 → 0.999 变 0.99
```

判据是**运算顺序**。有除法的地方就有精度问题。

## 2. 时序型

### 2.1 TOCTOU 的两个位置

```text
文件系统：check 路径 → 用路径（中间可换符号链接）
数据库：  SELECT 判断 → UPDATE 写入（中间可插一条）
```

判据是**「判断」与「使用」是两次独立操作**。一次 SQL 搞定的（`UPDATE ... WHERE balance >= 100`）没有这个洞。

### 2.2 并发窗口的三种打法

```text
1. HTTP/2 单包多请求（<100μs 派发间隔）
2. HTTP/1.1 末字节同步（1–5ms）
3. 多线程 + 网关限流绕过
```

判据是**服务端是「读-改-写」还是「原子更新」**。前者可打，后者不行。

**关键**：Nagle 算法生效的前提是 `TCP_NODELAY` **关闭**。开了 `TCP_NODELAY` 就必须用 `writev()` 聚写，`-c 1` 不等于同步。

### 2.3 注册/验证竞态

```text
场景：注册时先查用户名是否存在，再插入
打法：同一用户名并发注册，两个都通过检查
结果：两条同名记录，登录时取第一条 → 可能拿到别人的权限
```

判据是**唯一约束只在应用层做，数据库没加 `UNIQUE`**。加了 `UNIQUE` 的话，第二次插入会报重复键，与隔离级别无关。

## 3. 状态型

### 3.1 状态机跳步

```text
正常：created → paid → shipped → done
跳步：直接调 /done 接口，看是否校验前置状态
回退：已 done 的订单再调 /cancel，看是否退款
```

判据是**每个状态转换接口是否校验「当前状态」**。只校验「目标状态」的可跳步。

### 3.2 重放与幂等

```text
1. 同一个 sign 用两次
2. 同一个 coupon 用两次
3. 同一个 order_id 提交两次
4. 时间戳窗口内重放（nonce 未校验）
```

判据是**服务端有没有「已使用」标记**。有标记但标记在事务外（先标记再处理）仍有并发窗口。

### 3.3 参数污染

```text
?id=1&id=2          → 后端取第一个还是最后一个？
{"a":1,"a":2}       → JSON 解析器取哪个？
a[]=1&a[]=2         → 数组 vs 标量
```

判据是**前端校验的与后端使用的是不是同一个值**。前端取第一个、后端取最后一个时，可绕过。

## 4. 智能合约（Web3）

### 4.1 价格操纵

```text
漏洞模式：价格 = balanceOf(pair) 或 getReserves()
攻击：闪电贷借大量 token → swap 压低/拉高储备 → 触发业务 → 归还
```

判据是**价格源是「即时余额」而不是「TWAP/预言机」**。用 Chainlink 或时间加权的不受此影响。

### 4.2 流动性比例凑单

这是 WP 里最高频的 DeFi 题型，判据是**`addLiquidity` 是否校验最小份额**：

```text
Uniswap V2 的 addLiquidity 按「当前储备比例」计算份额
如果合约里两种代币的比例恰好等于 pair 的比例
→ 一次性把全部余额按比例入池，攻击者拿走全部 LP
```

**核心判据**：`amountAMin`/`amountBMin` 传 0 时不检查滑点。任何 `addLiquidity` 调用点没传 min 就是洞。

打法：

```text
1. 先 swap 出中间代币（让合约内两种代币比例接近 pair 比例）
2. 再用中间代币换 pair 里的第二种代币
3. 调 addLiquidity，min 传 0
4. 拿走 LP，撤池
```

### 4.3 Solidity 特有判据

| 判据 | 说明 |
|---|---|
| `transfer` 返回值未检查（< 0.8.0） | 假充值：token 转账失败但余额已加 |
| `abi.encodePacked` 多动态类型 | 哈希碰撞（`encodePacked("a","bc") == encodePacked("ab","c")`） |
| `MerkleProof` 未校验 index | `proofs[i]` 错配 + `index[i]=i` 可绕 |
| `usedLeafs` mapping 缺失 | 空投可重放 |
| `tx.origin` 用于鉴权 | 钓鱼可绕 |
| `selfdestruct` 强制转账 | 可污染 `address(this).balance` |
| `delegatecall` 到可控地址 | 直接拿存储写权限 |

### 4.4 Move / Sui 的差异

```text
资源（resource）是 first-class 类型，不能复制、不能隐式丢弃
转账必须显式 transfer::public_transfer
没有 entry 的函数不能被外部直接调用，需 script 包装
```

判据是**函数有没有 `entry` 修饰**。没有的话必须写 `script` 块调用。

## 5. 纪律

- **数值题先三连（负/零/超大）**，再考虑溢出。多数题不需要真溢出。
- **溢出先判位宽**。`uint32` 和 `int64` 的绕过值完全不同，猜错等于没打。
- **Solidity ≥ 0.8.0 别想溢出**，从公式的运算顺序找。
- **竞态先判「是不是原子更新」**。`UPDATE ... WHERE` 一条搞定的打不了。
- **状态机先画图**，标出每个转换的校验点，再找没校验的那条边。
- **DeFi 题先找 `minAmount=0`**，这是最高频的洞，比价格操纵简单得多。
- **不要一上来就写攻击合约**，先用 Foundry 的 `forge test` 在本地复现状态，再上链。
