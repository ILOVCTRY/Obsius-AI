# 代理池可信度校验（防「蜜罐代理」误报）

> 适用条件：任何经代理池/公共代理做的 Web 可达性与接口验证。核心一句话——**先证代理是透明的，再信它返回的东西。**

## 坑：代理返回对任意主机一致的 canned 响应

公共代理池（含自动抓取的免费池）里混有**蜜罐/伪造代理**：它不真正转发流量，而是对**任何目标**都返回一段固定响应。典型表现：

- 请求 `http://example.com/`、`http://www.google.com/`、`http://www.baidu.com/`、以及你的目标，**响应体逐字节相同**（同 Content-Length、同 JSON）。
- 例（2026-10-15 实测）：代理 `124.163.236.54:7302` 对以上全部主机返回
  `{"code":"0x01900012","message":"check token fail"}`（`Content-Type: application/json`，`Content-Length: 51`）。
- `proxy_check_url` 这类「按目标探测」的工具会把它判为**唯一可用**代理（因为其它代理对该目标超时/404），极具误导性。

## 危害

直接把 canned 响应当成目标真实回包 → **凭空造出「未授权 API / token 校验 / 业务数据泄露」类误报**。红线「无证据不下结论」在这里的具体体现就是：证据来源本身不可信。

## 步骤：三步校验（每个代理用前必做）

1. **对照主机验证**：先经该代理请求一个**你确知内容的公共站点**（`http://example.com/`、`http://httpbin.org/headers`、`http://ipinfo.io/ip`）。
   - `httpbin.org/headers` 会回显你发去的头，能验证代理是否真在转发。
   - 若返回的是你目标的业务 JSON，而不是 example.com 的内容 → **该代理是蜜罐，弃用**。
2. **多代理 + 直连三方一致性**：同一路径，直连基线与 ≥2 个不同来源代理的状态码/体积/关键字段一致，方可定论（与 `sudy-webplus-站群.md` 的复核原则一致）。
3. **看是否「过于整齐」**：所有主机、所有路径都返回同一状态码与同一体积 → 高度可疑；真实源站不同路径体积通常不同（如 404 会随路径长度变化）。

## 已验证路径：正常代理的表现

- 真代理经 `example.com` 返回 Cloudflare 的 200（有 `cf-ray`、`server: cloudflare`）。
- 直连/真代理访问目标返回**源站特征头**（`Server: Apache/2.4.58 (Ubuntu)`、`nginx`、`Date`），而经拦截层返回的 404 可能**没有 Server/Date 头**——头差异本身也是判别线索。

## 与工具配合

- `mcp__fir-proxy__proxy_check_url`：能给出「哪些代理对该目标可达」，但**不校验代理真伪**——它返回的 `usable` 仍需按上面第 1 步复核。
- 代理频繁掉线（000/503）时轮换后**重新做对照校验**，不要复用上一次的信任结论。
