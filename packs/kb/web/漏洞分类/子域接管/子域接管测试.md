# 子域接管全手法（按记录类型分）

**用法**：枚举子域后对每条记录做 §2 的四类判定（CNAME/NS/MX/A），命中指纹表（§3）再按 §4 认领。
**NS 接管危害远高于 CNAME**——CNAME 只控制一个子域，NS 控制整个 zone。

## 0. 判据速查

| 记录 | 悬空判据 | 危害 | 节 |
|---|---|---|---|
| CNAME → 外部服务 | 目标返回 `NoSuchBucket`/`No such app` 等指纹 | 单个子域内容被控 | §3、§4 |
| NS → 外部域名 | NS 域名过期/可注册 | **整个 zone 全控**（含 MX/TXT/签发证书） | §5 |
| MX → 停用邮件服务 | 租户可被重新认领 | 收密码重置邮件、冒充发信 | §6 |
| A → 弹性 IP | IP 未分配 | 抢注 IP 提供服务 | §8 |
| `*.target.com` 通配 | 任意随机子域都能解析 | 攻击面成倍放大 | §7 |

## 1. 原理

1. `sub.target.com` 有 DNS 记录指向外部服务；
2. 该外部资源**已被删除**（S3 桶删了、Heroku app 删了）；
3. 攻击者能在服务商那边**注册同名资源**；
4. 于是 `sub.target.com` 的内容由攻击者控制。

**危害链**：读父域 cookie（若 cookie 域设成 `.target.com`）、截 OAuth token、用可信域名钓鱼、绕过 CSP（子域在白名单里）。

## 2. 检测流程

### 2.1 CNAME 枚举

```
1. 收集子域（amass / subfinder / assetfinder / crt.sh / SecurityTrails）
2. 逐条解析：dig CNAME sub.target.com +short
3. CNAME 目标返回 NXDOMAIN 或服务商错误页 → 可疑
4. 拿响应去比对 §3 的指纹表
```

### 2.2 关键信号

| 信号 | 含义 |
|---|---|
| CNAME → `xxx.s3.amazonaws.com` + 404 `NoSuchBucket` | 桶已删，可抢注 |
| CNAME → `xxx.herokuapp.com` + `No such app` | app 已删 |
| CNAME → `xxx.github.io` + 404 `There isn't a GitHub Pages site here` | Pages 未认领 |
| CNAME 目标域本身 NXDOMAIN | 目标域过期或从未存在 |
| CNAME → 服务商但返回 200 停放页 | **不确定**，需实测能否认领 |

### 2.3 工具

| 工具 | 用途 |
|---|---|
| `subjack` | 自动化 CNAME 接管检测 |
| `nuclei -t takeovers/` | 接管检测模板 |
| `can-i-take-over-xyz`（GitHub 仓库） | 各服务是否可接管的参考表 |
| `dnsreaper` | 多服务商扫描 |
| `subzy` | 快速验证 |

## 3. 服务商指纹表

| 服务商 | CNAME 形态 | 指纹（HTTP 响应） | 可认领 |
|---|---|---|---|
| **AWS S3** | `*.s3.amazonaws.com` / `*.s3-website-*.amazonaws.com` | `NoSuchBucket`（404） | 是，建同名桶 |
| **GitHub Pages** | `*.github.io` | `There isn't a GitHub Pages site here`（404） | 是，建仓库开 Pages |
| **Heroku** | `*.herokuapp.com` / `*.herokudns.com` | `No such app` | 是，建同名 app |
| **Azure** | `*.azurewebsites.net` / `*.cloudapp.azure.com` / `*.trafficmanager.net` | 各种默认页、NXDOMAIN | 是，注册同名资源 |
| **Shopify** | `*.myshopify.com` | `Sorry, this shop is currently unavailable` | 是，建店加自定义域 |
| **Fastly** | CNAME 到 Fastly 边缘 | `Fastly error: unknown domain` | 是，在 Fastly 服务里加域 |
| **Pantheon** | `*.pantheonsite.io` | `404 Site Not Found` + Pantheon 品牌 | 是 |
| **Tumblr** | `*.tumblr.com`（自定义域 CNAME） | `There's nothing here` | 是 |
| **WordPress.com** | CNAME 到 `*.wordpress.com` | `Do you want to register` | 是 |
| **Zendesk** | `*.zendesk.com` | `Help Center Closed` | 是，建同名子域 |
| **Unbounce** | `*.unbouncepages.com` | `The requested URL was not found` | 是 |

## 4. 认领步骤

### 4.1 AWS S3

```bash
# 1. 确认
curl -s http://sub.target.com        # → NoSuchBucket

# 2. 从 CNAME 取桶名（sub.target.com.s3.amazonaws.com → 桶名 = sub.target.com）
# 3. 建桶（桶名全局唯一，注意区域要匹配）
aws s3 mb s3://sub.target.com --region <region>

# 4. 上传证明文件
# 5. 开静态网站托管
```

### 4.2 GitHub Pages

```
1. 确认：curl -s https://sub.target.com → "There isn't a GitHub Pages site here"
2. 建仓库（名字随意）
3. 加 CNAME 文件，内容为 sub.target.com
4. 仓库设置里开 GitHub Pages
5. 等 DNS 生效（GitHub 会校验 CNAME 匹配）
```

### 4.3 Heroku

```
1. 确认：curl -s http://sub.target.com → "No such app"
2. heroku create <CNAME 里的 app 名>
3. heroku domains:add sub.target.com
4. 部署证明页
```

## 5. NS 接管（高危）

**判据**：`dig NS target.com +short` 返回的 NS 域名已过期或可注册。

```
target.com NS → ns1.expireddomain.com
                 ↓
攻击者注册 expireddomain.com
                 ↓
target.com 的**全部** DNS 归攻击者
（A / MX / TXT 全部）
```

### 检测

```
1. dig NS target.com +short
2. 逐个 whois ns1.example.com → 域名是否过期/可注册
3. dig A ns1.example.com → NXDOMAIN/SERVFAIL？
4. 子委派 zone 也要查：dig NS sub.target.com
```

### 危害

- 整域接管：任意内容、截邮件、用 DNS-01 挑战签发 TLS 证书；
- 改 SPF/DKIM/DMARC → 以 `target.com` 身份发**通过认证**的邮件。

## 6. MX 接管（截邮件）

**判据**：MX 指向已停用的邮件服务。

```
target.com MX → mail.deadservice.com（服务已下线）
```

能认领 `mail.deadservice.com` 或对应邮件租户时：收密码重置邮件、截敏感通信、重置那些走邮箱认证的账号。

**常见场景**：Google Workspace / Microsoft 365 租户过期，MX 仍指向 Google/Microsoft，攻击者新建租户认领该域。

## 7. 通配 DNS 风险

`*.target.com` 有指向可认领服务的通配 CNAME 时，**每个**未定义的子域都可被接管。

```
dig A random1234567.target.com
```

能解析 → 存在通配。

## 8. 判定决策树

```
发现 sub.target.com
├── 有 CNAME → 外部服务？
│   ├── 响应命中 §3 指纹？
│   │   ├── 是 → 尝试认领（§4）
│   │   │   ├── 成功 → 接管确认
│   │   │   └── 被拒（名字保留/区域锁定）→ 记录，试变体
│   │   └── 否 → 服务活着，无接管
│   └── CNAME 目标 NXDOMAIN？
│       ├── 目标是可注册域名 → 注册 → 完全控制
│       └── 目标是活跃服务商的子域 → 查该服务商认领流程
├── 有 NS → 外部 NS？
│   ├── NS 域名过期/可注册 → 注册 → **整个 zone 接管**
│   └── NS 域名活跃 → 无
├── 有 MX → 外部邮件服务？
│   ├── 已停用/可认领 → 认领租户 → **截邮件**
│   └── 活跃 → 无
└── 有 A → IP？
    ├── 属于弹性云（AWS EIP / Azure / GCP）？
    │   ├── IP 未分配 → 抢占 IP → 提供服务
    │   └── 已分配给别的客户 → 无
    └── 独享服务器 → 无

接管后的影响评估：
├── 父域共享 cookie？ → 会话劫持
├── CSP 白名单含 *.target.com？ → 借子域打 XSS
├── OAuth redirect_uri 允许 sub.target.com？ → 盗 token
└── 能给 sub.target.com 签 TLS 证书？ → 完整 MITM
```

## 9. 容易被误判的点

1. **CNAME 不等于可接管**。CNAME 到 S3 但返回 403（桶存在且私有）**不是**漏洞，只有 `NoSuchBucket`（404）才是。
2. **S3 区域要对**。桶名全局唯一，但网站端点分区域，从 CNAME 里读出区域去匹配。
3. **GitHub Pages 加了域名验证**。组织已验证的域名别人抢不走，先确认目标有没有开。
4. **有些服务商要特定配置**。CloudFront 这类不是「认领域名」就行，要匹配 distribution 配置。
5. **二阶接管**：`sub.target.com CNAME → other.target.com CNAME → dead-service.com`，必须把整条链走完。
6. **SPF 子域接管**：SPF 里有 `include:sub.target.com` 且你接管了 `sub.target.com`，就能改它的 SPF TXT 记录授权自己的邮件服务器 → 以 `target.com` 身份发伪造邮件。

## 10. 纪律

- **先确认资源是否真悬空**。403 和 404 是两件事，报错就白跑。
- **NS/MX 接管的危害要单独说清**。这两个不是「一个子域被控」，是整域或邮件通道被控，评级完全不同。
- **认领只做到证明控制即可**，上传一个静态证明页，别在上面放任何业务内容。
- **不单独报 CORS**。子域接管后若顺带能打 CORS，写进主业务漏洞里，别拆成独立条目。
