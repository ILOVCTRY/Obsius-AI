# 容器能力边界与替代手法

沙箱逃逸是「怎么打破隔离」，本页是反过来的：**在隔离里面做题，哪些路是被堵死的、堵死后走哪条**。
逃逸手法见 [[binary/漏洞利用/沙箱逃逸与受限环境.md|沙箱逃逸与受限环境]]、seccomp 绕过见
[[binary/漏洞利用/Pwn 进阶手法.md|Pwn 进阶]] §1；加密卷头的解析见
[[forensics/磁盘与内存/磁盘数据恢复与容器链提取.md|磁盘数据恢复与容器链提取]] §6。

## 0. 先分清两种失败：没装 vs 不允许（EPERM 判据）

同一个「命令失败」，处置方向相反。判断错方向会浪费掉大部分时间：

| 现象 | 属于 | 处置 |
|---|---|---|
| `command not found` / `ImportError` / `No module named` | **没装** | 装包（但见 §5：运行期装不了） |
| `EPERM` / `Permission denied` / `Operation not permitted` / `-ENOTSUP` / `Cannot initialize` | **不允许** | **装包无效**，必须换手法 |
| `Required kernel crypto interface not available` | **不允许**（缺内核接口，不是缺包） | 换纯用户态实现 |
| `dm_mod` / `/dev/mapper` 不存在 | **不允许** | 放弃挂载，只做用户态解析 |

**一句话判据：报错里出现 `Permission` / `EPERM` / `not permitted` / 模块名（`algif_*`、`dm_crypt`），
就不是装包能解决的。** 反过来，`not found` 类才该想到装包。

## 1. 五条硬边界：ASLR setarch、AF_ALG cryptsetup、mount dm_mod、core dump、ptrace

这些是**内核/seccomp/capability 层的封禁**，镜像里装任何包都绕不过。遇到就立刻换路，不要重试。

### 1.1 ASLR：默认参数下 `EPERM`，当前平台已放开

`setarch -R` / `personality(ADDR_NO_RANDOMIZE)` 在 **Docker 默认**参数下返回 `EPERM`。

**关键细节（容易误判）**：Docker 默认 seccomp profile 对 `personality` 是**按参数值过滤**，
不是整体封禁。实测 `0x0`、`0x8`、`0x20000`、`0x20008` 全部放行，
**只有 `0x40000`（`ADDR_NO_RANDOMIZE`）被拒**——而 `setarch -R` 传的恰好就是
`current | 0x40000 = 0x40000`。

```bash
setarch -R ./pwn            # 默认参数下失败；本平台已放开，正常可用
cat /proc/sys/kernel/randomize_va_space
```

平台侧已通过 `--security-opt seccomp=unconfined` 放开。**这不是拆沙箱**：实测在
该参数下 `CapEff` 仍为 `0`、`mount` 仍被拒、对其他进程 `ptrace` 仍 `EPERM`、
`/proc/sys` 仍只读——隔离来自 `--cap-drop ALL`，不是 seccomp。

**若哪天又关不掉（换环境/被收紧），不要卡在这**：改用**泄漏 + 低 12 位反查**。
栈上返回地址的低 3 位十六进制在同一二进制里是固定的（页内偏移），用它去
`/opt/libc-db/`（见 §4）匹配版本，或反推 canary 等敏感值。
关 ASLR 只是省事，不是必要条件。

### 1.2 `AF_ALG` 被封 → `cryptsetup tcryptDump` 结构性不可用

```bash
python3 -c "import socket; socket.socket(socket.AF_ALG, socket.SOCK_SEQPACKET, 0)"
# PermissionError: [Errno 1] Operation not permitted
```

`cryptsetup tcryptDump --veracrypt` 依赖 `algif_skcipher`，因此必然报
`Required kernel crypto interface not available. Ensure you have algif_skcipher kernel module loaded.`
**装 `cryptsetup` 不能修**，加载模块也没有 `CAP_SYS_MODULE`。

`cryptsetup` 的能力边界要分清（装了确实有用，但只有半边）：

| 子命令 | 可用 | 原因 |
|---|---|---|
| `luksFormat` / `luksDump` | ✅ | 纯用户态解析 LUKS 头 |
| `luksOpen` / `tcryptOpen` | ❌ | 需 `dm_mod` + `/dev/mapper` |
| `tcryptDump --veracrypt` | ❌ | 需 `AF_ALG` |

→ 加密卷题走**纯 Python 头解析**（`pycryptodome` 已装），具体下标与 XTS 写法见
[[forensics/磁盘与内存/磁盘数据恢复与容器链提取.md|磁盘数据恢复]] §6。

### 1.3 挂不了 loop / 设备映射

实测在新启动参数下（`--cap-drop ALL` + `seccomp=unconfined`）：

```
mount -t tmpfs none /mnt   → 失败（CapEff=0）
losetup -f                 → losetup: cannot find an unused loop device: No such device
ls /dev/mapper             → No such file or directory
```

所以所有镜像题都必须走**用户态解析**：`fls`/`icat`（TSK）、`debugfs`、
自己按文件系统结构读。**不要写需要 `mount` 的解题脚本**——在容器里它永远跑不通。

### 1.4 改不了内核参数

`/proc/sys/*` 只读（实测 `Read-only file system`）。
`core_pattern` **例外**：默认值是**相对路径 `core`**，落进程 cwd，
所以 `ulimit -c unlimited` 就够，不需要写 `/proc/sys`。平台已加 `--ulimit core=-1`。

```bash
cd /path/to/target          # core 落在 cwd，所以先 cd 过去
ulimit -c unlimited
./crash                     # 产出 ./core.<pid>
```

### 1.5 对其他进程 `ptrace` 被拒

不能 attach 已在运行的进程。实测（新参数下仍如此）：

```python
# ptrace(PTRACE_ATTACH=16, pid=1) -> -1  errno=1  Operation not permitted
```

调试只能**自己启动**目标：`gdb ./pwn`、`gdb --args ./pwn`。
要多进程调试用 `gdbserver` 由自己拉起，不要 attach。

## 2. 装包能修的：pyinstxtractor-ng、decompyle3、cryptsetup-bin

这一档才是「容器缺工具」，但**必须在构建期装**（见 §5）：

| 缺什么 | 装什么 | 判据 |
|---|---|---|
| PyInstaller 解包 | `pyinstxtractor-ng` | `command -v pyinstxtractor-ng` |
| pyc 反编译 | `decompyle3` | `pip3 show decompyle3 \| grep -qx 'Name: decompyle3'` |
| VeraCrypt 头（半） | `cryptsetup-bin` | 只有 `luksDump` 可用，见 §1.2 |

**包名坑**：PyPI 上是 **`pyinstxtractor-ng`**，`pyinstxtractor` 是 **404**（不存在）。
写错名字会得到 `No matching distribution found`，看起来像网络问题，其实是名字错。

**版本坑**：镜像里只有 Python 3.11，题给 3.8 的 pyc 时不要找第二套解释器
（bookworm 没有 3.8），用 `decompyle3` 跨版本反编译即可。

**smoke 探针坑**（写自检脚本时会踩，会造成假绿/假红）：
- `cmd | head -n 1` 的退出码取的是 `head` 的 → 命令不存在也返回 0（**假绿**）
- 执行器给每条命令追加 `</dev/null` → `<<< "pw"` herestring 被顶掉，
  表现为恒 FAIL 且 detail 为空（**假红**）
- `decompyle3 --version` 会刷 click 的 `UserWarning`，输出脏且判不了 → 用 `pip3 show` 判断

## 3. 库自身怪癖：from pwn import * 覆盖同名变量（pwntools 命名空间遮蔽）、pwn.version、MODE_XTS、hashcat

### 3.1 pwntools 命名空间遮蔽

`from pwn import *` 会把 `process`、`connect`、`remote`、`args`、`log`、`context` 等
注入当前命名空间，**和同名的本地变量/函数冲突**。

**实测症状**（不是固定的报错文案，取决于你把那个名字覆盖成了什么）：

```python
from pwn import *
process = subprocess.Popen([...])     # 或 process = './pwn'
process('./pwn')
# TypeError: 'Popen' object is not callable
# 或       'str' object is not callable      ← 实测这行
```

**判据是「`X object is not callable` 而 X 是你自己赋的类型」**，不必记具体文案。
同样会撞的名字还有 `log`（覆盖后 `log.info()` 失效）、`args`、`context`。

**修法（按优先级）**：
```python
from pwn import context, remote, pwnlib, ELF, flat   # 只导入需要的，别用 *
# 或者给自己的变量改名：my_process / p_ / s_ / proc
# 或者用完整路径：pwnlib.tubes.process.process(...)
```

### 3.2 版本号：`pwn.version` 与 `pwnlib.__version__` 都在

实测 pwntools **4.15.0** 里 `pwn.version`、`pwnlib.version`、`pwnlib.__version__`
**三者都是字符串** `'4.15.0'`，互相相等。所以「`pwn.version` 不存在」
「`pwnlib.version` 是子模块」这类旧说法**都是错的**，不要照抄。

```python
import pwn, pwnlib
pwn.version                  # '4.15.0'   (str)
pwnlib.version               # '4.15.0'   (str)
pwnlib.__version__           # '4.15.0'   (str)
```

**唯一稳妥的写法是 `pwnlib.__version__`**：`pwn.version` 在更早版本里确实曾缺失/形态不同，
而 `__version__` 是 Python 包的通行约定，跨版本最稳。取版本号不要靠猜，直接打印三个看。

### 3.3 `pycryptodome` 没有 `AES.MODE_XTS`

```python
from Crypto.Cipher import AES
hasattr(AES, "MODE_XTS")        # False（实测镜像内 pycryptodome 3.17）
AES.new(k, AES.MODE_XTS)        # AttributeError: module 'Crypto.Cipher.AES' has no attribute 'MODE_XTS'
```
必须手写 XTS（AES-ECB + GF(2^128) tweak 乘 0x87），或用 `cryptography` 的 `modes.XTS`
（实测镜像内 cryptography 46.x，`modes.XTS` 可用）。
**注意 `cryptography` 的 `modes.XTS` 把整个入参当一个 data unit**，不会按 512B 自动推进
扇区号——多扇区必须自己切分。

### 3.4 hashcat 没有 VeraCrypt 常规容器模式

实测镜像内 hashcat **v6.2.6**：`-h` 里 51 行 `veracrypt` 全部标 **Full-Disk Encryption (FDE)**
（`13711`–`13743`、`29411`–`29413` 等），**没有任何 non-FDE 模式**。

```bash
hashcat -h | grep -i veracrypt | grep -v -i FDE | grep -E '^ +[0-9]+'   # 实测无输出
```

识别到是**常规文件容器**（不是整盘加密）就别在 hashcat 上耗时间：
`--veracrypt-keyfiles` / `--veracrypt-pim-*` 那些是 FDE 模式的参数，不解决容器题。
改用纯 Python 头解析 + 少量候选口令（500k 迭代**容器内约 0.8 s/次**，几十个候选够用），或用 2john 类工具提取哈希。
注意别拿宿主机的 0.3 s 排预算——容器里慢一倍多。

## 4. libc 版本反查要走 /opt/libc-db（不是环境缺失）

`/opt/libc-db/` 里有几十个版本的 libc（实测 26 个）。**问题不是没有，是模型不知道有。**
拿到泄漏地址后用低 12 位反查：

```bash
ls /opt/libc-db/                                    # 先看有哪些版本
# 用泄漏地址的低 3 位十六进制在该目录下匹配
```

## 5. 为什么运行期 pip install 一定失败（无 PyPI 出网）

运行期的容器**没有外网到 PyPI**（实测 `curl pypi.org` 返回 `000`；apt / github 通）。
新工具只能在**构建期**装：

```dockerfile
RUN pip3 install --break-system-packages --no-cache-dir pyinstxtractor-ng decompyle3
```

构建时通过 `--proxy http://host.docker.internal:7890` 走宿主代理，但代理**只以
`--build-arg` 传入，不写进 ENV**，所以运行期仍然装不了。

**推论**：解题过程中发现缺工具，正确的反应是**换手法**，不是 `pip install`。
这一点要在思路里就排除掉，否则会反复撞同一堵墙。

## 6. 判据速查表

| 现象 | 判断 | 动作 |
|---|---|---|
| `EPERM` / `Permission denied` / 模块名 | 内核/接口不允许 | 换纯用户态手法 |
| `algif_skcipher` 缺失 | `AF_ALG` 被封 | 纯 Python 解头，见 §1.2 |
| `dm_mod` / `/dev/mapper` 缺失 | 不能挂载 | `fls`/`icat`/`debugfs`/自解析 |
| `setarch -R` 失败 | ASLR 关不掉 | 泄漏 + 低 12 位反查 |
| `ptrace: Operation not permitted` | 不能 attach | 自己启动目标（`gdb ./pwn`） |
| `command not found` / `ImportError` | 真缺工具 | 构建期装，运行期换手法 |
| `pip install` 卡住/超时 | 运行期无 PyPI | 不要试，换手法 |
| `TypeError: 'module' object is not callable` | pwntools 名字被自己覆盖 | 只导入需要的符号 |
