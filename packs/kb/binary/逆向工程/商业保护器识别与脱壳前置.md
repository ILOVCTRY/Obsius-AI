# 商业保护器识别与脱壳前置

静态工具与异构格式选择见 [[binary/逆向工程/静态工具链与异构格式.md|静态工具链]] §9；反调试分类与绕过见 [[binary/逆向工程/反分析分类学与绕过.md|反分析]]；去虚拟化/去混淆工具见 [[binary/逆向工程/高级工具与去混淆.md|高级工具]]。

## 判据速查

| 现象                                        | 首选手法                   | 去哪节 |
| ----------------------------------------- | ---------------------- | --- |
| 多个区段 SizeOfRawData=0，另有一个随机名巨节熵 ≥7.9      | 掏空式商业保护器，先定类，别急着反编译    | §1  |
| 每个导入 DLL 只有 1 个 API，且多为冷门 API             | 诱饵导入表                  | §2  |
| IAT 表项步长 ≠ 指针宽度，或 IAT 指向高熵节内部             | IAT 混淆，自动搜索会读错步长       | §3  |
| TLS 目录 AddressOfCallBacks 指向高熵节           | TLS 回调反调试，先于入口点执行      | §4  |
| 入口点开头是 movabs 随机常量 + pushf + 偏移 ±1 字节的条件跳 | 变异引擎存根，反线性反汇编          | §5  |
| 有签名但 Authenticode 摘要不在证书里                 | 签名移植，不能拿签名做归因          | §6  |
| 导出表是 Go/cgo 符号但没有 Go buildinfo            | 本体是 Go，壳只抹了符号          | §7  |
| 已判定为掏空式保护器                                | dump 内存 → 修 IAT → 过反调试 | §8  |
| 要报出具体产品名                                  | 特征族投票，别用节名             | §9  |
| 高熵节里搜不到任何压缩流魔数                            | 加密而非压缩，别在静态解压上耗轮次      | §10 |

## 1. 掏空式区段表的判据

**判据**：区段表里出现若干「`PointerToRawData=0` 且 `SizeOfRawData=0`」的区段，而它们的 `VirtualAddress` 连续递增、名字是 `.text`/`.data`/`.rdata`/`.pdata` 这类原程序标准名——说明原映像的节表结构还在，内容已被整体搬走。同时有 1～2 个名字长度 4～8 的随机字符串节承载全部实体数据，其熵 ≥7.9，且 `SizeOfImage` 远大于实体节大小（压缩比常在 2～5 倍）。

**动作**：
```python
import pefile
pe = pefile.PE(path)
for s in pe.sections:
    print(s.Name, hex(s.Misc_VirtualSize), hex(s.PointerToRawData), hex(s.SizeOfRawData),
          hex(s.Characteristics))
print("SizeOfImage", hex(pe.OPTIONAL_HEADER.SizeOfImage),
      "TS", hex(pe.FILE_HEADER.TimeDateStamp),
      "Chars", hex(pe.FILE_HEADER.Characteristics))
```
看四项：空节数量、实体节熵、`SizeOfImage`/文件大小之比、`TimeDateStamp` 是否为 0（被抹时间戳是常见附带现象）。

**不成立**：若所有区段都有实体数据、只有某个节熵高，那是加密数据段（配置/资源），走 [[binary/恶意样本/PE 与 .NET 样本分析.md|PE 样本分析]] §2；若原始区段还在、仅名字被改，是普通重命名壳（UPX 改头一类），走静态工具链 §9 的 UPX 路线。

## 2. 诱饵导入表的识别判据

**判据**：导入目录里每个 DLL 只导入 **1 个** API，且这些 API 多为冷门/与业务无关的（设备枚举、HID、智能卡、硬件 profile、版本查询、代码页查询一类），总 DLL 数与总 API 数都只有十几；同时另有一组 KERNEL32 真 API（`LoadLibraryA`/`GetProcAddress`/`LocalAlloc`/`ExitProcess`）。真 API 集中在运行期解析三件套是这类壳的共同点。

**动作**：
```python
for e in pe.DIRECTORY_ENTRY_IMPORT:
    print(e.dll.decode(), len(e.imports), [i.name for i in e.imports])
```
统计「一 DLL 一 API」的 DLL 占比；确认运行期解析三件套是否存在。这类导入表还常带业务语义（硬件指纹/许可绑定选型），可顺带用于推断软件用途。

**不成立**：若导入表完整、API 数量正常（几十上百个），只是稀疏或延迟加载，则无保护器，属精简链接程序。

---

## 3. IAT 混淆的判据与真实步长换算

**判据**：IAT 目录的表项按**非指针宽度**连续排列（x64 下是 4 字节步长、x86 下是 8 字节步长）；或 IAT 指向的 RVA 大量落在高熵节内部而不是 `.rdata`/`.idata`；或 `Size` 与「导入项数 × 指针宽度」不符。

**动作**：
```python
dd = pe.OPTIONAL_HEADER.DATA_DIRECTORY[12]        # IAT
iptr = 8 if pe.OPTIONAL_HEADER.Magic == 0x20b else 4
print(hex(dd.VirtualAddress), hex(dd.Size), "step?", dd.Size / iptr, dd.Size / (iptr // 2))
```
哪个除法的结果接近导入项总数、且为整数，那个就是真实步长。dump 后重建 IAT 时要按这个步长手工修正，不要盲信自动搜索。

**不成立**：IAT 落在 `.rdata`/`.idata` 内且步长等于指针宽度，IAT 正常，dump 后可直接 Autosearch。

---

## 4. TLS 回调落点的判据

**判据**：TLS 目录存在且 `AddressOfCallBacks` 非空，回调地址落在**实体高熵节**内（保护器自己的区段），而不是原 `.tls`/`.CRT` 节。回调早于入口点执行，因此反调试/反 dump 能在 `main` 之前就把进程杀掉。

**动作**：
```python
tls = pe.DIRECTORY_ENTRY_TLS.struct
rva = tls.AddressOfCallBacks - pe.OPTIONAL_HEADER.ImageBase
print(hex(rva), hex(pe.get_offset_from_rva(rva)))
```
把回调数组逐个解出后映射到文件偏移，取前 32 字节；商业保护器的回调常与入口点属于**同一变异存根家族**（见 §5）。

**不成立**：回调为空，或落在 `.tls`/`.CRT` 且字节是正常 CRT 初始化代码（保存/恢复寄存器 + 调 `_initterm` 一类），则只有标准 TLS 初始化，按 §5 继续判。

---

## 5. 变异引擎存根的识别判据

**判据**：入口点或 TLS 回调的头 20 条指令呈固定形状——`push 寄存器` / `movabs 寄存器, 高熵随机 8 字节` / `push 通用寄存器` / `pushf` / 对寄存器取反或求补 / **条件跳转偏移为 -1 或 +1 字节**；块内散布 `f5`/`f8`/`f9`（cmc/clc/stc）这类对结果无影响的标志位指令；线性反汇编会吐出一堆 `(bad)`/`outsb`/`lret`/`fild` 的荒谬指令。

**动作**：
```python
import pefile
pe = pefile.PE(path)
off = pe.get_offset_from_rva(pe.OPTIONAL_HEADER.AddressOfEntryPoint)
print(hex(off))
```
```bash
dd if=sample of=ep.bin bs=1 skip=$OFF count=64 2>/dev/null
objdump -D -b binary -m i386:x86-64 --start-address=0 --stop-address=64 ep.bin
```
判据组合是「movabs 立即数为高熵随机值」+「条件跳转偏移 ±1」：正常编译器产物不会同时出现这两者。别对这些字节做线性反汇编后就认为看懂了。

**不成立**：入口点是标准 CRT 序言（`sub rsp, imm` / 保存非易失寄存器 / 调 `__security_init_cookie` / 直接调 `main`），说明无变异引擎，此时 §1 的空节结论要重新复核。

## 6. 签名移植的检测步骤

**判据**：证书目录项非空、签名结构是合法的 PKCS#7（能看到 CA 名、时间戳、CRL/OCSP URL），但按 Authenticode 算法算出的摘要**不在**证书的 SignedData 里。二次打包不会重新签名，常见做法是把别处搞到的签名表整体搬过来贴在自己文件尾。

**动作**：清零 `CheckSum` 字段与证书目录项本身（这两处参与计算），对「headers + 所有区段原始数据」求 SHA1/SHA256，再在证书 blob 里搜这两个摘要：
```python
import hashlib, pefile
pe = pefile.PE(path); raw = bytearray(open(path, 'rb').read())
cs = pe.OPTIONAL_HEADER.get_field_absolute_offset('CheckSum')
dd = pe.OPTIONAL_HEADER.get_field_absolute_offset('DataDirectory')
raw[cs:cs+4] = b'\0' * 4
raw[dd + 4*8 : dd + 4*8 + 8] = b'\0' * 8          # 证书目录项是第 4 项
co, csz = pe.OPTIONAL_HEADER.DATA_DIRECTORY[4].VirtualAddress, pe.OPTIONAL_HEADER.DATA_DIRECTORY[4].Size
body, blob = bytes(raw[:co]), bytes(raw[co:co+csz])
print(hashlib.sha1(body).digest() in blob, hashlib.sha256(body).digest() in blob)
```
注意证书目录项的 `VirtualAddress` 是**文件偏移**而不是 RVA，别做 RVA 换算。

**不成立**：摘要命中，签名有效。此时也不能反推发布者诚信——有效签名只说明「文件自签名以来未被改动」，不说明样本无害。

## 7. 本体语言识别（符号被抹后的适用条件）

**判据**：Go 程序的 `\xff Go buildinf:`、`go1.x`、`runtime.`、`goroutine` 全部搜不到，但导出表或残留字符串里有 `_cgo_dummy_export`、`*Trampoline`（go-sqlite3 一族）、`cgo_panic__<包名>_<hash>` 这类名字。cgo 的 panic 符号把**包名直接编进符号名**，是保护器最容易漏掉的指纹。

**动作**：
```bash
python3 -c "import pefile;pe=pefile.PE('s');print([x.name for x in pe.DIRECTORY_ENTRY_EXPORT.symbols])"
strings -a sample | grep -E '_cgo_|cgo_panic|Trampoline'
```
包名往往直接给出业务划分（磁盘/许可/网络/UI 等），可用于先建功能树再决定深析顺序。

**不成立**：导出表为空且无任何 cgo 痕迹。此时不要断言「不是 Go」——保护器可能连导出表一起清了；应 dump 后对映像跑 GoReSym 再判。

## 8. 脱壳前置四步与常见坑

**判据**：已按 §1 判定为掏空式保护器 —— 静态无路，必须动态。

**动作**（顺序不能反）：
1. **反调试层**：x64dbg + ScyllaHide（按 §9 的归因选预设）或 TitanHide。先开 TLS 回调断点（Options → Events → TLS Callbacks），否则回调里的反调试在入口点前就生效。
2. **到 OEP**：对「高熵节 → 另一段代码」的边界下断，或对目标节整段下内存写断点观察解密完成时刻。
3. **dump 内存而不是 dump 文件**：原文件里没有解包后的代码，`SizeOfRawData=0` 的区段在文件里是空的。
4. **修 IAT**：按 §3 算出的真实步长手工修正，别盲信 Autosearch；同时核对导出表与重定位表。
5. dump 后的映像按普通程序分析；若是 Go 本体，用 GoReSym 恢复函数表与符号，再走 §7 的包名线索分模块。

**不成立**：若 dump 出的映像仍高熵、OEP 又落回同一变异存根，说明存在二次解包或多层保护，重复 2～3 步即可；若反调试点多到补不完，改走模拟执行（Qiling/unicorn）从解密完成点把内存拖出来——模拟环境天然没有调试器痕迹。

## 9. 产品归因的适用条件与特征族投票

**判据**：现代商业保护器会把标志性节名（`.themida`/`.winlice`/`.vmp0`/`.vmp1`）清成随机串，**节名已不可用**。改用特征族投票：

| 特征组合 | 归因 |
|---|---|
| 掏空式区段表 + 一 DLL 一 API 诱饵 + TLS 回调存根 + 4 字符随机节名 | Oreans 系（Themida / WinLicense，同引擎） |
| 原始导入表基本保留 + 随机节名 + 大量 ROM 化资源 | Enigma Protector |
| `.vmp0`/`.vmp1` 节 + 可见的 VM handler 分派循环 | VMProtect（见 [[binary/逆向工程/高级工具与去混淆.md\|高级工具]] §1） |

**动作**：优先跑本地指纹库（Detect-It-Easy / PEiD 签名）而不是肉眼比对；没有签名库时用上表组合投票，并在结论里**标注归因置信度**，不要写成确定产品名。

**不成立**：特征族互相矛盾（例如掏空式区段表但导入表完整），说明可能是自研壳或安装包封装器（NSIS/Inno 一类），改按静态工具链 §9 的自定义壳路线手工定位 OEP，并先排除安装包：查 `MZ`/`PE` 嵌套数量与压缩流魔数。

## 10. 静态解压的适用条件（什么时候该停手）

**判据**：对高熵节头部尝试常见容器魔数（raw deflate、zlib 两种头、gzip、bzip2、xz、LZMA-alone）全部失败，且重复周期检测没有任何高于随机基线的周期（相邻等长块字节相同率 ≈1/256）。

**动作**：
```python
import zlib, lzma, re
blob = open('sample','rb').read()[BLOB_OFF: BLOB_END]
for wbits in (-15, 15, 47):
    try:
        out = zlib.decompressobj(wbits).decompress(blob[:0x20000]); print(wbits, len(out))
    except Exception as e:
        print(wbits, e)
print([hex(m.start()) for m in re.finditer(b'\x5d\x00\x00', blob[:0x100000])][:8])
```
```bash
binwalk -E sample        # 熵图：连续 8.0 说明加密
strings -a -n 6 sample | head
```
若 `strings` 在巨节里零命中、熵图平坦到 8.0，结论就是「加密而非压缩」，直接转 §8 动态路线。

**不成立**：任一容器格式能解出有意义数据（可打印率明显抬升、出现 PE/JS/脚本头），那是压缩层，逐层解到可读为止；此时静态路线可能比动态更省。

## 11. 纪律与已验证结论

- **掏空式区段表比熵更可靠**：熵只说明「有加密数据」，空节说明「原映像被搬走」——后者才直接指向上层保护器。
- **先定类，再定产品**：先确认是「压缩壳 / 虚拟化保护器 / 安装包封装器」三类中的哪一类，产品名最后再论；节名被清时任何节名判据都失效。
- **签名有效不等于可信，签名无效也不等于恶意**：只等于「不能拿签名做归因」。
- **dump 内存不是 dump 文件**，这是所有保护器的共同前提。
- **IAT 自动搜索会踩混淆步长的坑**：先按 §3 算出真实步长，再动手修。
- **反调试点补不完就上模拟执行**，别在补丁上耗轮次。
- **报的是「哪一层挡住了」**：掏空节表挡静态、TLS 回调挡调试器、IAT 混淆挡重建，三者解法不同，别混着补。
