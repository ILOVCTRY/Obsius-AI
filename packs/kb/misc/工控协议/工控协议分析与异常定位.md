# 工控协议分析与异常定位

工控题分两类：**藏数据型**（flag 就是某个字段的内容，读懂协议就能取）和**找异常型**（流量里有一条不该出现的指令，要报帧号）。前者考协议字段位置，后者考基线建模。先判类型再动手。

## 0. 判据速查

| 观察到的现象                                     | 结论                     | 去哪节  |
| ------------------------------------------ | ---------------------- | ---- |
| 功能码按固定序列循环（如 17,109,65,1,1,3,3,67）         | 周期轮询，异常 = 序列被打断        | §2.1 |
| 某功能码出现次数比基线多/少 1                           | 多出来那条就是注入指令            | §2.1 |
| 功能码全对，但某条 data 字段与其他同类不同                   | 异常在内容层，不在序列层           | §2.2 |
| `s7comm.header.error_class` / `errcod` 非 0 | 该帧是错误响应，异常源            | §3.1 |
| 流量里混着 `iec60870_104` / `mms` / `omron`     | 换协议找，别在 modbus 里死磕     | §3.2 |
| 字段值是乱码但长度整齐                                | 字节序问题，先按 2 字节交换        | §4.1 |
| 字段是 base64 且解码出图片                          | 直接提取，flag 在图里          | §4.2 |
| 十六进制串里出现 `ij` 这类非法 hex 字符                  | 字母做了位移，先小写字母减偏移再 hex 解 | §4.3 |

## 1. 先认协议

| 协议 | 端口/特征 | 用途 | Wireshark 过滤器 |
|---|---|---|---|
| Modbus/TCP | 502 | 读写线圈/寄存器 | `modbus` |
| S7comm | 102 | 西门子 PLC | `s7comm` |
| OMRON FINS | 9600/udp | 欧姆龙 PLC | `omron` |
| IEC 60870-5-104 | 2404 | 电力调度 | `iec60870_104` / `iec60870_asdu` |
| DNP3 | 20000 | 电力/水务 | `dnp3` |
| MMS | 102（ISO 栈上） | 制造报文规范 | `mms` |
| OPC UA | 4840 | 工业互联 | `opcua` |
| EtherNet/IP · CIP | 44818 | 罗克韦尔 | `enip` / `cip` |

**先看 `Statistics → Protocol Hierarchy`**，别默认是 modbus。题目里 modbus 占大头、flag 却在 `iec60870_104` 里是常见设置——协议分布一列就能避免这个坑。

## 2. Modbus：序列与内容两层异常

### 2.1 序列层：找被打断的周期

轮询型流量里，主站按固定顺序问同一批从站，功能码序列严格周期。异常判据：**把发送方的功能码按帧序导出，与基线序列逐位比对，第一个不匹配的位置就是异常点**。

```bash
tshark -r modbus.pcap -Y "modbus && ip.src==172.31.14.123" \
  -T fields -e frame.number -e modbus.func_code > data.txt
```

```python
base = ['17', '109', '65', '1', '1', '3', '3', '67']   # 从样本里数出来的周期
rows = [l.strip().split('\t') for l in open('data.txt') if l.strip()]
for idx, (fno, fc) in enumerate(rows):
    if fc != base[idx % len(base)]:
        print(fno, fc, 'expected', base[idx % len(base)])
```

注意两点：

1. **插入一条会让后续全部错位**。第一次比对会打出一长串「异常」，实际只有第一条是真的。定位到第一条后，把它当作插入项排除（或从基线里补上它），再跑一遍确认后面全部对齐——**只有第二遍干净，才能确认只插了一条**。
2. **改动（非插入）不会错位**，表现为孤立的一个点。所以「一长串 + 一个孤点」= 插了一条 + 改了一条，答案往往是两个帧号。

### 2.2 内容层：序列全对时看 data

功能码序列干净但仍有异常时，异常在字段值里。做法是**按功能码分组，取该组内出现频次最高的值当基线，找离群值**：

```bash
# 逐个功能码过滤掉「正常值」，剩下的就是离群
tshark -r x.pcap -Y 'modbus.func_code==17 && !(modbus.data==06:00:00)'
tshark -r x.pcap -Y 'modbus.func_code==1  && !(modbus.reference_num==0) && !(modbus.reference_num==1536)'
```

写线圈类（功能码 1/5/15）要同时看 `reference_num`（地址）和值：地址越界、值非 `0x00/0xFF` 都是可疑点。

### 2.3 功能码语义速查

| 码 | 名称 | 关键字段 |
|---|---|---|
| 1 / 2 | 读线圈 / 读离散输入 | `reference_num` 起始地址、`bit_count` |
| 3 / 4 | 读保持 / 输入寄存器 | 同上，值 2 字节 |
| 5 / 6 | 写单线圈 / 单寄存器 | 值 `0xFF00`=ON、`0x0000`=OFF |
| 15 / 16 | 写多线圈 / 多寄存器 | 后续 data 段 |
| 17 (0x11) | Report Slave ID | 返回设备标识，常藏字符串 |
| 43 (0x2B) | Read Device Identification | 同上，MEI 类型 |
| 65 (0x41) | 自定义/厂商扩展 | 值无标准语义，看 payload |

`0x11` 和 `0x2B` 是「读设备信息」类，最容易直接返回明文串——先试这两个再看别的。

## 3. 其他工控协议

### 3.1 S7comm：用错误码定位异常

西门子协议里 `Ack_Data` 帧带返回数据。正常响应 `error_class = 0x00`，异常帧非 0。判据：

```
s7comm.header.error_class != 0x00
s7comm.header.errcod   != 0x00
```

一条就够，比逐帧看 payload 快得多。`ROSCTR` 字段区分 Job(1)/Ack(2)/Ack_Data(3)/Userdata(7)，先按 ROSCTR 分组再看错误码，噪声更少。

### 3.2 换协议找：flag 常在「次要协议」里

工控赛题常把多种协议混在一个 pcap 里。modbus 里翻不到东西时，按 `Protocol Hierarchy` 的顺序换：`iec60870_104` → `mms` → `omron` → `dnp3`。这些协议的 payload 直接 `Follow TCP Stream` 就可能是明文。

### 3.3 OMRON FINS：命令码 + 字节交换

`omron.command == 0x0102` 是内存区读。返回的 payload 常常整段按 2 字节交换过，直接 hex 转字符是乱码，交换后才是文本。

### 3.4 MMS：文件名与句柄

MMS 的 `fileOpen` / `fileRead` / `fileDirectory` 操作在 `mms` 过滤器下可见。判据：**`fileOpen` 返回的 file identifier 要记住，后续 `fileRead` 用它取内容**。多次 open 就有多个标识符，逐个试 read。flag 可能是 base64 图片，也可能是纯文本。

Wireshark 解析不出响应时（长度字段没对上），**去掉过滤器看紧邻的下一个包**——工控流量里请求与响应常常背靠背，解析器失败不代表数据不在。

## 4. 编码与端序

### 4.1 字节序

工控设备大小端混用。整段数据是「像文本但字母乱」时，先按 2 字节交换：

```python
def swap2(h):
    return ''.join(h[i+2:i+4] + h[i:i+2] for i in range(0, len(h), 4))
```

判据：交换后出现可读英文或 base64 字符集（`A-Za-z0-9+/=`），就是对的。

### 4.2 base64 图片

payload 里出现 `iVBORw0KGgo`（PNG）或 `/9j/`（JPEG）开头，直接 base64 解码存盘。flag 常在图片上。

### 4.3 位移型混淆

十六进制串里出现 `g`–`z` 这类**非法 hex 字符**，说明字母被整体位移过。判据：`ij` 是 `ef` 加 4，`j` 是 `f` 加 4——所以偏移至少 4。从小偏移往上试，减完能 hex 解码且出可读文本就是对的。

```python
import string
buf = bytearray(b"666i5250356j4249")
for i in range(len(buf)):
    if buf[i] in string.ascii_lowercase.encode():
        buf[i] -= 4
print(bytes.fromhex(buf.decode()))   # → f66e5250356f4249 ... 再按需拼段
```

前后半段分开混淆时，解完要**尝试拼接**（前半 + 后半、逐 2 字节交错），不要只试直连。

## 5. 纪律

- 先看协议分布，别默认 modbus。
- 序列比对时区分「插入」与「改动」：插入会让后续全部错位，改动只留孤点。
- 解析器失败不等于数据不在，去掉过滤器看相邻包。
- 端序先试 2 字节交换，再考虑更复杂的重排。
- 只记「现象 → 判据 → 命令」，不记某题第几步。
