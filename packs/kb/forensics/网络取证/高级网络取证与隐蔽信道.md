# 高级网络取证与隐蔽信道

基础抓包、对象导出、TLS、TCP 重组和一般协议取证见 [[forensics/网络取证/网络流量取证与协议隐写.md|网络流量取证]]；USB/HID/Bluetooth 外设抓包见 [[forensics/隐写与信号/全方向 HID、蓝牙外设流量分析.md|外设抓包分析]]。

## 0. 判据速查

| 现象 | 重点检查 | 不要做什么 |
|---|---|---|
| 包内容几乎相同但间隔分两簇 | inter-packet interval、接口和包序 | 只看 payload |
| TCP flag 出现 FIN+SYN 等非法组合 | flag bit 到符号的映射 | 把异常 flag 当噪声丢掉 |
| DNS 名称随机且同域高频 | label、末字符、尾随字节、序列号 | 只抽完整 qname 后直接 base64 |
| ICMP payload/延迟有规律 | payload、长度、请求回复配对和 RTT 分布 | 不配对请求与响应 |
| “TLS”流导出后出现 `PK` | 原始 TCP stream、协议误标和并行流 | 信任 Wireshark 的协议标签 |
| 压缩比异常，解压会 OOM | 重复块和异常 seam | 直接完整解压 |
| SMB 后出现 `\pipe\lsarpc` | SID/RID 查询序列 | 把单次 SID 查询当成 RID cycling |
| NTP Key Identifier 随 RID 变化 | MS-SNTP 扩展和 HMAC 字段 | 把普通 NTP 当 timeroasting |
| PDF 有未引用对象 | xref、Pages/Kids、对象类型 | 只用渲染器查看页面 |
| 大量 UDP 小包、载荷高熵、码流固定 | RTP/G.711，先判 PT 值 | 当普通 UDP 直接看 hex |
| 抓包是 `.etl` | Windows `netsh trace`，先转 pcapng | 直接用 Wireshark 打开 |
| TLS 全是 `ChangeCipherSpec` 重复 | 加密信道（挖矿/隐蔽 C2） | 等 TLS 解密 |

## 1. 时序与字段信道

### 1.1 包间隔编码

若同一接口上的包内容、长度和方向几乎一致，但相邻间隔呈两簇，信息可能编码在时间而不是数据。大文件先用 tshark 做接口/协议统计，不要直接 `rdpcap` 把数百万包全部载入内存：

```bash
tshark -r capture.pcapng -q -z io,phs
tshark -r capture.pcapng -Y 'frame.interface_id == 2' \
  -T fields -e frame.time_epoch
```

解码前先画间隔直方图，确认阈值来自数据分布；保留接口、五元组、排序方式和是否存在丢包。若两个间隔映射为 0/1，再按明确的 MSB/LSB、前导位和字节边界尝试。首包没有前一个间隔，不能擅自补零，应用已知前缀或校验验证。

### 1.2 ICMP 延迟信道

把 echo request 与 reply 按 `ident`、`seq`、源/目的和方向配对，再计算 RTT。真实网络延迟通常是连续分布；隐蔽信道常出现 filler、短延迟和长延迟三个区域：

```python
from collections import defaultdict
from scapy.all import rdpcap, ICMP

req = {}
bits = []
for p in rdpcap("capture.pcap"):
    if ICMP not in p:
        continue
    key = (p[ICMP].id, p[ICMP].seq, p.src, p.dst)
    if p[ICMP].type == 8:
        req[key] = float(p.time)
    elif p[ICMP].type == 0:
        reverse = (p[ICMP].id, p[ICMP].seq, p.dst, p.src)
        if reverse not in req:
            continue
        dt = float(p.time) - req[reverse]
        if dt < 0.2:       # filler；阈值应由直方图确定
            continue
        bits.append("1" if dt > 1.0 else "0")
```

最后检查 bit 数是否完整、是否存在帧头/校验和。只按抓包顺序读取 reply 会被重传和多会话污染。

### 1.3 TCP flag 信道

TCP 的 FIN、SYN、RST、PSH、ACK、URG 共 6 个常用 flag，可组合成 0..63 并映射 Base64。异常组合、固定端口和包数与 Base64 对齐是强线索：

```python
from scapy.all import rdpcap, TCP
import base64
alphabet = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/"
vals = [p[TCP].flags & 0x3f for p in rdpcap("capture.pcap")
        if TCP in p and p[TCP].dport == 5748]
encoded = "".join(alphabet[v] for v in vals)
raw = base64.b64decode(encoded, validate=True)
```

确认 flag 位顺序、是否包含 ECE/CWR/NS，以及是否要按 stream/方向过滤；不要把 Scapy 的 flag 字符串顺序当数值顺序。

## 2. DNS 隐写与 dnscat2

### 2.1 查询名和尾随字节

大量查询指向同一异常域时，依次测试：完整 label 的 base32/hex、每个 label 的首/末字符、固定位置、查询顺序和 DNS ID。保留 qname 的原始 bytes，避免 Unicode 解码替换破坏数据。

某些题把 `0x30/0x31` 放在标准 Question 结构之后。不能只使用 Scapy 解析出的字段；须根据 DNS header、压缩指针、qname 终止符、QTYPE 和 QCLASS 计算预期长度，再检查 raw payload 尾部是否为合法 bit：

```python
raw = bytes(pkt[DNS])
qname_wire = bytes(pkt[DNSQR].qname)
expected = 12 + len(qname_wire) + 1 + 2 + 2
trailing = raw[expected:]
if trailing and all(b in (0x30, 0x31) for b in trailing):
    bits.extend(chr(b - 0x30) for b in trailing)
```

长度计算受 qname 表示方式影响，必须用实际 wire bytes 验证；拼成 bitstream 后检查 8 位分组、已知前缀与尾部 padding。

### 2.2 dnscat2 重组

dnscat2 查询常把十六进制或 base32 分片放进 label，并带会话、序列、确认信息。重组步骤：按域名和方向筛选 → 解码 label → 解析/去除协议头 → 按序号排序 → 去重重传 → 检查文件 magic 和长度。只比较相邻 chunk 不能覆盖乱序重传，应优先读取 header 中的 sequence。

不要把所有 DNS 请求拼在一起；多会话、请求/响应和控制帧需分开。重组后的 PNG、ZIP 等应验证 magic、文件长度和 checksum。

## 3. PCAP 多层、伪协议与并行数据

抓包中的协议标注可能是误导。对可疑 TCP stream 导出 raw bytes，先 `file`、magic、熵和长度，再决定是否真 TLS/ZIP。HTTP、mDNS TXT、DNS 或其他明文协议可能携带 XOR key；只在确认字段语义后提取。

并行流合并不能简单按“可打印优先”决定：可打印字节可能是随机噪声。应先检查两流长度、已知文件头、位置索引、校验和或题目给出的选择规则，再合并并重新验证整体结构：

```bash
tshark -r capture.pcap -q -z 'follow,tcp,raw,<stream>' > stream.bin
file stream.bin
xxd -l 32 stream.bin
```

XOR 处理保持 `bytes`，明确单字节/重复 key、方向、起始偏移和是否存在 nonce；解密结果应通过 magic 或语法解析，而不是仅凭可打印率。

## 4. SMB RID cycling 与 MS-SNTP timeroasting

### 4.1 RID cycling

SMB 认证后进入 `\pipe\lsarpc`，先取得域 SID，再对连续 RID 调用 `LsaLookupSids`，有效 RID 返回账户名、无效 RID 返回错误，这才构成 RID cycling。特征包括 Guest/null session、RPC bind、递增 RID、大量同类调用：

```bash
tshark -r capture.pcapng -Y 'smb2 || dcerpc' \
  -T fields -e frame.number -e ip.src -e dcerpc.cn_bind_to_str
```

单次 SID 查询、管理员正常枚举或不连续的几个 RID 不足以证明暴力枚举。

### 4.2 Timeroasting

MS-SNTP 是 AD 环境下的 NTP 扩展。攻击者将 machine-account RID 放入 Key Identifier，请求 DC 返回与机器账户 NTLM hash 相关的 HMAC-MD5 材料。先确认是 NTP 扩展响应而非普通时间同步，再按协议字段解析 salt、RID 和 16 字节 checksum；不要使用固定偏移处理未知版本/额外扩展。

提取后离线验证 hash 格式和 RID，再使用当前 Hashcat 文档确认模式。RID cycling 与 timeroasting 只是攻击链线索，必须把 SMB、RPC、NTP 的时间和源地址关联起来。

## 5. 压缩炸弹与边界分析

极端压缩比、`Content-Encoding: br` 或解压程序 OOM 时，不要完整展开。先复制原文件，计算相邻固定块的相似性，定位重复序列中的异常 seam；但 Brotli 是有状态流，任意中间块通常不能独立解压。正确做法是使用受限输出的 streaming decompressor，设置最大输出、超时和内存上限，从前一个可验证边界开始读取到 seam，或用格式解析器定位独立成员。

“异常块单独 `process()` 就能还原 flag”只有在块恰好是独立 Brotli stream 时才成立；不能把它当通用规则。记录输入/输出上限，防止取证过程本身触发资源耗尽。

## 6. ICMP payload、校验和与协议修复

ICMP Echo payload 常被忽略。检查非标准长度、非重复默认 payload、方向、序号和 byte rotation/XOR/base64 层；先按 request/reply 和 stream 分组，不要把多个探测会话拼接。

损坏包恢复可把协议校验当约束：

- IPv4 header checksum：只覆盖 IP header，16-bit one’s complement。
- TCP/UDP checksum：还包含 pseudo-header、长度和 payload。
- TCP sequence/ack、IP total length、协议 magic 可继续缩小候选。

单字节缺失可穷举并验证；多个字节不要只靠 checksum（碰撞空间大），还需同时满足序号、长度、应用层格式和上下文。修复结果另存，保留原始包与候选集合。

### 6.1 ICMP 三种字段级隐蔽通道

ICMP 没有 payload 也能藏东西——**包长、目的地址、TTL 都在传输中被保留，都能当比特流**。三种典型形态，各有独立的提取字段：

| 藏法 | 提取字段 | 判据 |
|---|---|---|
| **payload 长度当字节** | `data.len` | 全是 Echo，payload 内容无意义，但**长度在变**；前几个值 hex 后是文件头 |
| **目的 IP 末位当比特** | `ip.dst` | 源 IP 固定、目的 IP 只有最后一字节在两个值间跳 |
| **TTL / id 低位当比特** | `ip.ttl` / `icmp.ident` | 同一目标 TTL 不该变却在变 |

**长度当字节**——长度值本身就是数据，不要看 payload：

```bash
tshark -r secret.pcapng -T fields -e data.len -Y "icmp.type == 8" > lens.txt
```

```python
out = b''
for line in open('lens.txt'):
    line = line.strip()
    if not line: continue
    v = int(line)
    out += b'\x00' if v == 1 else bytes([v])   # 长度 1 是空行残留，补 0
open('out.bin','wb').write(out)
```

**目的 IP 末位当比特**——两个取值映射 0/1，八位拼一字节：

```bash
tshark -r secret.pcapng -T fields -e ip.dst -Y "icmp.type == 8" > ips.txt
```

```python
bits = ''
for line in open('ips.txt'):
    last = int(line.strip().split('.')[-1])
    bits += '0' if last == 38 else '1'      # 具体两个值看实际分布
data = bytes(int(bits[i:i+8], 2) for i in range(0, len(bits)//8*8, 8))
open('out.bin','wb').write(data)
```

**通用判据**：解出来的前 4 字节必须是已知文件头（`50 4b 03 04` ZIP / `89 50 4e 47` PNG / `52 61 72 21` RAR）。
认不出就是映射反了（0/1 对调）或位序反了（需 `bits[::-1]` 按字节倒），两种都试一遍。

**先看分布再写脚本**：`sort -u` 看该字段有几个不同取值。
2 个 → 比特通道；几十个且集中在 ASCII 可打印范围 → 字节通道；几百个 → 加密或压缩过。

## 7. 文件对象与加密会话

PDF 只渲染 `/Pages` 树可达的页面；检查 xref、对象类型、`/Kids` 和 `/Count`，对未引用 stream 做 hash、magic 和内容解析。不要直接手改 xref 覆盖原文件，优先用 qpdf/mutool 生成工作副本并重新校验。

PCAP 中若导出 PKCS#12，应先确认私钥属于目标会话、用途和口令保护状态；私钥导入 Wireshark 只有在协议使用兼容 RSA key exchange 时有效，ECDHE 仍需要 keylog。任何密钥材料都只在授权取证目录保存，并限制权限。

RADIUS 的 User-Password 依赖 shared secret 与 Request Authenticator；从捕获中提取 hash 后离线验证候选 secret，再在 Wireshark 中配置。不要把“能解析 Access-Request”误当作密码字段已解密。

RC4 流量若 shellcode 中存在 256 次 KSA 初始化，且连接初始固定长度突发后进入高熵流，可测试“前 N 字节为 key”的假设。重组 TCP 时先按 sequence 去重；RC4 key 长度、方向和是否丢失握手需由代码/协议证实，不要凭高熵猜 RC4。

### 7.1 ETL 与 TLS 解密的现实路径

**`.etl` 是 Windows 的 ETW 二进制 trace**，不是 pcap。Wireshark 打不开，`strings` 也拿不到明文包。

```bash
etl2pcapng capture.etl out.pcapng
tshark -r out.pcapng
```

判据：`file x.etl` 显示 `MS-DOS executable` 或 `data`，但文件头附近能 grep 到 `Microsoft-Windows-NDIS` / `ndiskd` 之类字符串 → ETW trace。

**TLS 解密只有两条正路**，别浪费时间猜密钥：

| 条件 | 做法 |
|---|---|
| 有 `SSLKEYLOGFILE` 日志 | `tshark -o tls.keylog_file:keys.log -r a.pcap` |
| 是 RSA key exchange（无 ECDHE） | 导入服务器私钥（`Edit→Preferences→Protocols→TLS`） |
| 两者都没有 | **解不了**，转去查握手元数据（SNI、证书、JA3） |

判据：ClientHello 的 `supported_groups` 里只有 `ecdh_x25519`/`secp256r1` → 走的是 ECDHE → **私钥无用**。
只有出现 `TLS_RSA_WITH_*` 套件时私钥才有效。

**TLS 元数据也能破题**：SNI 明文可见（除非 ESNI）、证书里常有内网域名、JA3 指纹能认工具（Cobalt Strike / Meterpreter / 挖矿）。

### 7.2 RTP / VoIP 音频还原

**判据**：大量 UDP 小包（100-200 字节）、载荷高熵、`rtp.seq` 连续递增 → RTP。
`PT`（payload type）决定编解码：

| PT | 编码 | 说明 |
|---|---|---|
| 0 | G.711 μ-law | 北美电话标准，8-bit 压缩 |
| 8 | G.711 A-law | 欧洲标准 |
| 9 | G.722 | 宽带 |
| 18 | G.729 | 低码率，需专用解码 |

```bash
# 一步抽全部流并解码成 wav（最省事）
tshark -r voip.pcap -Y rtp -T fields -e rtp.seq -e rtp.timestamp -e rtp.p_type -e rtp.payload

# 或用 rtpbreak / Wireshark 的 Telephony→RTP→Show All Streams→Analyze→Play Streams
```

**多流题的判据**：`rtp.ssrc` 有几个不同值就是几路通话。上千路时**必须脚本化**，
手点 GUI 不可能完成——先 `tshark` 导 `ssrc + payload` 到文件，再按 `ssrc` 分组逐路解码。

**RTMP 视频抽帧**（直播流题）：

```bash
tshark -r live.pcap -Y "rtmp && rtmp.chunk_type==0" -T fields -e rtmp.payload > video.hex
# 或按 tcp stream 抽出后
tcpflow -r live.pcap
rtmp2flv <stream> out.flv && ffmpeg -i out.flv -vf fps=1 frame_%04d.png
```

判据：`tcp.port==1935`、载荷前几字节是 `03`（RTMP chunk 头）→ RTMP。
`rtmp2flv` 只认完整流，缺头时先从 `connect`/`createStream` 的 chunk 拼回。

## 8. 工控协议取证

**判据**：流量里有 Modbus / S7comm / OPC UA / IEC104 / DNP3 / FINS。

| 协议 | 端口 | Wireshark 过滤器 | 关键字段 |
|---|---|---|---|
| Modbus TCP | 502 | `modbus` | `func_code`、`regval_uint16` |
| S7comm | 102 | `s7comm` | `header.errcod`、`param.func` |
| OPC UA | 4840 | `opcua` | `NodeId` |
| IEC 104 | 2404 | `iec60870_104` | `ioa`（信息体地址） |
| DNP3 | 20000 | `dnp3` | `al_objtype` |
| FINS | 9600 | `fins` | 魔数 `46494e53` |
| MQTT | 1883 | `mqtt` | `topic`、`msg` |

**功能码语义就是判据**——写操作出现在「不该写」的时间点就是攻击：

```text
Modbus func_code = 5   → 写单个线圈（开/关阀门）
Modbus func_code = 6   → 写单个寄存器
Modbus func_code = 8   → 诊断（常被忽视的隐蔽通道）
Modbus func_code = 16  → 写多个寄存器
S7comm errcod != 0x00  → 异常响应（可能是攻击探测）
```

**数据提取**：寄存器值拼起来常是文件头——

```bash
tshark -r a.pcap -Y modbus -T fields -e modbus.regval_uint16
```

判据是**寄存器值拼起来是不是文件头**。比如 `35152 = 0x8950`，正是 PNG 的前两字节。

## 9. 证据与纪律

所有高级信道都遵守同一流程：

1. 复制原始抓包并记录 hash、时间范围和过滤器。
2. 按接口、五元组、stream、方向和会话拆分。
3. 识别信号所在维度：内容、字段、顺序、时间或解析边界。
4. 用长度、序号、magic、校验或已知明文验证候选。
5. 保存中间层、参数、失败样本和资源限制。

不要将题名、异常协议标签、可打印率或单一工具输出当成结论。涉及凭据破解、密钥恢复或漏洞复现时，仅针对明确授权的题目资产和测试环境执行。
