# 通用隐写结构与容器分析

图像格式专属手法见 [[forensics/隐写与信号/图像格式隐写与载体修复.md|图像格式隐写与载体修复]]；FFT、SSTV、音频、视频、JPEG XL 等进阶手法见 [[forensics/隐写与信号/高级隐写：频域、音频与结构变换.md|图像隐写进阶]]；编码判定见 [[misc/编码解码/编码与二维码.md|编码与解码基础]]；DNS/网络隐蔽信道见 [[forensics/网络取证/高级网络取证与隐蔽信道.md|高级网络取证与隐蔽信道]]。

## 0. 判据速查

| 现象 | 优先检查 | 常见误区 |
|---|---|---|
| 文件能打开但尺寸异常 | 尾部追加、魔数被覆盖、多流容器 | 只按声明尺寸读取 |
| 图像正常但内容“少一块” | IHDR 宽高/CRC、chunk 顺序、帧数 | 只检查 magic 与 CRC |
| 文档有“看不见”的文字/图形 | 注释、链接、矢量矩形、压缩流、元数据 | 只跑 `strings` |
| 同源两份文件互相覆盖 | 交错、叠加、异或嵌套 | 先跑通用 LSB 工具 |
| 终端/矢量输出很大 | 转义序列、keyframe、微坐标 | 直接渲染后截图 |
| 图看起来全重复/可“对眼” | 自相关求重复宽度，做差 | 纯肉眼观察 |
| 文本全是奇怪汉字/「佛曰」 | 中文隐写三件套（佛曰/天书/阴阳怪气） | 当成乱码放弃，见 §5.1 |
| GIF 调色板有相邻极近的两个索引 | 索引当 bit，`gifsicle --change-color` | 只做帧间差分，见 §5.2 |
| zip 报 CRC 错误 / 打不开 | 伪加密标志位、Compression method | 直接删文件，见 §5.3 |
| 解出还是压缩包（多层） | 递归解，判文件头 | 手动逐层解，见 §5.3 |

## 1. 容器边界与格式修复

### 1.1 尾部追加与魔数覆盖

格式逻辑结束标记（如 PNG `IEND`）之后仍可附加数据；追加段的魔数也可能被改写成宿主格式签名以便伪装。定位结束标记后检查尾部，按候选 magic（ZIP `PK`、7z `37 7a bc af`、gzip `1f 8b`）识别并切分到工作副本。不要在原文件上直接改写。

### 1.2 PNG 尺寸与 chunk

- IHDR 宽高与可见内容不符：用 CRC 反推正确高度（CRC 匹配即为原始值）；若 CRC 也被改，先试提高高度再重算 CRC 并验证 IDAT 可完整解码。
- chunk 顺序非法：官方要求 IHDR 在前、IDAT 连续、IEND 结束；按类型重排时保留原 CRC，仅调整顺序。
- chunk 名大小写决定 critical/ancillary/private/safe；小写的关键 chunk 会被忽略。
- 多帧 PNG：检查 `acTL/fcTL/fdAT`，普通查看器只显示第一帧；用 APNG 工具导出全部帧后再逐帧分析。
- 自定义 chunk：非标准四字母类型通常被解析器忽略，却是理想的载荷容器；逐 chunk dump 并按长度切分。

### 1.3 多流容器

MP4/MKV 等可含多个视频/音频/字幕轨，播放器默认只显示第一条。先枚举全部流，再按 index 提取：

```bash
ffprobe -hide_banner file.mp4
ffmpeg -i file.mp4 -map 0:1 -c copy second.mp4
```

注意 `handler_name`、语言标签等元数据可能只是线索。隐藏轨可能使用少见编码，提取失败时先校验轨道参数与解码器可用性。

## 2. 结构元数据载体

### 2.1 PDF

把 PDF 当结构文件而不是文本：对象、流、注释、页面树和元数据都是可能载体。检查顺序建议：

1. `strings`/对象级扫描，找注释与隐藏文本片段。
2. 解压 FlateDecode 流后再搜索；压缩流里常藏 `strings` 看不到的内容。
3. 解包后检查注释、链接 `/Annots` 与 `/URI`（注意 `\{`、`\}` 等转义）、表单域和 OpenAction。
4. 用 pdfimages 抽取所有嵌入图像，另行做隐写分析；模糊/涂黑区域可用反卷积或移除覆盖物还原。
5. 内容流里的矢量图形可能是伪装的二维码：解析 `re` 等绘制算子，取几何中心重建成栅格再解码。
6. 元数据（Producer/Author/Keywords）与 `%%EOF` 之后的尾部都要看。
7. 图像 LSB 可能不在 bit0；逐通道逐位面检查后再判定。

### 2.2 SVG

动画 keyframe 的颜色交替可编码二进制（如两种填充色对应 0/1），间隔时长可再叠一层 Morse；先解析 `<animate>` 的 `keyTimes/values`，再按色值与时间双重解码。

SVG 的坐标精度可能承载微尺度图形：某些 `<g>` 的坐标聚集在极小范围，正常视口下不可见。检查小数位数异常的坐标，通过 viewBox/transform 放大到该区域后再渲染。

### 2.3 终端协议与转义序列

Kitty 图形协议把图像分块编码进 `ESC_G...;base64` 序列，头部带格式、压缩（如 zlib）、尺寸和后续块标志；按块拼接后再 base64/zlib 解码，按 `f=24` 等字段还原像素。ANSI 终端艺术可能在转义码之间插入不可见文本；剥离转义序列与特定字符集后可取回，注意区分“真隐藏字符”与正常排版字符。

### 2.4 表格与结构化数据

单元格数值的频次排序可能构成字节映射。先统计唯一值数量（接近 256 提示按字节处理），按频率排序得到值→序号映射，再替换并验证输出是否为可识别文件。频率相近或映射不唯一时不要硬解，需结合出现位置或 padding 规则。

## 3. 交错与多层数据

### 3.1 字节/行交错

两份文件按奇偶字节交错时，按步长切分即可还原；但识别标志常是切分后仍“有条纹”。此时再做一次扫描线级 deinterleave（奇偶行/列）。双层扩展名、目标文件重复 magic 都可作为线索。

### 3.2 嵌套与渐进层

嵌套 PNG 常通过自定义 chunk 逐层 XOR，key 可能是递增词或由上一层内容揭示；每层解密后重新走 chunk 解析。用已知频数字节（如 `FF`）跑异或分析，得到候选 key 后逐层验证。短重复 key XOR 会保留大尺度像素结构，即使未完全解密也可能出现可读图案——这只能作为存在性证据，仍需完整解密确认。

Angecryption 说明 AES-CBC 也可以构造出“加密后仍是合法文件”的特例：给定 key/IV 时可能从一个合法文件得到另一个合法文件。遇到两份结构相似的文件与密钥材料，可构造验证；不要把它当作通用“无损加密”假设。

## 4. 视觉与信号恢复

### 4.1 立体图与自动立体图

重复宽度是核心参数。对单行做自相关，取中心后第一个峰值作为移位量；再用图像与移位副本做差，重复背景相消后显现深度/文字。移位量不对时输出接近噪声，应扫描候选范围并比较可读性。

### 4.2 帧间差分

GIF/视频中的隐藏信息可能只在相邻帧差异中出现：逐帧导出后比较对应像素，把“是否变化”“变化量”“变化位置”三种假设分别尝试。压缩编码、帧尺寸不一致和调色板差异会造成伪差异，先统一帧格式再定义规则；结果按 Morse、ASCII 或文件 magic 复核。

### 4.3 反射/残缺二维码

球面反射、遮挡、低分辨率二维码可借助结构先验：先找 finder pattern 与尺寸推定版本，再反变换（镜像/去畸变/缩放）；模块不确定时用已知明文修正早期数据位，让 ECC 纠正剩余错误。手工转录只在工作副本进行，保留原始帧与每一步矩阵。

### 4.4 调色板帧编码

帧数异常多且为完全平方数时，可能是“每帧一像素”的调色板编码：每帧像素相同但 palette 不同，用调色板首项决定黑白后即可按 √n 拼出隐藏图。先验证帧数与尺寸关系，再检查调色板索引规则。

## 5. 边界像素与视觉编码

一像素边框的黑白可承载位流：沿固定方向（顺时针/逆时针）遍历边框，按亮度阈值取 bit。方向、起点和阈值都要先用已知样本或同步位确认。边框宽可能不是 1 像素；也可能是内嵌第二层图案而非纯黑白位。

## 5.1 中文隐写三件套：佛曰 / 天书 / 阴阳怪气

国内 misc 题的固定组合。判据：**文本全是看起来像某种「语言」的字，但不成句、无语法**。

| 名称 | 形态 | 解码 |
|---|---|---|
| 佛曰 | 「佛曰：XXX。佛又曰：XXX。」 | 在线 `keyfc` 佛曰加解密，或 `FoYue` 脚本 |
| 天书（Sealed-Book） | 一堆生僻字/CJK 组合 | `github.com/BlackCat184/Sealed-Book` |
| 阴阳怪气 | 「就这？就这？」「不会吧不会吧」 | 在线「阴阳怪气编码」，或按词表映射 |

三者常**串联**：阴阳怪气解出压缩包密码 → 解压得佛曰文本 → 佛曰解出天书 → 天书解出 Base58/Base45 串。判据是**每层解出的都是「另一种奇怪文本」而不是可读内容**时，继续按下一层解，不要以为解错了。

**纪律**：这三类都有在线工具，不要自己实现。但要注意**同一名称有多种变体实现**（佛曰有 v1/v2，天书有不同词表），解出乱码时先换实现而不是换算法。

## 5.2 逐帧调色与 GIF 处理

GIF 隐写的判据是「**颜色索引异常**」而非像素异常：调色板里存在两个几乎相同、只差 1 的索引值，说明被拿来当 bit 用了。

```bash
# 把索引 234 映射成黑、235 映射成白，隐藏图案立刻显现
gifsicle --change-color 234 "#000000" --change-color 235 "#ffffff" in.gif > out.gif
```

**判据**：`identify -verbose in.gif | grep -A20 Colormap` 里出现相邻且极接近的颜色对（如 `#010101` 与 `#020202`），就是这对索引承载信息。`--change-color` 一次只能改一个，多个索引要串联多次。

**多帧分离**：`convert in.gif -coalesce frames/%03d.png` 拆帧后，先看**帧间差分**（`compare -compose src`），再看每帧同位置的像素变化序列——「每帧一像素」的编码在差分图里是一条线。

## 5.3 压缩包：伪加密、CRC 与套娃

三件事按顺序查，别跳步：

**① 伪加密**：`zip` 的「加密」标志位在本地文件头（offset 6）和中央目录（offset 8）各有一份，两份不一致或值非 0 但实际无密码，就是伪加密。

```bash
# 中央目录的标志位：504b0102 后第 8 字节
# 本地文件头的标志位：504b0304 后第 6 字节
# 都改成 00 00 即可
```

**② CRC 校验失败**：`unzip` 报 CRC error 但能解出文件，说明数据被改过。两种处理：改 `Compression method`（`504b0304` 后第 8-9 字节）从 0（stored）改成 8（deflate）或反之；或直接用 `7z x -y` 忽略 CRC。

**③ 套娃**：解出一层又是压缩包。判据：**文件头是 `37 7A BC AF 27 1C`（7z）/ `504B`（zip）/ `52617221`（rar）**。脚本化递归：

```python
import subprocess, pathlib
p = pathlib.Path('start.zip')
for i in range(50):
    subprocess.run(['7z', 'x', '-y', f'-o{i}', str(p)], check=False)
    nxt = [x for x in pathlib.Path(f'{i}').rglob('*')
           if x.suffix.lower() in ('.zip', '.7z', '.rar', '.tar', '.gz')]
    if not nxt: break
    p = nxt[0]
```

**已知明文攻击（bkcrack）**：zip 用 ZipCrypto 加密且你能猜出明文片段（PNG 头 `89504e47...` 是最常见的）时，可以直接恢复密钥。

```bash
bkcrack -C challenge.zip -c challenge.png -x 0 89504e470d0a1a0a0000000d49484452
bkcrack -C challenge.zip -k <key1> <key2> <key3> -U decrypted.zip easy
```

判据：**加密方式是 ZipCrypto（不是 AES）**，且明文片段 ≥12 字节。12 字节是下限，片段越长越快。

**④ 文件名本身就是载荷**：解出来的文件名乱码、或文件名长度/后缀异常规整，说明**数据在文件名里**，不在内容里。

最常见的是 **GBK 文件名被按 CP437 解码**（Windows 打的包在 Linux 解开）：

```python
import zipfile
with zipfile.ZipFile('x.zip') as z:
    names = [n.encode('cp437').decode('gbk') for n in z.namelist()]
print(names)
```

反过来（Linux 打包、Windows 打开乱码）用 `n.encode('gbk').decode('cp437')`。判据：**乱码里全是西欧重音字符**（`í`、`ó`、`ú`、`ß`）就是 CP437/GBK 错配。

文件名**有规律地被切成等长段**（`用户1_xxxx的外卖`、`part01`、`a_b_c`）时，把每段按序拼起来再解码，通常得到 Base64 或十六进制。
配合题面提示替换字符（`-` ↔ `/`）后直接 `b64decode`。

**⑤ 缺头补头**：解出的数据长度对、但认不出格式，说明**头部几个字节被故意丢掉**。
用尾部反推：ZIP 结尾必有 `504b0506`（EOCD），PNG 结尾必有 `49454e44ae426082`。
由结尾推出应有的开头（ZIP → `504b0304`，PNG → `89504e47`），补齐后再解。
判据：**数据末尾能认出格式，开头认不出** → 补头；反之补尾。

## 6. 纪律

容器题优先看“文件比内容大多少”和“结构比渲染多什么”。任何提取都必须跨层验证：magic、长度、CRC、zlib 可解、图像可解码、文本可读。遇到多层嵌套时记录当前层使用的 key/chunk/偏移，避免重复或跳层。题面名称只提出假设，最终结论必须由字节级证据支撑。
