## 0. 按格式的必查顺序

格式决定了**同一方向该查哪些字段**——先认格式，再按上表过方向。

| 格式 | 必查（按顺序） |
|---|---|
| PNG | IHDR 宽高 → 全部 chunk 列表（tEXt/zTXt/iTXt 常藏文本）→ PLTE 调色板 → IDAT 块数/长度/CRC → IEND 之后有无数据 |
| JPG | EXIF 全段 → 尾部 FF D9 之后有无数据 → DCT 系数（需工具）→ 缩略图与主图不一致 |
| GIF | 帧数与帧间隔 → 全局/局部调色板 → NETSCAPE2.0 扩展块 → 每帧 LSB |
| BMP | 头部 4 个保留字段（`reserved1`/`reserved2`/`offbits` 高位）→ 像素数组后有无附加 → 调色板 → 位深异常 |
| WebP/AVIF | RIFF chunk 遍历 → EXIF/XMP chunk |

## 1. 元数据检查

**判据**：`exiftool` / `strings` 出现非工具生成的字段——`Comment`、`Author`、
`ImageDescription`、`XPComment` 里是可读文本或 Base64；或 `strings` 在文件头/尾
出现与图片内容无关的长串。

**动作**：
```bash
exiftool -a -u -g1 x.png        # -a 全字段（含重复 tag）、-u 未知 tag、-g1 按组
exiftool -b -ThumbnailImage x.jpg > thumb.jpg   # 缩略图单独导出（可能含未裁剪内容）
strings -n 6 x.png | head -50
identify -format "%c\n" x.gif   # GIF 每帧的 comment 扩展块
```
XMP 段常被忽略：`exiftool -xmp:all x.jpg`，内容是 XML，可直接搜 `<dc:description>`。
PNG 的 `tEXt/zTXt/iTXt` 也归这里——`exiftool` 会列，但要 `-u` 才看得到私有 tag。

**不成立**：所有字段都是相机/编辑器默认值（`Software` 只有 Photoshop、`DateTime`
连续无跳变），且 `strings` 无可读长串 → 元数据无载荷，转 §2 看附加数据。

## 2. 附加数据

**判据**：文件大小明显大于像素数据的理论体积；文件尾不在标准结束标记
（PNG 的 `IEND`、JPG 的 `FF D9`、GIF 的 `3B`）；`binwalk` 列出嵌入式条目。

**动作**：
```bash
binwalk -e file.png          # 分离尾部嵌入
foremost -i file.jpg -o out/ # 按魔数雕刻
# 手工定位：从结束标记之后 dump
xxd file.jpg | tail -20      # 看 FF D9 之后还有没有东西
```

**不成立**：`binwalk` 只报出 `Zlib compression`（那是 IDAT 本体）且文件尾就在结束标记处
→ 无附加数据，转 §3 看结构。

## 3. 文件结构异常

**判据**：文件头尾不符、chunk 长度越界、CRC 错、保留字段非零。
**动作**：按下表逐格式查；结构层不破坏像素，永远最先做。

**不成立**：头尾正确、所有 chunk/段长度自洽、CRC 全过、保留字段全 0 →
结构层干净，转 §4（改像素值）或 §13（工具产物），不要在结构层反复换工具。

### 3.1 PNG

#### 文件格式

对于一个 PNG 文件来说，其文件头总是由位固定的字节来描述的，剩余的部分由 3 个以上的 PNG 的数据块（Chunk）按照特定的顺序组成。

文件头 `89 50 4E 47 0D 0A 1A 0A` + 数据块 + 数据块 + 数据块……

#### 数据块CHUNk

PNG 定义了两种类型的数据块，一种是称为关键数据块（critical chunk），这是标准的数据块，另一种叫做辅助数据块（ancillary chunks），这是可选的数据块。关键数据块定义了 4 个标准数据块，每个 PNG 文件都必须包含它们，PNG 读写软件也都必须要支持这些数据块。

| 数据块符号 | 数据块名称             | 多数据块 | 可选否 | 位置限制           |
| :--------- | :--------------------- | :------- | :----- | :----------------- |
| IHDR       | 文件头数据块           | 否       | 否     | 第一块             |
| cHRM       | 基色和白色点数据块     | 否       | 是     | 在PLTE和IDAT之前   |
| gAMA       | 图像γ数据块            | 否       | 是     | 在PLTE和IDAT之前   |
| sBIT       | 样本有效位数据块       | 否       | 是     | 在PLTE和IDAT之前   |
| PLTE       | 调色板数据块           | 否       | 是     | 在IDAT之前         |
| bKGD       | 背景颜色数据块         | 否       | 是     | 在PLTE之后IDAT之前 |
| hIST       | 图像直方图数据块       | 否       | 是     | 在PLTE之后IDAT之前 |
| tRNS       | 图像透明数据块         | 否       | 是     | 在PLTE之后IDAT之前 |
| oFFs       | （专用公共数据块）     | 否       | 是     | 在IDAT之前         |
| pHYs       | 物理像素尺寸数据块     | 否       | 是     | 在IDAT之前         |
| sCAL       | （专用公共数据块）     | 否       | 是     | 在IDAT之前         |
| IDAT       | 图像数据块             | 是       | 否     | 与其他IDAT连续     |
| tIME       | 图像最后修改时间数据块 | 否       | 是     | 无限制             |
| tEXt       | 文本信息数据块         | 是       | 是     | 无限制             |
| zTXt       | 压缩文本数据块         | 是       | 是     | 无限制             |
| fRAc       | （专用公共数据块）     | 是       | 是     | 无限制             |
| gIFg       | （专用公共数据块）     | 是       | 是     | 无限制             |
| gIFt       | （专用公共数据块）     | 是       | 是     | 无限制             |
| gIFx       | （专用公共数据块）     | 是       | 是     | 无限制             |
| IEND       | 图像结束数据           | 否       | 否     | 最后一个数据块     |

对于每个数据块都有着统一的数据结构，每个数据块由 4 个部分组成

| 名称                            | 字节数   | 说明                                                 |
| :------------------------------ | :------- | :--------------------------------------------------- |
| Length（长度）                  | 4字节    | 指定数据块中数据域的长度，其长度不超过（231－1）字节 |
| Chunk Type Code（数据块类型码） | 4字节    | 数据块类型码由 ASCII 字母（A - Z 和 a - z）组成      |
| Chunk Data（数据块数据）        | 可变长度 | 存储按照 Chunk Type Code 指定的数据                  |
| CRC（循环冗余检测）             | 4字节    | 存储用来检测是否有错误的循环冗余码                   |

CRC（Cyclic Redundancy Check）域中的值是对 Chunk Type Code 域和 Chunk Data 域中的数据进行计算得到的。

#### IHDR

文件头数据块 IHDR（Header Chunk）：它包含有 PNG 文件中存储的图像数据的基本信息，由 13 字节组成，并要作为第一个数据块出现在 PNG 数据流中，而且一个 PNG 数据流中只能有一个文件头数据块

其中我们关注的是前8字节的内容

| 域的名称 | 字节数  | 说明                   |
| :------- | :------ | :--------------------- |
| Width    | 4 bytes | 图像宽度，以像素为单位 |
| Height   | 4 bytes | 图像高度，以像素为单位 |

我们经常会去更改一张图片的高度或者宽度使得一张图片显示不完整从而达到隐藏信息的目的。

![pngihdr](https://cdn.jsdelivr.net/gh/AMG4MATIC/PicGo/img/pngihdr.png)

**pngihdr**

这里可以发现在 Kali 中是打不开这张图片的，提示 `IHDR CRC error`，而 Windows 10 自带的图片查看器能够打开，就提醒了我们 IHDR 块被人为的篡改过了，从而尝试修改图片的高度或者宽度发现隐藏的字符串。

对于png的IHDR部分的隐写，有如下的工具和脚本，可以解决大部分问题

- PCRT(还不错)：自动修复图片
- pngcheck（配合脚本使用）：自动检查宽高与crc的匹配关系
- magnetos（强烈推荐）: 一个强大的自动化misc工具
  - https://github.com/restran/magnetos.git
- pngcalculate：根据CRC校验和计算图片的宽高

```python
import os
import binascii
import struct

misc = open("flag.png","rb").read()

for i in range(1024):
    data = misc[12:16] + struct.pack('>i',i)+ misc[20:29]
    crc32 = binascii.crc32(data) & 0xffffffff
    if crc32 == 0x932f8a6b:
        print(i)
```

#### PLTE

调色板数据块 PLTE（palette chunk）：它包含有与索引彩色图像（indexed-color image）相关的彩色变换数据，它仅与索引彩色图像有关，而且要放在图像数据块（image data
chunk）之前。真彩色的 PNG 数据流也可以有调色板数据块，目的是便于非真彩色显示程序用它来量化图像数据，从而显示该图像。

#### IDAT

图像数据块 IDAT（image data chunk）：它存储实际的数据，在数据流中可包含多个连续顺序的图像数据块。

- 储存图像像数数据
- 在数据流中可包含多个连续顺序的图像数据块
- 采用 LZ77 算法的派生算法进行压缩
- 可以用 zlib 解压缩

值得注意的是，IDAT 块只有当上一个块充满时，才会继续一个新的块。

用 `pngcheck` 去查看此 PNG 文件

```bash
λ .\pngcheck.exe -v sctf.png
File: sctf.png (1421461 bytes)
  chunk IHDR at offset 0x0000c, length 13
    1000 x 562 image, 32-bit RGB+alpha, non-interlaced
  chunk sRGB at offset 0x00025, length 1
    rendering intent = perceptual
  chunk gAMA at offset 0x00032, length 4: 0.45455
  chunk pHYs at offset 0x00042, length 9: 3780x3780 pixels/meter (96 dpi)
  chunk IDAT at offset 0x00057, length 65445
    zlib: deflated, 32K window, fast compression
  chunk IDAT at offset 0x10008, length 65524
...
  chunk IDAT at offset 0x150008, length 45027
  chunk IDAT at offset 0x15aff7, length 138
  chunk IEND at offset 0x15b08d, length 0
No errors detected in sctf.png (28 chunks, 36.8% compression).
```

可以看到，正常的块的 length 是在 65524 的时候就满了，而倒数第二个 IDAT 块长度是 45027，最后一个长度是 138，很明显最后一个 IDAT 块是有问题的，因为他本来应该并入到倒数第二个未满的块里.

利用 `python zlib` 解压多余 IDAT 块的内容，此时注意剔除 **长度、数据块类型及末尾的CRC校验值**。

```python
import zlib
import binascii
IDAT = "789...667".decode('hex')
result = binascii.hexlify(zlib.decompress(IDAT))
print result
```

#### IDAT 的两种隐写通道（判据 + 提取）

IDAT 段不止「多出来的块」一种藏法，**块数、长度、CRC 三个字段都是通道**：

| 现象 | 藏法 | 判据 |
|---|---|---|
| IDAT 块数上万（正常几十到几百） | **CRC 隐写**：每块 CRC 的最后一字节当数据 | 块数 > 10000 且 `pngcheck` 报 CRC 错或全对但数量离谱 |
| 单块 length 远小于 65524 却另起新块 | **长度隐写**：length 低位当数据 | 非末块 length 不满且后续还有 IDAT |
| 块结构完全正常、CRC 全对 | 数据在解压后的扫描线里（filter 字节 / 像素） | 解压后按 filter 重建再查像素 |

**CRC 隐写的提取脚本**（每块 CRC 取末字节，按出现顺序拼成文件头）：

```python
import re
data = open('alien.png','rb').read()
out = b''
pos = 0
while True:
    pos = data.find(b'IDAT', pos)
    if pos < 0: break
    # 'IDAT' 前 4 字节是 length；CRC 在数据之后，即下一个 chunk 头前 4 字节
    length = int.from_bytes(data[pos-4:pos], 'big')
    crc = data[pos+4+length: pos+8+length]
    out += bytes([crc[-1]])          # 只取最后一字节
    pos += 4
open('out.bin','wb').write(out)
```

**关键判据**：提取出来的首 4 字节必须能认出文件头（`50 4b 03 04` = ZIP、`52 61 72 21` = RAR、`89 50 4e 47` = PNG）。
认不出就说明取的位不对——换「CRC 首字节」或「length 低位」再试，别直接放弃。

**配套工具**：`tweakpng` 能图形化列出全部 chunk 并允许改 length/CRC，用来肉眼确认「哪个字段在动」比写脚本快。

#### IEND

图像结束数据 IEND（image trailer chunk）：它用来标记 PNG 文件或者数据流已经结束，并且必须要放在文件的尾部。

```none
00 00 00 00 49 45 4E 44 AE 42 60 82
```

IEND 数据块的长度总是 `00 00 00 00`，数据标识总是 IEND `49 45 4E 44`，因此，CRC 码也总是 `AE 42 60 82`。

这里是可以隐藏数据的，解法也很简单，使用工具、010editor等都可以获取。

#### 其余辅助数据块

- 背景颜色数据块 bKGD（background color）
- 基色和白色度数据块 cHRM（primary chromaticities and white point），所谓白色度是指当 `R＝G＝B＝最大值` 时在显示器上产生的白色度
- 图像 γ 数据块 gAMA（image gamma）
- 图像直方图数据块 hIST（image histogram）
- 物理像素尺寸数据块 pHYs（physical pixel dimensions）
- 样本有效位数据块 sBIT（significant bits）
- 文本信息数据块 tEXt（textual data）
- 图像最后修改时间数据块 tIME （image last-modification time）
- 图像透明数据块 tRNS （transparency）
- 压缩文本数据块 zTXt （compressed textual data）

### 3.2 BMP

**判据**：文件头 `42 4D`（`BM`）之后，紧跟的 4 个字段是 `reserved1`、`reserved2` 各 2 字节——
**规范要求全 0，看图软件一律忽略它们**。所以只要这两个字段非 0，就是人为写入的数据。

BMP 文件头（BITMAPFILEHEADER，14 字节）字段顺序：

```text
偏移 0  2 字节  bfType      固定 'BM' (42 4D)
偏移 2  4 字节  bfSize      文件总大小
偏移 6  2 字节  bfReserved1 规范为 0 —— 隐写通道
偏移 8  2 字节  bfReserved2 规范为 0 —— 隐写通道
偏移 10 4 字节  bfOffBits   像素数据起始偏移
```

**提取**：

```python
import struct
d = open('x.bmp','rb').read()
r1, r2 = struct.unpack('<HH', d[6:10])
print(hex(r1), hex(r2))            # 非 0 → 直接按字节读出来
raw = struct.pack('<HH', r1, r2)   # 拼回去看是不是文件头/坐标
```

**典型用法**：两个 2 字节字段刚好拼成 4 字节，够放一对坐标 `(x, y)` 或一个小整数。
看到「题目给了大图但要你定位某点」而图里没有其他线索时，优先查这里。
注意 `bfSize` 与 `bfOffBits` 也可能被改（前者算错说明文件被追加过数据）。

### 3.3 JPG

**判据**：文件头 `FF D8`、文件尾 `FF D9`。以下任一即为可疑：
① `FF D9` 之后还有数据（追加区）；② 段长字段与实际不符；③ 出现 APP0-APP15 之外的段，
或 APPn 段长度异常大；④ 主图与内嵌缩略图（APP1/EXIF 里的 `IFD1`）内容不一致；
⑤ 段与段之间有超过 2 个连续 `FF`（规范允许填充，但长串填充常被当作隐写区）。

**动作**：
```bash
# 1) 尾标记后有没有东西
python3 -c "d=open('x.jpg','rb').read(); i=d.rfind(b'\xff\xd9'); print(len(d), i+2, len(d)-i-2)"
# 2) 逐段列出标记码与长度，找越界段
python3 - <<'PY'
d=open('x.jpg','rb').read(); i=2
while i < len(d)-1:
    if d[i] != 0xFF: i += 1; continue
    m = d[i+1]; n = int.from_bytes(d[i+2:i+4],'big')
    print(f'FF{m:02X} @{i} len={n}')
    if m == 0xDA: break          # SOS 之后是熵编码数据，按标记重新扫描
    i += 2 + (n if n else 2)
PY
# 3) 工具侧：steghide 有无嵌入、stegdetect 判用了哪个工具
steghide info x.jpg
stegdetect x.jpg
```
追加区直接 `dd if=x.jpg bs=1 skip=<i+2> of=tail.bin` 再 `binwalk` / `file` 判类型。

**不成立**：`FF D9` 后无数据、段长全部自洽、`stegdetect` 全阴性 → 不是结构层，
转 §4 看 DCT 系数域（F5/JSteg/OutGuess 都改系数而非文件结构），或 §13 判工具。

#### 文件结构

- JPEG 是有损压缩格式，将像素信息用 JPEG 保存成文件再读取出来，其中某些像素值会有少许变化。在保存时有个质量参数可在 0 至 100 之间选择，参数越大图片就越保真，但图片的体积也就越大。一般情况下选择 70 或 80 就足够了
- JPEG 没有透明度信息

JPG 基本数据结构为两大类型：「段」和经过压缩编码的图像数据。

| 名 称   | 字节数 | 数据 | 说明                                        |
| :------ | :----- | :--- | :------------------------------------------ |
| 段 标识 | 1      | FF   | 每个新段的开始标识                          |
| 段类型  | 1      |      | 类型编码（称作标记码）                      |
| 段长 度 | 2      |      | 包括段内容和段长度本身,不包括段标识和段类型 |
| 段内容  | 2      |      | ≤65533字节                                  |

- 有些段没有长度描述也没有内容，只有段标识和段类型。文件头和文件尾均属于这种段。
- 段与段之间无论有多少 `FF` 都是合法的，这些 `FF` 称为「填充字节」，必须被忽略掉。

### 3.4 GIF

#### 文件结构

一个GIF文件的结构可分为

- 文件头（File Header）
  - GIF 文件署名（Signature）
  - 版本号（Version）
- GIF 数据流（GIF Data Stream）
  - 控制标识符
  - 图象块（Image Block）
  - 其他的一些扩展块
- 文件终结器（Trailer）

下表显示了一个 GIF 文件的组成结构：

![gif](https://cdn.jsdelivr.net/gh/AMG4MATIC/PicGo/img/gif.png)

**gif**

中间的那个大块可以被重复任意次

#### 文件头

GIF 署名（Signature）和版本号（Version）。GIF 署名用来确认一个文件是否是 GIF 格式的文件，这一部分由三个字符组成：`GIF`；文件版本号也是由三个字节组成，可以为 `87a` 或 `89a`。

#### 逻辑屏幕标识符（Logical Screen Descriptor）

Logical Screen Descriptor（逻辑屏幕描述符）紧跟在 header 后面。这个块告诉 decoder（解码器）图片需要占用的空间。它的大小固定为 7 个字节，以 canvas width（画布宽度）和 canvas height（画布高度）开始。

#### 全局颜色列表（Global Color Table）

GIF格式可以拥有global color table，或用于针对每个子图片集，提供local color table。每个color
table由一个RGB（就像通常我们见到的（255，0，0）红色 那种）列表组成。

#### 图像标识符（Image Descriptor）

一个 GIF 文件一般包含多个图片。之前的图片渲染模式一般是将多个图片绘制到一个大的（virtual
canvas）虚拟画布上，而现在一般将这些图片集用于实现动画。

每个 image 都以一个 image descriptor block（图像描述块）作为开头，这个块固定为 10 字节。

![imagesdescription](https://cdn.jsdelivr.net/gh/AMG4MATIC/PicGo/img/imagesdescription.png)

**imagesdescription**

#### 图像数据（Image Data）

终于到了图片数据实际存储的地方。Image Data是由一系列的输出编码（output codes）构成，它们告诉decoder（解码器）需要绘制在画布上的每个颜色信息。这些编码以字节码的形式组织在这个块中。

#### 文件终结器（Trailer）

该块为一个单字段块，用来指示该数据流的结束。取固定值0x3b.

更多参见 [gif 格式图片详细解析](https://www.jianshu.com/p/df52f1511cf8)

**不成立**：`pngcheck -v` / `jpeginfo -c` / `gifsicle --info` 全部无报错，
且各格式结束标记位置与文件长度一致 → 结构层无载荷，转 §4 看像素层。

## 4. LSB

**判据**：肉眼与正常渲染都无损，但**统计异常**——LSB 平面出现长程有序结构
（`zsteg` 有输出）、Alpha 通道出现 `0`/`255` 以外的值、或 RGB 全为偶数/全为奇数。
LSB 改的是 RGB 各分量最低 1 bit，人眼不可见，每像素最多携带 3 bit。

**动作**：
```bash
zsteg -a x.png                            # 全通道 × 全位平面 × 双向位序，先跑这个
zsteg x.png | grep -i "text\|flag\|PK"    # 只筛像结果的
```
GUI 用 Stegsolve：`Analyse → Data Extract` 可指定通道与位平面组合，
`Frame Browser` 逐帧看。**`zsteg` 全空不等于没有 LSB**——起始位/步长被改过时
它枚举不到，见下方「参数空间」。

**不成立**：`zsteg -a` 无输出、Alpha 全为 `0/255`、且 LSB 平面统计与随机噪声
不可区分（卡方检验无偏离）→ LSB 无载荷，转 §5 看调色板。

### LSB 参数空间：zsteg 覆盖不到的部分要自己爆

`zsteg -a` 只枚举**默认的几种组合**（通道顺序 × 位平面 × 字节序）。
题目一旦改动起始位或步长，`zsteg` 就全空——这时候不能判定「没有 LSB」，要自己爆参数。

**参数空间一共四维**：

| 维度 | 取值 | 说明 |
|---|---|---|
| 通道 | `R/G/B/A`、`RG/GB/BR`、`RGB/RGBA` | 有时只藏单通道（如 `G[1::3]`） |
| 起始位 | 0-7 | 从第几个像素开始取 |
| 步长 | 1..len/(L*8) | 每隔几个像素取一个 |
| 位序 | MSB / LSB | 每字节内先取高位还是低位 |

```python
from PIL import Image
import itertools

im = Image.open('x.png').convert('RGBA')
px = list(im.getdata())

def bits_of(channel_idx, start, step, msb):
    out = []
    for i in range(start, len(px), step):
        v = px[i][channel_idx]
        rng = range(7, -1, -1) if msb else range(8)
        out += [(v >> b) & 1 for b in rng]
    return out

def to_bytes(bits):
    return bytes(int(''.join(map(str, bits[i:i+8])), 2)
                 for i in range(0, len(bits)//8*8, 8))

for ch in range(4):
    for step in (1, 2, 3, 4):
        for msb in (True, False):
            for start in range(8):
                d = to_bytes(bits_of(ch, start, step, msb))
                # 判据：可打印率 > 90% 才值得看
                txt = d[:200].decode('latin-1')
                if sum(c.isprintable() for c in txt) / max(len(txt), 1) > 0.9:
                    print(ch, step, msb, start, txt[:80])
```

**`isprintable()` 过滤是减少假阳性的关键**。不加这个过滤，4 通道 × 4 步长 × 2 位序 × 8 起始 = 256 种组合里
会有几十种「碰巧像文本」，人工看不完。加上 90% 阈值后通常只剩 1-2 个候选。

**判据**：解出来的串**开头就是可见字符**（`flag`/`PK`/`{`/常见英文词）才继续；
从中间某个位置才开始像文本，说明起始位偏了，把 `start` 往后挪。

**Alpha 通道的特殊信号**：正常 PNG 的 Alpha 只有 `0`/`255`（全透明/全不透明）两种值。
若出现 `254`、`253` 这种「差一点点」的值，**几乎必然是 LSB 隐写**——正常渲染不会产生它。
`zsteg` 默认不查 Alpha，这是最容易漏的方向。

## 5. 调色板

**判据**：索引色图片（PNG-8 / GIF / BMP-8）的 `PLTE` 颜色数远小于像素实际用色，
或调色板顺序不符合任何正常量化算法（相邻色跳变极大）。

**动作**：
```python
# 调色板本身就是字节流：按序取出三字节一组
plte = data[plte_start:plte_start + plte_len]
payload = bytes(plte)          # 直接当载荷读
```

**不成立**：调色板是标准 web 安全色板或工具默认色板（颜色数 = 256 且分布均匀）
→ 调色板无载荷，转 §4 看 LSB。

## 6. 尺寸/宽高

**判据**：`IHDR` 的宽高与图片实际渲染尺寸不符；CRC 校验对不上（改过宽高但没重算 CRC）；
图片下半部分或右侧是纯色/噪声。

**动作**：
```bash
pngcheck -v file.png     # 报 CRC error 且位置在 IHDR → 宽高被改过
# 用 CRC 反解真实宽高（1-3 字节爆破，或已知高度反解宽度）
python3 -c "import zlib,struct; print(hex(zlib.crc32(b'IHDR'+struct.pack('>II',W,H)+b'\x00\x00\x00')))"
```

**不成立**：CRC 正确且尺寸与 `file` 命令一致 → 尺寸未被改动，转 §4。

## 7. 时间轴

**判据**：GIF/APNG/WebP 动画的**帧间隔（delay）**只有两三种离散取值，
而不是正常动画那种连续变化；或帧数与文件体积不匹配（帧很多但每帧几乎一样）。

**动作**：
```bash
# 每帧序号 + 延迟（%T = delay，单位 1/100 秒）
identify -format "%s %T\n" x.gif
# 先看取值分布：只有 2 个值 → 二值编码；值域 32-126 → 十进制 ASCII
identify -format "%T\n" x.gif | sort -n | uniq -c
```
延迟序列常见三种编码：①两值映射二值（`10`/`20` → `1`/`0`）；
②直接当十进制 ASCII；③`0` 与非 `0` 分别代表点与划（摩斯）。
提取时注意**首帧 delay 常是占位值**（如 `66`），要单独剔除。

**不成立**：所有帧 delay 相同，或 delay 分布连续无离散簇 → 时间轴无载荷，转 §8。

## 8. 空间轴

**判据**：单帧被切成网格、多帧各自只画一部分、或图片被拼图式打散
（每帧只有局部区域非透明/非背景色）。

**动作**：
```bash
# 逐帧分离（GIF → 多个 PNG）
convert x.gif frame-%03d.png
# 或用 ffmpeg（对 webp/apng 更稳）
ffmpeg -i x.gif -vsync 0 frame-%03d.png
```
分离后按「每帧非背景区域的坐标」求并集：各帧互补覆盖整图就是逐帧补全型，
取每帧不透明像素叠加即可还原；若是网格切片，按切片尺寸与序号重建索引图。

**不成立**：每帧都是完整画面（全图都有像素），只是内容渐变 → 不是空间轴拆分，
转 §7 看时间轴或 §4 看 LSB。

## 9. 视觉隐写

**判据**：肉眼可见但"不像原图"——局部噪点、色偏、轻微旋转/错位、某区域对比度异常。
这类通常**不需要工具**就能看出来，容易被忽略。

**动作**：
```bash
# 通道分离 + 对比度拉伸
convert file.png -channel R -separate r.png
convert file.png -modulate 100,100,300 boost.png   # 极端调色
# 逐通道看差异
python3 -c "from PIL import Image,ImageChops; ..."
```

**不成立**：各通道差异 < 1 LSB 且拉伸后无可见结构 → 无视觉隐写。

## 10. 盲水印

**判据**：空域完全正常（无噪点、LSB 干净），但题面暗示"水印"或给了同源样本
（原图 / 同一张图的多个副本）。频域嵌入在空域看不出。

**动作**：
```bash
# 频域盲水印需要两张图：原图 + 带水印图
python3 bwm.py decode --original orig.png --image wm.png --result out.png
# 只有一张时：DCT/DFT 系数直方图异常（某频段被抬高）
```

**不成立**：没有原图且频域直方图平滑（无异常峰）→ 盲水印不可解，转 §11。
**注意**：单张图做不了盲水印比对，这是最常见的误判点。

## 11. 条形码

**判据**：图中有一条或多条由不等宽黑白竖条组成的区域，且条码承载的信息
比肉眼可读的内容多（例如条码下印着数字，但条码实际编码的是另一串）。

**动作**：
```bash
zbarimg -q x.png                 # 一次扫全部条码，输出 SYMBOL:TEXT
# 扫不出：先二值化 + 放大，条码对分辨率很敏感
convert x.png -colorspace Gray -threshold 50% -resize 300% big.png && zbarimg -q big.png
```
制式判定：EAN-13 = 13 位纯数字（末位校验）；Code-39 = 大写字母数字加 `- . $ / + %`；
Code-128 = 全 ASCII。扫出的制式与内容长度对不上，说明条宽被改过，
按实际条纹宽度手工重新解码。

**不成立**：`zbarimg` 与二值化放大后都无输出 → 不是条码，转 §11.1 看二维码。

## 11.1 二维码

**判据**：图中有三个角上的回字形定位图案（finder pattern）；或二维码残缺/
被遮挡/被切块但残留部分定位图案。

**动作**：
```bash
zbarimg -q x.png                 # 完整码直接扫
convert x.png -negate inv.png && zbarimg -q inv.png   # 被反色/低对比时
```
三类常见修复：①缺定位角 → 按标准模板贴回三个 finder pattern；
②码被切成多块 → 按 §8 的空间轴拼回；③码上覆盖噪点 → 中值滤波后再二值化。
QR 有纠错等级可容错，**L 级约容忍 7% 模块损坏**，先试直接扫再修。

**不成立**：三处定位图案都完整但反色/滤波后仍扫不出 → 内容可能不是文本
（二进制/加密串），扫出原始字节后转 `编码与解码` 或 `密码学手法`。

## 12. 像素值转化

**判据**：文件里是**文本形式的像素值**（`255,255,255,...` 或 `#RRGGBB` 列表），
或图片像素值全部落在极窄值域（如全是 16 的倍数），说明像素本身是数据容器。

**动作**：
```python
from PIL import Image
vals = [int(x) for x in open('rgb.txt').read().replace('\n', ',').split(',') if x.strip()]
w = h = int((len(vals) / 3) ** 0.5)      # 先试正方形
im = Image.new('RGB', (w, h))
im.putdata([tuple(vals[i:i+3]) for i in range(0, len(vals), 3)])
im.save('out.png')
```
宽度未知时按 `len/3` 的因子逐个试（正方形优先，其次常见比例），
**渲出来的图能看出结构（文字/二维码/图形）就是对的宽高**。

**不成立**：所有因子下渲出的都是噪声 → 不是像素值直接成像，转 §12.1。

## 12.1 图片转像素

**判据**：图能正常显示，但**每个像素的多通道合起来才是一条记录**
——例如 RGB 全是某个基数的倍数（低位恒定），而 Alpha/某单通道的值域
恰好是可打印 ASCII 或 brainfuck 字符集。

**动作**：
```python
from PIL import Image
px = list(Image.open('x.png').convert('RGBA').getdata())
px.sort(key=lambda p: (p[0] << 16) + (p[1] << 8) + p[2])   # RGB 当排序键
print(''.join(chr(p[3]) for p in px))                        # A 当载荷
```
常见三种：①**排序键在 RGB、载荷在 A**；②**低位恒定**：RGB 全是 `0x?0`，
说明低 4 位被清零腾出来放数据；③**通道当索引**：R 是数据、G/B 是下一个坐标。

**不成立**：按任一通道排序后拼出的串可打印率都低于 30%，且各通道值域连续
→ 像素只是图像内容，转 §13 判工具产物。

## 13. 隐写工具产物

**判据**：上面 12 个方向全部不成立，但图片仍可疑——JPEG 的 DCT 系数分布异常、
文件体积与视觉复杂度不匹配、或题面点名某个工具名。

**动作**：按载体分流，别挨个试。

| 工具 | 载体 | 判据 | 提取 |
|---|---|---|---|
| Stegdetect | JPEG DCT 系数 | `stegdetect -q x.jpg` 报 `jsteg`/`jphide`/`outguess`/`f5` | 用对应工具 + 口令；口令未知跑 `stegseek` |
| JPHide / JPHS | JPEG | `stegdetect -t p` 命中 | `jpseek x.jpg out.txt` |
| OutGuess | JPEG | 保留全部 DCT 系数（不经二次压缩） | `outguess -r x.jpg out.txt` |
| F5 | JPEG | 矩阵编码，改动量极小 | `f5 -e/-d`；`stegseek` 可直接爆破 |
| SilentEye | JPEG/PNG/WAV | 文件尾有 `SilentEye` 标记 | GUI 或 `silenteye-cli` |
| Steghide | JPEG/BMP/WAV | `steghide info x.jpg` 提示需口令 | `steghide extract -sf x.jpg` |
| OpenStego / Camouflage | 多格式 | 尾部附加数据（先过 §2） | 按工具格式解析尾部 |

```bash
stegdetect -q -s 2 x.jpg                          # 先判是哪个工具的产物
stegseek x.jpg /usr/share/wordlists/rockyou.txt   # steghide 口令爆破（秒级）
```

**不成立**：`stegdetect` 全阴性且 `steghide info` 报「无嵌入数据」→ 该图确实没有
工具产物，回测试面表打勾收工，不要继续换工具重试同一方向。
