# 磁盘数据恢复与容器链提取

Volatility、磁盘镜像、VM/OVA/VMDK、云与容器取证见 [[forensics/磁盘与内存/磁盘与内存镜像取证.md|磁盘与内存取证]]；分区表/ZFS/APFS/RAID/内存 carving 见 [[forensics/磁盘与内存/进阶磁盘与内存取证.md|磁盘与内存进阶]]；Unix 提取见 [[forensics/系统取证/Linux 与应用取证.md|Linux 系统取证]]。

容器里为什么 `cryptsetup` / `mount` / `AF_ALG` 全都不可用，以及被堵死后走哪条替代路，见 [[binary/环境与工具/容器能力边界与替代手法.md|容器能力边界]]。

## 0. 判据速查

| 现象 | 优先动作 | 常见误区 |
|---|---|---|
| 挂载后文件缺失 | 先列删除项/孤儿 inode/子卷 | 直接 carving 全盘 |
| 挂载正常但看不到内容 | 检查 shadow 子卷/快照/未挂载分区 | 只挂默认子卷 |
| carving 找不到 magic | 文件系统级 extent 提取 + 反混淆 | 只跑 binwalk/foremost |
| 容器打不开 | 看头尾 magic 与 CRC 字段，先修结构 | 直接报“文件损坏” |
| zip 列出为空 | 核对 LFH/CDE 长度字段是否一致 | 重下/换工具不解结构 |
| zip 有口令 | 区分 ZipCrypto/AES；ZipCrypto 可已知明文攻击 | 直接暴力字符集 |
| 高熵块搜不到任何文件系统 magic、头里有 PBKDF2/xts 字段 | 解析卷头 dump 主密钥（MK），用 MK 直接解密，见 §6 | 直接对整文件穷举口令 |
| 深度嵌套文件 | 逐层 file/识别并递归提取 | 手动逐层点开 |
| 密钥在历史版本 | git 历史/回收站/快照/旧提交 | 只查当前工作树 |

## 1. 内存与运行态密钥恢复

加密卷的主密钥常驻留在进程内存中。AES key schedule 具特殊数学结构，可用 `aeskeyfind` 搜索候选 key；对 LUKS/dm-crypt 等格式，拿到 master key 后可添加新口令再打开卷：

```bash
aeskeyfind memory.elf
echo "<hex key>" | xxd -r -p > master.key
cryptsetup luksAddKey --master-key-file master.key <device>
```

RSA 私钥用 `rsakeyfind`。候选 key 需要验证（能否解密、magic 是否出现），不要把顺序排列的候选直接当 key。

若密钥由时间种子 PRNG 生成，先用文件 mtime/ctime、日志与题面时间圈定窗口，再逐秒重放 PRNG 并用解密后的文件 magic 验证。窗口要覆盖时钟偏移、时区与文件系统粒度，不能只取单一时间戳。

## 2. 文件系统级恢复

### 2.1 删除项与孤儿 inode

FAT 删除只在目录项首字节写 `0xE5` 并把簇标记为空闲，数据仍在。优先用 TSK 列表删除项并按 inode 提取，比盲 carved 更能保留文件边界：

```bash
fls -r -d image.img        # 列出已删除项
icat image.img <inode> > recovered.bin
```

ext2/3/4 删除保留 inode 与数据块；`e2fsck` 可把未挂接 inode 连回 `lost+found`，也可用 `debugfs` 的 `lsdel`/`extundelete` 按 inode 提取。命名破坏（如 `_lag.png`）可结合同目录项顺序与内容 magic 还原。`.git` 等目录删除后，对象文件按 inode 逐个提取即可重建对象库，再用 `git fsck`/`git log --all` 恢复历史。

### 2.2 空闲簇与反 carving

FAT16/32 空闲簇（FAT 项为 0）不清零，按引导扇区参数解析布局后逐个读取即可恢复隐藏或已删数据：

```python
# boot sector → bytes/sector, sectors/cluster, reserved, nFATs, sectors/FAT, root entries
cluster_size = bytes_per_sector * sectors_per_cluster
fat_start = reserved_sectors * bytes_per_sector
root_dir_start = fat_start + nFATs * sectors_per_fat * bytes_per_sector
data_start = root_dir_start + root_entries * 32
```

若 carving 无命中而文件系统显示大小正常，先看是否存在字节级混淆：例如每字节后插入 `0x00` 使体积翻倍、容量翻倍与 magic 断续是典型特征。按文件系统 extent 提取原始块，再做去混淆。

### 2.3 BTRFS 子卷与快照

COW 文件系统删除文件不会立即擦除被快照引用的块。默认挂载只显示活动子卷，先枚举全部子卷再逐一提权挂载：

```bash
btrfs subvolume list /dev/loop0
mount -o subvol=@backup /dev/loop0 /mnt/backup
btrfs-find-root /dev/loop0     # 找孤立旧根
```

子卷 ID、generation 和快照时间是重要证据；不要只依据可见树判定“文件不存在”。

### 2.4 XFS 元数据重建

superblock 损坏但 inode 完整时，可直接解析 inode 内嵌 extent（`startoff/startblock/blockcount`）并按块大小 `dd` 抽取；extent 超过内联容量时循 B+tree 根。修正块号与文件长度后按 magic 校验。文件大小与 extent 覆盖范围不一致时以 extent 为准复核。

## 3. 嵌套容器链

### 3.1 递归提取原则

外层载体打不开、搜不到内容时，假定每个提取物仍是载体。流程固定为：`file` 识别 → 按 magic 提取 → 对新目标重复。`binwalk --dd=".*"` 可批量落地所有签名命中；DOCX/XLSX/PPTX/APK/JAR 本质是 ZIP，直接解包即可。

### 3.2 尾部追加与顺序歧义

- PDF/PNG 之后常附数据：检索 `%%EOF`/`IEND` 之后的内容再 `strings | tail`。
- tar 允许多个同名条目：默认提取只保留最后一个，用 `--occurrence=N` 取中间条目，或程序化遍历成员。
- 深度嵌套 zipped chain：口令若由正则描述，不要穷举字符集，用 `exrex` 生成少量候选后逐层自动提取；每层读提示并更新下一个口令。

### 3.3 文件系统套文件系统

镜像可层层嵌套压缩文件系统（可达数十层）。每步循环执行：识别类型 → 解压/挂载 → 在新层中找下一目标。少见文件系统需预装驱动；无分区表时手动计算偏移挂 loop。

## 4. 压缩与格式修复

### 4.1 头尾互推与 CRC

格式损坏时优先看尾部 footer：XZ 的 footer 保存 stream_flags，可与 header magic、flags、CRC32 一起重建 12 字节头；同样思路适用于 gzip、zstd 等“尾端保存关键字段”的容器。原则是检查最后几字节的真实 footer 签名，再决定修头还是修尾。

### 4.2 ZIP 结构修复

ZIP 列出为空但 magic 正常，通常是 Local File Header（偏移 26）与 Central Directory（偏移 28）的 filename/extra 长度字段被破坏。两处长度必须一致且匹配实际文件名；修好后重写并校验。若仍失败，从候选偏移直接 `zlib.decompressobj(-15)` 试探 raw deflate 数据。

### 4.3 ZipCrypto 与 AES 口令

ZipCrypto（传统 PKZIP 流密码）在已知 12 字节以上明文时可完全恢复内部状态，`bkcrack` 兼容性优于 `pkcrack`；需要未加密参考文件或可猜文件头。AES 加密 zip 只能爆破。先用 `file`/头部字节区分类型，不要混用工具。

### 4.4 特殊压缩模型

FemtoZip 等共享字典压缩需要配套 `.model` 才能解压；按题面提供模型解压后，再按元数据条件筛选产物文件。识别点是出现 `.model` 且大量同构小文件。

## 5. 应用层结构取证

### 5.1 VBA/单元格编码

宏可能把二进制编码进单元格数值（如 `value = byte*3 + 78`）。先读宏找编码公式，逆向得 `byte = (value - c) // m`，再批量还原并用 `file` 校验。注意取数顺序（行优先/列优先）与空单元格处理。

### 5.2 SQLite serial-type

记录中的 serial-type varint 同时表达类型与长度：`type ≥ 13` 表示文本，长度为 `(type - 13)/2`。两份数据库逐字节 diff 后，定位被改动的 serial-type，再读相邻文本载荷即可还原隐藏字段。先理解记录结构再解释差异字节。

### 5.3 Git 历史

删除不等于消失。`git log --diff-filter=D` 找删除提交，`git show <commit>^:<path>` 恢复删除前内容；所有历史提交中的密钥材料都可取回。这类密钥只能用于授权环境下的取证验证。

## 6. VeraCrypt / TrueCrypt 加密卷：头解析与 keyfile 池

**判据**：一段高熵数据（熵接近 8、分组块全唯一、任何偏移都搜不到文件系统 magic），
且满足下列任一：① 卷头区能用 `PBKDF2 + XTS` 解出 `VERA` 并验过 CRC（这是唯一硬判据）；
② 题面给出「口令 / 密钥文件」暗示而负载长度是 64KB 头 + 512 字节整数倍数据区的结构；
③ 已经是 `tcryptDump` 的输出，里面有 `PBKDF2 hash`、`Cipher chain`、`Cipher mode`、
`Payload offset`、`MK bits` 等字段。加密容器题与「高熵就是密文、去试 AES-CBC 口令」
是两条不同的路，先判是不是容器。

> **先注意头是加密的**：VeraCrypt 头里**明文只有 64 字节 salt**，`VERACRYPT` 标识本身
> 在解密之后才出现。所以「偏移 0 直接搜 `VERACRYPT` 字符串」通常搜不到——那是 LUKS 的
> 判法（LUKS 的 `LUKS\xba\xbe` 是明文）。判 VeraCrypt 只能靠「头区可解密并验 CRC」，
> 或靠题型 / 文件长度特征。**不要因为搜不到 `VERACRYPT` 就排除 VeraCrypt。**

**前置**：`cryptsetup tcryptDump --veracrypt` **需要内核 crypto 接口**（`AF_ALG` / `algif_skcipher`）。
容器里这个接口通常被封（seccomp 拒 `socket(AF_ALG)`），此时 `tcryptDump` 会报
`Required kernel crypto interface not available. Ensure you have algif_skcipher kernel module loaded.`
—— **这不是「工具没装」，装包也修不了**。所以第一步是探测，再决定走哪条路。

**动作**：
1. 先分清标准卷与隐藏卷：**标准卷头在偏移 0，隐藏卷头在偏移 65536**（不是卷尾），
   备份头在卷尾上溯 131072；三处都试。
2. **探测能否用 `cryptsetup`**（一条命令定分支，别直接硬上）：
   ```bash
   python3 - <<'PY'
   import socket
   try:
       socket.socket(socket.AF_ALG, socket.SOCK_SEQPACKET, 0)
       print("AF_ALG=ok  → 可试 cryptsetup tcryptDump")
   except PermissionError:
       print("AF_ALG=EPERM → 必须走纯 Python 路径（见动作 3）")
   PY
   ```
   能通再用 `cryptsetup tcryptDump --veracrypt <file>`；报 `algif_skcipher` 缺失就立刻转纯 Python，
   **不要重复试、不要装包、不要猜是不是文件坏了**。
3. **纯 Python 头解析（容器内的主路径）**。头结构（权威定义，见文末出处）：
   偏移 0 起 64B 明文 salt，其后 448B 是 XTS 加密区（占 header 前 512B），整个 header 占 **65536B**。
   派生 `PBKDF2-HMAC-<hash>(口令+keyfile池, salt, dkLen=192, count=<迭代数>)`
   （64B primary key + 64B secondary key + 64B HMAC key；`hash`/`count` 由版本与模式定，
   SHA-512 非系统卷是 500000、隐藏卷 1500000；SHA-256 是 200000/1000000）。
   **判定口令正确的唯一可靠方式是两条同时满足**：解密后前 4 字节是 `VERA`，
   且**头 CRC 对得上**。这里最容易踩的一步是**下标换算**：规范里的 CRC 范围写的是
   「头偏移」，而解密缓冲是从头偏移 64 开始的 448 字节，所以
   `CRC-32 of key area`（规范：校验头 256–511，期望值存于头 72）= `crc32(buf[192:448])`
   与 `buf[8:12]`；`CRC-32 of header fields`（规范：校验头 64–251，期望值存于头 252）
   = `crc32(buf[0:188])` 与 `buf[188:192]`。
   **直接照规范写 `crc32(plain[256:512])` 会永远失败**——448 字节的缓冲上
   `plain[256:512]` 被静默截成 192 字节，CRC 恒不相等，而且不报任何错。
   ```python
   from Crypto.Cipher import AES
   from Crypto.Protocol.KDF import PBKDF2
   from Crypto.Hash import SHA512
   import struct, zlib

   def xts_decrypt(key64, data, sector=0, unit=512):
       """最小 XTS-AES。pycryptodome **没有** AES.MODE_XTS，必须自己写。"""
       k1, k2 = key64[:32], key64[32:]
       c1, c2 = AES.new(k1, AES.MODE_ECB), AES.new(k2, AES.MODE_ECB)
       out = bytearray()
       for off in range(0, len(data), unit):
           blk = data[off:off + unit]
           tweak = c2.encrypt((sector + off // unit).to_bytes(16, "little"))
           for i in range(0, len(blk), 16):
               t = bytes(a ^ b for a, b in zip(tweak, blk[i:i + 16]))
               out += bytes(a ^ b for a, b in zip(c1.decrypt(t), tweak))
               carry = 0x87 if tweak[15] & 0x80 else 0
               tweak = ((int.from_bytes(tweak, "little") << 1) & ((1 << 128) - 1)
                        ^ carry).to_bytes(16, "little")
       return bytes(out)

   def try_header(pw: bytes, hdr: bytes, count=500000):
       """hdr = 该位置起的 65536 字节；返回 None 表示口令/参数不对。
       注意：缓冲区下标 = 头偏移 - 64（缓冲从头的第 64 字节起）。"""
       salt, enc = hdr[:64], hdr[64:64 + 448]
       dk = PBKDF2(pw, salt, dkLen=192, count=count, hmac_hash_module=SHA512)
       out = xts_decrypt(dk[:64], enc, sector=0)      # 448B 明文
       if out[:4] != b"VERA":
           return None
       # CRC-32 of key area：规范覆盖头 256..511 → 缓冲 [192:448]，期望值在头 72 = buf[8]
       if zlib.crc32(out[192:448]) != struct.unpack("<I", out[8:12])[0]:
           return None
       return out
   ```
   解出来后按字段取（均为小端，**括号里同时给头偏移与缓冲下标**）：
   `Volume header format version` 头 68 / buf[4] (2)、
   `CRC-32 of key area` 头 72 / buf[8] (4)、
   `Size of volume` 头 100 / buf[36] (8)、
   `Byte offset of start of master key scope` 头 108 / buf[44] (8)、
   `Size of encrypted area` 头 116 / buf[52] (8)、
   `Sector size` 头 128 / buf[64] (4)、
   `CRC-32 of header fields` 头 252 / buf[188] (4)（校验头 64–251 = buf[0:188]）、
   **master keys 头 256 / buf[192]**（primary 紧跟 secondary，级联加密时多把拼接）。
4. **用 MK 解数据区，与口令彻底无关**：MK 前半/后半各作一把 XTS key，
   tweak 取**扇区号的小端 64 位**，扇区号从头的 `Byte offset of start of master key scope`
   （标准卷默认 131072）起算。拿到 MK 后连 keyfile 池都不用再管。
5. keyfile 池按 VeraCrypt 规则重建：每个 keyfile 取前 1MiB，以 crc32 迭代混合进 64 字节池；
   最多 64 个参与 HMAC、128 个参与 XTS。池与口令共同构成 KDF 输入。
   **keyfile 必须是「原始载体前缀」——即追加/拼接数据之前的那一段，不是拼接后的完整文件**：
   用整文件算池时，任何 hash × 迭代数 × 池大小的组合都不会命中，截断到原始长度后一次命中。
6. 解密后立刻按 magic 校验文件系统（`MSDOS5.0` / `NTFS    ` / ext 的 `0x53EF`），
   再按引导扇区参数（bytes/sector、sectors/cluster、reserved、nFATs、root entries）
   算根目录与数据区，取目标文件。

**降级**：`cryptsetup` 不可用（AF_ALG 被封 / `-ENOTSUP`）→ 走动作 3 的纯 Python 头解析，
只需 `pycryptodome`（本工具箱已装），500k 次 PBKDF2 **在容器内实测约 0.8 s**
（宿主上更快，约 0.3 s——排时间预算按容器内的 0.8 s 算），穷举几十个候选完全够用；
纯 Python 也跑不动（候选太多）→ 改用 hashcat/john 的 VeraCrypt 模式先猜口令，
**注意 hashcat 只有 FDE 模式、没有常规容器 boot-mode**，常规容器要走 2john 类提取；
头 CRC 全不通过且无隐藏卷 → 回到「高熵密文」路线，不要继续耗在加密卷上。

**不成立**：`VERA` 都对不上、CRC 全不通过 → 先怀疑 keyfile 池的取材范围（整文件 vs 原始前缀）
与 keyfile 数量/顺序，以及**隐藏卷的迭代数是另一套**（SHA-512 隐藏卷 1500000，
拿 500000 去试隐藏卷必然全错）；解密后前几个扇区仍是随机字节 → tweak 起点算错
（应从 master key scope 起点而非卷起点计扇区号），或该卷是隐藏卷 / 需换头部位置。
若偏移 0、65536、卷尾三处都算不出 `VERA`，则不是 VeraCrypt，回到「高熵密文」路线。

**工具坑**：
- **`pycryptodome` 没有 `AES.MODE_XTS`**（实测 4.1.0 `hasattr` 为 False）。写
  `AES.new(k, AES.MODE_XTS)` 会直接 `AttributeError`。要么按上面手写 XTS，
  要么用 `cryptography` 库的 `modes.XTS`。
- **`cryptography` 的 `modes.XTS` 把整个入参当成一个 data unit**，不会按 512B
  自动推进扇区号；多扇区必须自己按 `512` 切分、逐段以 `sector + i//512` 调用，
  否则结果静默错（不抛异常，只是解出来是乱码）。
- **两块 CRC 的写入顺序敏感**（自己做题合成卷 / 修复卷头时会踩）：key 区 CRC 存在
  头 72，而头 72 落在「header fields CRC」的覆盖区头 64–251 之内。所以必须
  **先写 key 区 CRC，再算 header fields CRC**；反过来则 header fields CRC 恒错。
  读的时候不受影响，只有生成/修补时才有这个顺序约束。
- **VeraCrypt 卷没有明文签名**，未解密时与随机数据不可区分。`grep -a VERACRYPT` 搜不到是正常的，
  不能据此排除。
- `cryptsetup` 在某个 cipher 返回 `-ENOTSUP` 时会跳出整个 KDF 循环，只试到第一个 KDF 就结束，
  表现成「穷举无果」；需打补丁或改用 gcrypt 后端 / 自写头解析。
- `--key-file` 传的是口令文件，不是 keyfile 池，两者别混。
- `cryptsetup luksDump` 是**可用的**（纯用户态解析 LUKS 头），但 `luksOpen` 挂载在容器里必然失败
  （缺 `dm_mod`、无 `/dev/mapper`）。**不要试图挂载，只做用户态解析 + 自己解数据区。**

## 7. 纪律

恢复按“元数据优先”排序：文件系统 → 容器结构 → 应用结构 → carving → 暴力猜测。所有操作在工作副本进行，记录 inode、偏移、块号、口令来源和步骤；每恢复一层都验证 magic/长度/CRC/可解码性。对 zip/加密容器先判断算法再选工具，避免把可解析问题升级为纯爆破。
