# 污点分析与数据流追踪手册（source→sink）

> 污点分析 = 追踪**不可信数据**从进入系统（source）到触发危险操作（sink）的完整路径。
> 用途：把"这里好像有注入"变成"这条路径可复现"——**是白盒定级的证据来源**。

---

## 一、模型

```
Source ──▶ Propagation ──▶ Sanitizer? ──▶ Sink
(污点源)   (传播路径)      (净化检查)     (汇聚点)
用户输入    变量赋值/传参    过滤/转义/白名单  SQL/命令/文件/网络/模板…
```

**四问闭环**：输入可控吗？→ 能到危险点吗？→ 中间净化有效吗？→ 能构造触发吗？四问全 YES 才够 Critical/High 置信度。

---

## 二、Source 定位（常见污点入口）

| 入口类别 | 例子 |
|---|---|
| HTTP 请求 | query、body(form/json)、path param、header、cookie、filename |
| 文件/日志 | 上传文件内容、被读取的日志行、被跟读的配置 |
| 服务间 | MQ 消息体、RPC 参数、回调/webhook 载荷、缓存值 |
| 环境 | env 变量、注册表、命令行参数（桌面/CLI 应用） |

## 三、传播链取证（逐跳）

- 每一跳都标注 **文件:行号 + 该跳的数据变换**（URL 解码、类型转换、字符串拼接、序列化）。
- 有分支则说明触发条件；经过校验函数则说明**为何可绕过或未生效**。
- **不止追直接调用者**——数据流模型是 `Source → [转换层₁ → … → 转换层ₙ] → Sink`；中间层常见命名 `*Builder/*Provider/*Manager/*Utils/*Handler/*Assemble/*Render` 等，接受外部参数却无净化时即独立注入入口（可能被多个 sink 共享）。
- 向上追溯**最多 3 层**，避免无限递归。

## 四、净化判定（最容易误判的一步）

| 判定 | 说明 |
|---|---|
| 有效净化 | 参数化查询、白名单枚举、强类型约束、上下文相关编码 |
| 疑似净化 | 黑名单替换（可绕）、一次性转义（二次编码绕过）、仅前端校验 |
| 无净化 | 直接拼接/直接传入 sink |

**"有防护"≠安全**：必须证明防护在**该上下文**下不可绕过，否则按疑似/无净化处理。

## 五、报告模板（逐步）

```markdown
## [严重度] 漏洞类型 — path/to/file.ext:行号

### 基本信息
| 属性 | 值 |
|------|----|
| 类型 | SQL注入 / 命令注入 / SSRF / … |
| 严重度 | Critical / High / Medium / Low |
| CWE | CWE-89 / … |
| 位置 | file.ext:行号（函数名） |

### Source（污点源）
位置 / 类型（HTTP参数·Header·文件·…) / 代码片段 / 为何是源

### 传播路径（逐跳 file:line + 操作）
[1] file:行  code / 操作:污点引入
[2] file:行  code / 操作:传递(未净化)
[3] file:行  code / 操作:拼接 → sink

### Sink（汇聚点）
位置 / 危险操作 / 危害

### 分析结论
净化判定 + 触发条件 + 利用复杂度

### PoC / 修复
最小触发载荷 / 参数化或白名单修复
```

## 六、收敛纪律

- 候选链深度 = 1：枚举一轮候选，下一轮只**消化**候选、**不派生新候选**，防无限扩展。
- 同一 pattern 在多个文件出现 → 报 1 条 + 受影响文件清单，不逐个深挖。
